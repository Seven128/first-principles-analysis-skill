# 回归方法

## 目的

回归分成两套互补检查，并在推理套件内增加一组关键节点专项案例。

### 推理回归

使用 `evals/regression-cases.json` 和 `evals/rubric.md`，判断 Skill 是否仍能稳定完成：

1. 定义、识别和分类；
2. 解释技术、人、组织、市场和自然结果怎样形成；
3. 分析怎样达到目标；
4. 比较和选择；
5. 混合的“为什么 + 怎么做”；
6. 将通用规则迁移到未专门举例的新主体。

### 关键节点校验回归

使用 `evals/node-validation-regression-cases.json` 和同一份 `evals/rubric.md`，专项检查候选原因、必要条件、方案路径和小结论在进入正式因果链前是否能够：

- 区分必要条件、充分条件、促进条件、一种实现路径和伴随关系；
- 正确区分逆否命题与否命题；
- 检查“条件存在但结果不成立”和“条件不存在但结果仍成立”；
- 发现反向因果、共同原因和替代路径；
- 区分严格命题与概率命题的反例作用；
- 在发现漏洞后修复节点，而不是只附加“存在例外”。

该专项套件属于推理回归，不是第三套输出模式。它只把高风险节点错误集中出来，方便在通用逻辑变更时快速定位退化。

### 成文回归

使用 `evals/writing-regression-cases.json`、`evals/writing-rubric.md` 和 `evals/writing-style-pairs.json`，判断完整分析能否进一步被整理为：

- 简洁、直白、因果关系清楚的技术文章；
- 不删减关键机制的完整详细方案；
- 面向普通读者的解释文章；
- 条件化决策备忘录；
- 围绕结果链组织的经营分析报告；
- 版本边界清楚的技术演进说明。

成文回归不重新证明分析结论。应先确认推理和关键节点校验通过，并锁定事实、因果、条件、不确定性和评价标准，再评价信息选择、关系表达、局部理解负担、结构去重和辅助材料控制。

两套回归都不以逐字相似度为标准。真正要保持的是问题识别、主体路由、连续因果、关键节点强度、证据纪律、中立性，以及最终交付的阅读效率。

## 成对样本

`evals/writing-style-pairs.json` 保存同一推演中的修改前后片段。它用于校准：

- 有依赖的机制是否被压成并列属性；
- 抽象名词是否隐藏主体和动作；
- 字段是否一次全部展开；
- 例子是否重复正文；
- 条件化结论是否被方法说明挡住；
- 比喻是否增加额外理解任务。

“after” 不是需要逐字复制的标准答案。评审应学习其中的变换逻辑，并检查是否保持 `must_preserve`、没有加入 `must_not_infer`。

## 执行步骤

1. 核心推理规则变更时运行全部推理案例和全部关键节点专项案例；局部主体指南变更时至少运行相关案例和两个迁移案例。
2. 成文规则变更时运行全部文章案例，并至少抽查三个对应的推理案例，确认没有用压缩替代分析。
3. 使用推理案例生成完整分析，先记录不能改变的事实、因果、条件、不确定性和评价标准。
4. 对直接支撑最终结论的节点，检查关系类型、反例、反事实、替代路径、因果方向和证据强度。
5. 使用文章案例中的 `prompt` 生成成稿。
6. 先检查对应套件的 `global_invariants`、案例的 `must` 和 `must_not`。
7. 推理输出使用 `evals/rubric.md` 评分；文章输出再使用 `evals/writing-rubric.md` 评分。
8. 对照 `evals/writing-style-pairs.json` 定位失败变换，不复制示例措辞。
9. 记录失败层级：问题识别、方向、主体、因果、节点校验、事实、中立、信息筛选、关系平铺、段落混杂、抽象名词、辅助材料或整体阅读。
10. 修复最上游的通用原因后，用同一输入重跑。
11. 结构检查通过后仍需实际模型输出评审。

## 同推演多版本测试

验证成文规则时，优先冻结同一份推演，只改变写法。建议生成：

```text
A：当前基线版
B：极度压缩版
C：新成文规则版
D：更强叙事或比喻版
```

随机隐藏版本名称。先测试读者能否正确复述关键事实和因果，再询问阅读偏好。不能只问“更喜欢哪一篇”，因为故事和比喻可能提高偏好，却没有提高正确理解。

建议分开记录：

- 关键事实与因果的正确复述；
- 错误理解；
- 阅读时间；
- 回读位置；
- 主观理解难度；
- 文风偏好。

句长、术语数和自动可读性分数只能用于相对预警，不能替代理解测试。

## 最低通过条件

### 推理套件

- 每个案例建议总分不少于 16/20；
- 不得出现 `evals/rubric.md` 中的严重错误；
- 旧核心案例不出现明显退化；
- 新增的人、组织、行业、商业、定义和迁移案例达到通过标准；
- 关键节点专项案例全部满足各自 `must`，且不出现 `must_not`；
- 输出不暴露内部路由、公式和检查表；
- 通用结论只在条件成立时使用。

### 成文套件

- 每个案例建议总分不少于 10/12；
- 不得出现 `evals/writing-rubric.md` 中的严重错误；
- 标准文章不退化为研究记录、压缩报告或模块百科；
- 完整详细方案不因压缩而遗漏用户点名的关键机制；
- 已证明的依赖在成稿中可见，并行条件没有被改写成新因果；
- 每段闭合一个主要新结论，同一结论不在多个章节重复；
- 抽象内容优先改成主体、动作和状态变化；
- 字段、术语和实现细节在成为当前答案时出现；
- 例子、表格、代码、引用和比喻只在降低理解成本或提高证据效率时使用；
- 压缩后仍保留必要因果。

## 评分记录

推理评分模板：

```text
evals/score-template.json
```

文章评分模板：

```text
evals/writing-score-template.json
```

汇总推理评分：

```bash
python3 scripts/eval_report.py scores.json
```

汇总文章评分：

```bash
python3 scripts/eval_report.py writing-scores.json --suite writing
```

## 结构校验

```bash
python3 scripts/validate_skill.py
python3 scripts/validate_node_reasoning.py
python3 scripts/validate_writing.py
python3 scripts/validate_conclusions.py
python3 scripts/lint_language.py --strict
```

`validate_node_reasoning.py` 检查专项案例文件的结构、必需案例和评分维度。所有脚本都只检查仓库结构、来源哈希、指南字段、结论卡、成文运行时材料、回归清单、成对样本和高风险措辞，不替代模型输出质量回归与阅读理解测试。
