# 回归方法

## 目的

回归分成两套互补检查。

### 推理回归

使用 `evals/regression-cases.json` 和 `evals/rubric.md`，判断 Skill 是否仍能稳定完成：

1. 定义、识别和分类；
2. 解释技术、人、组织、市场和自然结果怎样形成；
3. 分析怎样达到目标；
4. 比较和选择；
5. 混合的“为什么 + 怎么做”；
6. 将通用规则迁移到未专门举例的新主体。

### 成文回归

使用 `evals/writing-regression-cases.json` 和 `evals/writing-rubric.md`，判断完整分析能否进一步被整理为：

- 直白、紧凑的技术文章；
- 不删减关键机制的完整详细方案；
- 面向普通读者的解释文章；
- 条件化决策备忘录；
- 围绕结果链组织的经营分析报告。

成文回归不重新证明分析结论。应先确认推理通过，再评价信息筛选、因果压缩、结构去重、语言流畅和辅助材料控制。

两套回归都不以逐字相似度为标准。真正要保持的是问题识别、主体路由、连续因果、证据纪律、中立性，以及最终交付的阅读效率。

## 执行步骤

1. 核心推理规则变更时运行全部推理案例；局部主体指南变更时至少运行相关案例和两个迁移案例。
2. 成文规则变更时运行全部文章案例，并至少抽查三个对应的推理案例，确认没有用压缩替代分析。
3. 使用案例中的 `prompt` 生成新输出。
4. 先检查对应套件的 `global_invariants`、案例的 `must` 和 `must_not`。
5. 推理输出使用 `evals/rubric.md` 评分；文章输出再使用 `evals/writing-rubric.md` 评分。
6. 必要时对照旧案例，只比较因果能力和表达效果，不复制措辞和未经核验的事实。
7. 记录失败层级：问题识别、方向、主体、因果、替代解释、事实、中立、信息筛选、因果压缩、结构去重或语言。
8. 修复最上游的通用原因后，用同一输入重跑。

## 最低通过条件

### 推理套件

- 每个案例建议总分不少于 16/20；
- 不得出现 `evals/rubric.md` 中的严重错误；
- 旧核心案例不出现明显退化；
- 新增的人、组织、行业、商业、定义和迁移案例达到通过标准；
- 输出不暴露内部路由、公式和检查表；
- 通用结论只在条件成立时使用。

### 成文套件

- 每个案例建议总分不少于 10/12；
- 不得出现 `evals/writing-rubric.md` 中的严重错误；
- 标准文章不退化为研究记录或模块百科；
- 完整详细方案不因压缩而遗漏用户点名的关键机制；
- 同一结论不在多个章节重复；
- 压缩后仍保留必要因果；
- 例子、表格、代码和引用只在增加理解时使用。

## 评分记录

推理评分模板：

```text
evals/score-template.json
```

文章评分模板：

```text
evals/writing-score-template.json
```

汇总推理评分：

```bash
python3 scripts/eval_report.py scores.json
```

汇总文章评分：

```bash
python3 scripts/eval_report.py writing-scores.json --suite writing
```

## 结构校验

```bash
python3 scripts/validate_skill.py
python3 scripts/validate_conclusions.py
python3 scripts/lint_language.py --strict
```

这些脚本检查仓库结构、来源哈希、指南字段、结论卡、两套回归清单和高风险措辞，不替代模型输出质量回归。
