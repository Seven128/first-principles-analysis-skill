# 旧案例使用说明

`references/回归样例/` 保存 v1 阶段的长篇案例。它们是来源基线和回归材料，不是可以整篇模仿的标准答案。

## 可以学习

- 从任务要求推到能力缺口；
- 机制按依赖关系出现；
- 技术细节与实际例子结合；
- 方案与问题建立对应关系；
- 对复杂系统给出可运行的整体链路。

## 不应直接复制

- “绝对、物理、完美、降维、跃迁”等夸张表达；
- 没有版本范围的实现细节；
- 把合理推断写成历史事实；
- 把现有模块直接写成唯一必要条件；
- 未经重新检查的安全、商业或平台做法；
- 将案例中的人物、市场和产品结论迁移到新问题。

## 各案例的使用边界

### Fiber

可用于检查：

- 旧同步递归执行与可保存工作单元之间的因果；
- 可中断后为什么需要中间结果隔离、优先级和集中提交。

需警惕：

- 当前版本实现细节被写成所有历史版本的统一事实；
- 先列 Fiber、Lane、双缓存、flags 再补理由。

### HTTP

可用于检查：

- 明确版本演进触发下的问题—方案链；
- 长连接引入后为什么需要报文定界；
- HTTP/1.1 的局限怎样继续推动 HTTP/2。

需警惕：

- 把后代协议面对的问题倒写成早期设计者已经完整预见；
- 使用“绝对、彻底、物理”等词替代协议事实。

### Node

可用于检查：

- 单线程、异步来源和调度机制之间的关系；
- 规范事实与版本实现边界。

需警惕：

- 将不同 Node.js/libuv 版本的阶段行为写成永恒事实；
- 将实现比喻当作内存和机器码层面的严格证明。

### 浏览器安全

可用于检查：

- 将攻击拆成成立条件；
- 防御机制具体切断哪个环节；
- 区分 XSS、CSRF 和 CORS 的责任边界。

需警惕：

- 把单一安全属性写成所有部署中的充分防御；
- 把 CORS 当成服务端授权或通用 CSRF 防御；
- 使用“绝对隔离、完美平衡”等表达。

### Harness 工程与 AI SDLC

可用于检查：

- 从模型和工程限制推到状态、上下文、执行和治理机制；
- 区分宿主真正执行的硬机制与模型阅读的软约束；
- 复杂工作流中的阶段、状态、检查和恢复。

需警惕：

- 为了架构完整而新增没有问题来源的模块；
- 把自然语言文件单独称为不可绕过的安全边界；
- 把某个客户端实现泛化为所有 Agent。

### API 中转站获客

可用于检查：

- 触达、注册、首次使用、留存和传播不是同一个结果；
- 用户价值、价格、信任和渠道之间的关系。

需警惕：

- 将心理操纵、虚假信息、批量滥用免费额度、规避平台限制或侵权路径当作推荐方案；
- 把曝光直接等同于真实用户增长。

## 使用方法

1. 先使用 v2 核心规则独立生成分析；
2. 只在定位结构退化时读取最相关案例；
3. 对照案例中的因果能力，而不是措辞和完整模块清单；
4. 案例事实重新核验后才可进入新文章；
5. 发现案例错误时记录为回归禁项，不静默改写原始来源。
