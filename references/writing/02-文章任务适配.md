# 文章任务适配

通用成文规则先保证正确理解和较低理解成本。本文件只决定不同文章任务怎样组织，不改变分析阶段已经成立的事实、因果和评价标准。

## 0. 所有文章先呈现实质问题

无论文章类型如何，标题之后默认先写补全后的读者可见问题。后续结构再按对象是否承载明确目的进行适配。文章契约默认以当前提出问题的人为读者，但正文不写“用户当前材料”等生成上下文。

## 1. 原理与机制解释

### 读者任务

理解某个技术、制度、现象或结构为什么出现，以及主要机制怎样协作。

### 默认顺序

```text
读者可见问题
→ 适用时的最终目的
→ 对象或结果概括
→ 形成前已有能力或条件
→ 当前任务还要求什么
→ 已有能力为什么不够
→ 推出第一项能力或机制
→ 新状态暴露什么后续问题
→ 推出后续机制
→ 边界、代价和证据
```

### 成文重点

- 机制按真实依赖出现；
- 先写问题和抽象能力，再写术语；
- 当前实现与逻辑需要分开；
- 字段在成为当前答案时展开；
- 一个例子可以串起多项机制时，只使用一次；
- 父标题直接写明对象与总关系，并行能力和主要因果阶段使用信息型小标题；父节不提前完整复述子节。

### 避免

- 开头列完整模块表；
- 把现有结构反推成形成原因；
- 每个字段都附定义、代码和例子；
- 用夸张词或比喻代替机制；
- 使用只写“两类能力”“第一个断点”“核心机制”等隐藏实际内容的标题。

## 2. 完整方案与系统设计

### 读者任务

理解方案解决什么问题、由哪些机制构成、怎样衔接、如何验证，以及需要付出什么成本。

### 默认顺序

```text
读者可见问题
→ 最终目的与完成标准
→ 当前关键差距
→ 总体设计原则
→ 按依赖展开机制
→ 机制之间的数据、状态或责任流
→ 异常和恢复
→ 验证、成本与适用边界
```

### 成文重点

- 用户点名的关键机制全部保留；
- 每项机制能追溯到一个问题；
- 目录和数据结构只在实施需要时展开；
- 同一状态结构只在最合适的位置完整说明；
- 详细程度来自关键分支和边界，不来自重复。

### 避免

- 把完整方案压成原则摘要；
- 在总体思路、模块、生命周期和总结中重复同一内容；
- 为架构完整感加入没有问题来源的模块；
- 把自然语言约束写成底层已经执行的控制。

## 3. 决策备忘录与比较

### 读者任务

在明确目标和评价标准后，判断不同选项在什么条件下更合适。

### 默认顺序

```text
读者可见问题
→ 当前能给出的条件化结论
→ 使用哪些评价标准
→ 各选项怎样影响这些标准
→ 哪些事实已知，哪些是预测
→ 结论对哪些假设敏感
→ 最值得补充的信息
```

### 成文重点

- 尽快给出“在什么条件下选什么”；
- 比较标准来自用户目标，不替用户排序；
- 表格只用于真实横向比较；
- 缺失信息按决策价值排序，不列通用调查表。

### 避免

- 长篇介绍决策方法后才开始比较；
- 对每项标准重复两边完整背景；
- 编造个人条件或公司前景；
- 给没有条件说明的单一答案。

## 4. 经营、商业与行动分析

### 读者任务

理解结果由哪些环节共同产生，当前断点在哪里，哪些干预能够改变结果，以及怎样验证。

### 默认顺序

```text
读者可见问题
→ 目标结果和口径
→ 结果形成链
→ 当前已知断点和待验证断点
→ 每项干预对应哪个断点
→ 成本、依赖、规则和单位经济
→ 执行顺序和指标
```

### 成文重点

- 曝光、注册、首次成功、留存、付费和传播等结果分开；
- 渠道、产品、信任、价格和运营措施分别对应明确问题；
- 方案按验证价值和依赖排序；
- 法律、平台规则和经营约束靠近对应方案说明。

### 避免

- 把营销手段写成长清单；
- 用过程指标替代最终结果；
- 在每个阶段重复同一用户需求；
- 把需求存在直接写成支付成立。

## 5. 人的行为与社会机制解释

### 读者任务

理解一个行为、情绪或群体结果可能怎样形成，同时保留证据边界和替代解释。

### 默认顺序

```text
读者可见问题
→ 可观察事件或结果
→ 主体可能感知到什么
→ 可能怎样解释
→ 哪些预期、需要、利益或身份受到影响
→ 形成什么情绪、判断或行动倾向
→ 主要候选解释
→ 用什么证据区分
```

### 成文重点

- 客观事件与主体理解分开；
- 多个候选原因共享同一主链时，先讲共同过程，再列分支；
- 心理术语只在提高准确性时使用；
- 一次行为不足以确认人格、动机和成长经历。

### 避免

- 为每个候选原因重复一套完整流程；
- 用人格标签代替作用过程；
- 为生动建立一套拟人角色或比喻系统；
- 在结尾再次复述所有候选原因。

## 6. 定义与分类

### 读者任务

知道一个概念的边界、必要属性、相邻概念和识别方法。

### 默认顺序

```text
读者可见问题
→ 简洁定义
→ 必要属性
→ 排除边界
→ 相邻概念
→ 一个例子和一个反例
```

### 成文重点

- 先直接回答是什么；
- 只有用户需要形成原因时才继续解释；
- 例子用于检验边界，不扩展成历史文章。

### 避免

- 把定义问题强行改写成形成史；
- 为简单概念加入完整第一性原理框架；
- 用多个近义比喻替代精确定义。

## 7. 读者水平适配

默认读者是当前提出问题的人。适配体现为术语选择、解释深度和内容范围，不是在正文中说明“用户已经知道什么”或引用其其他材料。

### 普通读者

- 先说明日常含义，再给术语；
- 展开关键中间因果；
- 使用一个短例子帮助观察机制；
- 默认省略字段、源码和历史旁支。

### 有基础读者

- 可以直接使用常见术语；
- 保留决定结构的主要机制；
- 只解释容易混淆或对结论关键的部分；
- 代码和字段按问题需要出现。

### 专业读者

- 术语可以更紧凑，但因果和版本边界仍要显式；
- 可以展开接口、状态和取舍；
- 不因为读者专业就把依赖压成名词清单；
- 详细实现与原理主线分层组织。

## 8. 可选语气与作者风味

技术原理、系统说明和一般报告默认使用中性、自包含的说明口吻，不反复使用“我、你”，也不把读者称为“用户”。个人行动建议可以在确有必要时使用“你”；只有用户明确要求代其发文时才使用“我”。全文不得在不同视角之间无理由切换。

默认语气是平静、中性、直接、具体。

第一人称、故事、幽默、情绪、悬念、口头禅、短段落和文化联想属于可选风味。只有用户明确要求，或真实材料本身包含第一手经历时才使用。

可选风味必须服从以下边界：

- 不编造亲身经历和情绪；
- 不让口语降低事实精度；
- 不强制每篇从故事开始；
- 不强制不用标题；
- 不规定固定字数、句长或口语词数量；
- 不把某位作者的个人风格当成跨领域通用规则；
- 不让“像真人”覆盖正确理解、证据边界和读者任务。
