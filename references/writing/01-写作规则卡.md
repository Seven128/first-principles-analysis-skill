# 写作规则卡

本文件把“简洁、直白、直接、信息密度高而不密”转换成成文操作和示例，不重新分析事实和因果。局部结论统一遵守 `references/core/05-输出与表达规则.md` 第 5 节；去套话与术语保真遵守第 6 节；段落分组、例子时机和证据展示的详细规则统一见 `references/writing/04-信息密度、段落与例子控制.md`。

## 0. 先完成分析交接与文章契约

成文前必须已经存在语义锁定的分析定稿，并建立文章类型、目标读者、读者任务、职责范围、范围外内容、结构、详细程度、叙述视角和交付载体。写作规则只转换分析定稿，不能直接从原始对话继续推理。

### 文章开头先写读者可见问题

标题之后的第一个实质内容默认写出文章契约中的读者可见问题。它从核心问题生成，直接说明主要对象和真正未知；内部完整分析任务中的支撑问题、必须覆盖项、资料来源和版本边界分别保留，不复制成长问句。读者可见问题不能只写“Agent”“Fiber”等主题，也不能用定义、答案或“本文将介绍”替代。

目的结构适用时，读者可见问题之后继续保留最终目的、当前状态与要解决的问题、采用的方案。这里的“要分析的问题”描述文章回答什么，“最终目的”描述行动主体希望达到的结果，或人为设计物最终形成的稳定角色与目标状态，二者不能合并。

### 先区分结论句与解释段

结论句用完整陈述给出当前位置的主答案，解释可以由一个段落或相邻段落组说明依据与实现。语法完整、位于段首或已经加粗，都不足以证明主答案已经说全。改写前先确定当前职责，不能总把准确的概括扩写成过程说明。

在一篇讨论大模型接口型 Agent 的文章中，定位句可以是：

> Agent 是基于大模型接口的通用任务执行应用。

这里先说清类别、核心职责与讨论范围。规划、工具、反馈、状态和验证在各自问题出现后说明，不挤进定位句；这也不构成对所有 Agent 的无条件定义。

已经足够的结论可以保持原样：

> 阶段契约规定当前阶段的输入、产出和完成条件。

若当前只需说明职责，就在这里结束。只有读者还需要知道这些约定怎样减少阶段衔接遗漏，才继续解释。简短、准确、无需改写也应作为正向结果。

### 完整陈述要给出具体判断

以下变换依据已提供的 Agent 验证与停止片段。它们示范结论怎样说全，不据此断言所有 Agent 都实现了相同机制。

| 未给出主答案的表达 | 直接陈述具体判断 |
| --- | --- |
| 验证与停止：让完成判断对应实际证据。 | Agent 应根据任务要求和验证结果判断任务是否完成。 |
| 动作成功只证明该动作的结果。 | 单次操作成功不足以证明整个任务已经完成。 |
| 验证结果还需要进入后续判断。 | 验证失败时，模型应根据错误信息调整方案；验证成功时，应用应保留已检查的要求和结果。 |
| 要求模型检查，与程序阻止未经检查的完成，是不同强度的设计。 | 提示词依赖模型遵循；程序检查可以在缺少规定证据时拒绝完成请求。 |
| 验证本身也有边界。 | 测试通过不能证明未覆盖的需求已经满足。 |
| 停止原因需要与成功分开。 | Agent 可能因任务完成而停止，也可能因执行受阻或预算耗尽而停止。 |

程序检查的例子以完成入口由程序控制为前提，正文仍须保留这个条件。操作成功的例子仍应解释文件写入和命令退出各自能证明什么。把主答案提前后，必要依据继续留在正文。

比较说出差异，分类说出分法，边界说出限制，机制说出作用。若还要读后文才能回答“具体是什么”，先补齐主答案；“为什么成立、如何实现”可以留给解释。先不带格式检查结论，合格后才按需强调，不给每段首句自动加粗。

## 1. 一句推进一个主要关系

### 解决的问题

一句话同时装入多个事实、术语、条件和结论，或者虽然没有长句，却没有直接回答当前问题。

### 生成规则

先选准当前位置的主要结论，再用完整陈述把答案说全。一个句子以一个主要新结论或主要关系为中心；多个可以独立成立的结论优先拆开，并保留真实连接词。

### 适用与例外

适用于解释、方案、决策和报告。简短且关系紧密的比较可以有两个分句；横向比较可以使用列表或表格。不按固定字数判断质量。否定、条件和不确定判断同样可以构成完整陈述。

### 常见失败

- 只把所有长句机械拆成短句，仍让读者自行归纳重点；
- 拆句后删除“因此、但、只有、同时”等关系；
- 用句号或粗体包装“有边界”“需要区分”等未说全的判断；
- 定位句同时列出后面的机制和验收要求。

### 改写示例

修改前：

> Fiber 将递归渲染改造成可保存进度、可分片、可调度、可丢弃、可集中提交的任务系统。

若当前小节只说明“进度怎样保存”，局部结论写成：

> React 把渲染进度保存在 Fiber 中，以便暂停后继续计算。

需要解释时，再说明进度如何从调用栈变成可保存的数据。分片、优先级和提交仍在对应小节保留，不因为当前结论变短而删除。

### 检查

保留已说明的对象范围，暂时隐藏后文和强调格式，是否仍能获得具体判断？若只有话题或铺垫，补齐分析定稿已经支持的主答案；若缺少依据，返回分析。独立谓词、新术语和长并列只作为预警，不设置机械阈值。

## 2. 从平铺属性中恢复真实依赖

### 解决的问题

作者知道几个机制彼此相关，正文却只给出名词清单，读者需要自行推断它们为什么一起出现。

### 生成规则

多个机制之间存在“先有 A 才能推出 B”的关系时，按依赖顺序解释；某项机制处理前一项带来的新问题时，紧接前一项说明。已经证明的局部结论可以先呈现，再给依据。

### 适用与例外

适用于技术演进、制度设计、行业机制、行为因果和方案设计。原分析没有证明依赖时，保留并列或不确定性。

### 常见失败

为了显得有逻辑，凭空制造先后关系，改变原推演。

### 改写示例

修改前：

> Agent 需要工具、反馈、权限、状态和记忆。

作为解释段，修改后：

> 模型先需要工具把动作落到外部环境。动作执行后，结果还要返回模型，否则下一步判断仍然基于旧状态。真实动作可能产生副作用，因此执行前还需要权限和确认边界。任务跨越多轮后，系统又要保存当前进度。

这段展开适合解释多项机制的来源，不用于替换一个已经准确的定位句。

### 检查

看到连续的“A、B、C”或“需要 A、B、C”时，回查推演是否存在依赖边。没有证据时，不自动改写成因果。

## 3. 抽象名词还原为主体、动作和状态变化

### 解决的问题

句子听起来专业，但读者无法想象真实发生了什么；删除几个套话后，剩下的句子仍然没有实质答案。

### 生成规则

按输出规则第 6 节删除无信息的开场、修饰和套话，用明确主体和动词说明实际关系。先保证主答案完整，再删除包装。原文没给出的动作、对象或效果，不为凑一句具体话而补造。

### 适用与例外

适用于所有文章，尤其技术、商业和组织分析。正式术语、精确标识符和原文引语保留。真正的比较、排除条件、范围边界与不确定性也保留，不按词表机械删除。

### 常见失败

- 为了口语化删除必要术语；
- 只把抽象名词换成另一组抽象名词；
- 给所有结论加“值得注意的是”“简而言之”等开场；
- 无人提出相反观点，却先写一段“不是……而是……”；
- 删除修辞后把“尚未验证”也删掉，使结论变强。

### 改写示例

已知系统保存任务进度供下次继续时：

> 需要实现执行状态的持久化能力。

改为：

> 系统保存当前执行进度，下次从这里继续。

已知检查结果返回模型供下一轮使用时：

> 值得注意的是，这一机制真正赋能了后续判断，形成强大的反馈闭环。

改为：

> 应用把检查结果返回模型，供下一轮判断使用。

若只收到“这一机制提供全面支撑”，却不知道具体动作，不能直接套用上面的改写，应先指出缺少哪项信息。

### 检查

删除包装后是否仍有完整答案？新增的主体、动作和效果能否追溯到分析定稿？“闭环”“机制”等词本身不是错误；只在它们遮住实际关系时改写。准确而直接的原句可以不改。

## 4. 细节在第一次成为必要答案时出现

### 解决的问题

介绍一个结构时一次展开全部字段、模块和术语，读者尚未理解问题来源就面对实现百科。

### 生成规则

字段、模块、协议或术语在它第一次成为当前因果问题的必要答案时进入主文。后续需要源码级说明时，再在对应位置展开。

### 适用与例外

适用于技术原理、系统设计、制度规则和复杂方案。用户明确要求字段参考手册时，可以集中列出，但应与原理主文分开。

### 常见失败

- “属于这个结构”被当成“现在就要介绍”；
- 为完整感提前列出全文答案；
- 每个字段都附定义、代码和例子。

### 改写示例

修改前：

> Fiber 节点包含 child、sibling、return、lanes、childLanes、flags、subtreeFlags、deletions 和 alternate。

修改后：

> 要暂停遍历，React 先要保存当前节点、父节点和接下来处理哪个节点，因此 Fiber 记录 child、sibling 和 return。

优先级和中间结果隔离的细节留到对应小节，再分别说明 lanes 与 alternate。不要把这种写作安排本身写进成稿。

### 检查

对每项细节追问：它在当前段落解决了哪个已经成立的问题？答不出来时后移、合并或删除。

## 5. 段落分担阅读任务，共同完成论点

### 解决的问题

同一段连续解释多个任务，或为了“结论闭合”把复杂论证压进长段；反过来，机械逐句换段又切断紧密关系。

### 生成规则

先选准主要结论并完整说出具体判断，再按问题、作用过程、依据或边界等阅读任务组织。一个论点可以由多个相邻段落共同完成，不要求每段重复结论。具体分组遵守 `references/writing/04-信息密度、段落与例子控制.md` 第 2 节。

### 适用与例外

适用于连续正文。简单关系可以用一个紧凑段落，独立小点一句话已完整回答时停止。标题已表达结论时，后文直接说明，不为每个段落增加标题。普通正文也可以清楚呈现结论，不强制加粗。

### 常见失败

- 固定两句话一段、一个论点固定占一段，或每段首句自动加粗；
- 为了留白把完整因果拆成多个孤立句；
- 一段同时讲工作单元、优先级、双缓存和提交；
- 每段都重复结论，或给简单结论强配背景、例子和小结。

### 改写示例

修改前：

> React 需要保存进度、处理优先级并隔离中间结果，所以 Fiber 记录遍历指针、Lane 和 alternate，最后统一 Commit。

修改后先按问题拆分：进度保存、优先级和中间结果隔离分别承担独立结论。每个论点需要的解释可以再分成相邻段落；这些段落分别完成必要任务，不能用一个长句提前复述全部小节。

### 检查

先检查承担结论的句子是否说全主答案，再检查段落是否各有明确任务。跨段后主体和关系能否连续跟随？主要结论是否在合适位置可见，而不是每段机械复述？只在后文才补齐真正答案时，应修复结论；涉及多个独立答案时，重组段落。

## 6. 例子必须替正文完成一项工作

### 解决的问题

例子只把结论换成具体名词再讲一遍，或者虽有理解价值，却被推迟到读者已经难以继续的位置。

### 生成规则

例子只有在使机制可观察、串联因果、区分概念、展示边界或检验理解时保留。在第一次帮助理解时使用，允许位于抽象概括之前、机制之中或原理之后。时机、场景复用和证据区别统一见 `references/writing/04-信息密度、段落与例子控制.md` 第 3、4 节。

### 适用与例外

结论已经直观，或例子比机制更复杂时不使用。假设性例子必须按文章契约第 7 节标示说明性质，不新增机制或事实，不能替代真实证据。

### 常见失败

- 每个章节重复同一个完整案例；
- 案例细节比被解释对象还多；
- 用案例替代因果证明或掩盖证据缺口；
- 按固定段落间隔插例子，或强制全部例子后置。

### 改写示例

修改前：

> 工作单元、双缓存、Lane 和 Commit 四节都完整重讲搜索输入案例。

修改后：可以只在优先级章节用一次搜索输入，也可以复用同一场景，在各节只展示当前新关系。前面已交代的输入不重讲，后面不再完整重演。是否需要例子取决于读者理解，不能为了贯穿全文补造场景。

### 检查

删除例子后理解成本是否增加？例子是否及时？多个例子是否同功能？真实演示的支持范围与说明性例子是否清楚？

## 7. 先具体化，最后才考虑比喻

### 解决的问题

为追求生动加入新的意象系统，读者既要理解目标概念，又要理解比喻和两者映射。

### 生成规则

优先选择准确的字面因果、具体主体与状态变化，再判断是否需要最短相关例子；局部类比或比喻只在进一步降低理解成本时使用。这个优先级不规定例子必须等全部原理讲完才出现。

### 适用与例外

适用于技术、科学、商业机制和人的行为。读者缺少心智模型，且熟悉参照物能够用更短文字准确映射时，可以使用类比。

### 常见失败

- 一个概念连续使用多个比喻；
- 比喻暗示目标对象没有的属性；
- 比喻成为正文主角；
- 使用后不再解释字面机制。

### 改写示例

修改前：

> Fiber 像给 React 装上了一个可以随时存档的时间机器。

修改后：

> React 把当前处理到哪个 Fiber 保存下来。主线程需要处理更紧急的工作时，它可以先停；下次再从保存的位置继续。

### 检查

比喻进入正文前确认：

1. 读者确实缺少心智模型；
2. 参照对象更熟悉；
3. 映射局部且清楚；
4. 不带入错误属性；
5. 比直接解释更短、更好理解。

任一项不成立时，改用具体过程或例子。

## 8. 删字不能删掉因果桥

同样不能把实际分析问题和适用的结构性节点当作重复铺垫删除。它们负责确定文章任务和因果位置，不等同于正文后面的答案。

### 解决的问题

文章看起来更短，却只留下“事实 A，所以结论 C”，中间作用过程 B 被删除。

### 生成规则

删除重复、旁支和无关细节时，保留从事实到结论不可缺少的中间关系与必要限定。关系可以出现在结论后的解释中，不要求全部挤进结论句；后文不能替结论补齐主答案。承接下一步的简短回指、文字与展示之间有用途的互补说明可以保留，不按信息重合直接删除。

### 适用与例外

适用于所有压缩。读者依据常识已经能够稳定补全且不会误解的步骤，可以概括，但不能改变结论成立条件。

### 常见失败

- 把完整链压成模块名；
- 用“因此”掩盖未说明的中间过程；
- 为控制篇幅删除限制和条件；
- 为去套话删掉必要否定、条件或不确定性。

### 改写示例

修改前：

> 模型只能输出文本，所以 Agent 需要工具、权限、状态和记忆。

作为解释段，修改后：

> 模型输出的动作意图不会直接改变文件或外部服务，因此需要执行器完成真实操作。操作结果还要返回模型，下一步判断才能依据现实变化。真实操作可能产生副作用，所以执行前还需要权限和确认边界；任务跨越多轮时，还要保存当前进度。

### 检查

对每个“所以、因此、从而”反向追问：正文是否说明中间作用过程？删掉某句后，读者是否仍能准确回答“为什么会得到下一步”？若不能，补回因果桥。不要把“说明依据”误读成“结论必须最后出现”。
