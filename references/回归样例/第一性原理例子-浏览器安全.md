# Web 前端安全与防御架构 第一性原理推演

## 1\. 最终目的 \(The Absolute Objective\)

实现Web前端对可能发生的攻击的防御能力

可能发生的攻击：

1. 不受控的代码执行

2. 盗用的身份凭证访问

---

## 2\. 目前现状与要解决的问题 \(Current Status \& The Root Conflict\)

### 关于 XSS 攻击的浏览器现状与攻击

- **现状：**

    - **浏览器解析引擎对脚本与文本的无差别执行机制。** 浏览器引擎在处理响应数据流时，无法识别符合规范的 HTML 标签（如 `<script>`）是属于业务原本数据还是外部第三方注入，均会触发脚本执行引擎。

- **实际攻击：**

    - **恶意注入的数据越权获取当前环境代码执行能力。** 黑客通过数据库持久化（存储型）、URL 反射（反射型）或 JS 纯前端操作（DOM 型）注入载荷，恶意代码在合法的页面上下文中被执行，窃取会话凭证。

### 关于 CSRF 攻击的浏览器现状与冲突

- **现状：**

    - **HTTP 底层网络模型对凭证的无脑隐式携带机制。** 浏览器底层网络模块在构建网络请求时，遵循“只要目标域名匹配，即自动附加对应的 Cookie”规则，完全脱离了请求发起的页面上下文。

- **实际冲突：**

    - **同源策略允许单向发送机制导致的非自愿鉴权被滥用。** 同源策略（SOP）限制了跨站的“读”权限，但未封锁跨站的“写/发送”权限。黑客利用这一不对称性，诱导用户在第三方恶意站点发出请求，借用底层的隐式 Cookie 越权执行高危业务。

## 3\. 采用的方案 \(First\-Principle Solutions\)

### XSS 防御

#### HTML敏感字符转义

在服务端响应 HTML 报文或前端写入 DOM 之前，强制对不可信数据进行实体编码（如 \< 转为 \<），在词法层面将其降维为纯文本，阻断脚本解析器的执行通路。

#### HttpOnly

服务端在 HTTP 响应头中下发 Set\-Cookie: session=xxx; HttpOnly。浏览器协议栈接收该属性后，在前端接口层物理锁死 document\.cookie 对该凭证的访问权，使 XSS 脚本即便执行也无法窃取会话。

#### CSP 协议

彻底放弃应用层黑名单，服务端通过 Content\-Security\-Policy HTTP 响应头向浏览器下发最高优先级的安全声明。

- **资源网络拦截**：浏览器在发起外部网络请求（如 \<img\>, \<script\> 或 fetch）前，严格比对 URL 是否在 default\-src / connect\-src 白名单内，违规直接在网络层抛出 \(blocked:csp\)。

- **执行通道拦截**：默认关闭 unsafe\-inline 和 unsafe\-eval，强行阻断任何嵌在 HTML 中的内联脚本或事件，以及 eval\(\) 动态求值操作。

- **异常遥测**：利用 report\-uri 建立独立监控流，违规行为被阻断时，浏览器网络模块会自动向安全网关 POST JSON 格式的报警数据，实现 0 业务阻塞的攻击捕获。

### CSRF

#### SameSite 限制同站 Cookie携带

服务端在 Set\-Cookie 中声明 SameSite=Lax 或 Strict。浏览器网络模块在构造 HTTP Request 时，强制核对“当前页面 URL”与“目标请求 URL”的 eTLD\+1。若判定为跨站上下文（且结合公共后缀列表 PSL 排除伪同站），则在报文发出前直接剥离该 Cookie 字段。

#### CSRF Token

**下发与隔离存储**：服务端生成高强度随机 Token，以以下三种方式发送给客户端并存储：

- 通过 API 返回

    - 存储：通过js存在LocalStorage 中；

- 内嵌于 HTML `<meta>` 标签中

    - 存储：dom树解析完之后，自动存储在js内存中

- 服务端在鉴权通过后，通过 HTTP 响应头额外下发一个 Cookie： `Set-Cookie: csrf_token=...;`

    - 存储：在通过domain校验即同源条件下，通过js读取cookie

**显式携带与后置校验**：前端在发起敏感请求（POST/PUT/DELETE）时，用 JS 读取该 Token，并显式写入自定义 HTTP 请求头（如 `X-CSRF-Token`）。服务端强制校验该 Header，缺失或不匹配则直接拒绝（403）。

**防御的绝对基石（同源策略 SOP）**：该方案能生效的底层物理墙是浏览器的同源策略。SOP 严格限制了跨站的“读”权限，意味着黑客在恶意站点的 JS 代码，绝对无法跨域读取合法站点的 DOM 树或 LocalStorage 数据，或cookie数据。

因此，黑客纵使能诱导浏览器“暗中发送”携带 Cookie 的伪造请求（跨域写/发），也会因为被 SOP 蒙住双眼“读不到” Token，从而无法伪造出合法的自定义请求头，最终被服务端精准拦截。

#### 针对同源绝对隔离的协议级授权握手 \(CORS 机制\)

CORS \(Cross\-Origin Resource Sharing\) 的本质，是利用 HTTP Header 在浏览器网络栈与目标服务器之间建立的一套状态机握手协议。

##### 针对标准网络行为的“后置授权” \(简单请求\)

- **触发条件**：当请求不会对服务器数据产生非预期副作用时（仅限 GET/HEAD/POST，且 HTTP Header 仅限基础字段如 Accept、Content\-Language 等纯文本表单标准类型）。

- **流转逻辑**：

    1. 浏览器网络模块不加拦截，直接发出真实 HTTP 报文，并在底层的 Request Header 中强制打上来源标记：Origin: [https://www\.a\.com](https://www.a.com/)（该字段 JS 无法篡改）。

    2. 服务器处理请求并返回数据，但在 Response Header 中附带授权印章：Access\-Control\-Allow\-Origin: [https://www\.a\.com](https://www.a.com/)（或 \*）。

    3. 浏览器网络栈收到报文后进行匹配裁决。若 Origin 未包含在允许名单中，网络栈直接抛弃响应体并抛出 CORS Error；若匹配，则放行数据进入 JS 内存。

##### 针对高危操作的“前置探路协议” \(预检请求 Preflight\)

- **触发条件**：当请求属于非简单请求时（如携带了自定义头部 Authorization，或使用了 application/json 数据格式，或使用了 PUT/DELETE 方法），这种请求可能会在校验之前就对服务器数据造成破坏。

- **流转逻辑**：

    1. 浏览器网络模块挂起（Suspend）真实的业务请求报文。

    2. 网络模块自动封装并隐式发散一个 Method: OPTIONS 的探路报文。包含两个关键侦测头：

        - Access\-Control\-Request\-Method: PUT \(问：允许用这个方法吗？\)

        - Access\-Control\-Request\-Headers: Authorization \(问：允许带这个自定义头吗？\)

    3. 服务器校验后，返回允许的清单（Access\-Control\-Allow\-Methods / Access\-Control\-Allow\-Headers）。

    4. 浏览器网络栈核对这份“通行证”，如果权限吻合，才真正将挂起的业务请求发往服务器；若不吻合，直接短路报错。

##### 针对握手时延的网络降维优化 \(预检缓存\)

- **消除 2 RTT 损耗**：预检机制（OPTIONS）会导致一次普通的 API 调用产生两次网络往返时延（2 RTT），在弱网环境下首屏性能急剧恶化。

- **流转逻辑**：服务器在响应 OPTIONS 预检报文时，下发 Access\-Control\-Max\-Age: 86400。浏览器据此在网络协议栈的内存中开辟一块预检缓存区。在 86400 秒内，针对同一 URL 的复杂请求，浏览器将直接提取缓存中的通行证，跳过 OPTIONS 探路，将通信成本硬性降维回 1 RTT。

#### HTTPS TLS加密 \+ 服务端验证origin和referer

现代架构全量部署 HTTPS，加密层（TLS）保证了 HTTP Header 绝对无法被中间节点抹除或篡改。Nginx 等 API 网关直接强校验网络模块强制附带且 JS 无法伪造的 Origin 或 Referer 头，拦截非白名单流量。

### 身份鉴权架构选型与安全方案实现

#### 1\. 传统有状态模式 \(Session \+ Cookie\)

##### 实现：

- 用户登录成功后，服务器会在自己的内存或数据库（如 Redis）中创建一条该用户的会话记录（Session），并生成一个唯一的 Session ID。

- 服务器通过 HTTP 响应头 Set\-Cookie: sessionId=xxx; HttpOnly 将这个 ID 发送给浏览器。

- 浏览器后续发送的每一个 HTTP 请求，都会自动在请求头中带上 Cookie: sessionId=xxx。

##### 安全影响：

- **防止 XSS 窃取**：因为设置了 HttpOnly 属性，前端的 JavaScript 代码无法通过 document\.cookie 读取到这个值。即使页面被注入了恶意脚本，也偷不走凭证。

- **容易遭受 CSRF 攻击**：因为浏览器会在所有请求中自动带上目标域名的 Cookie，即使用户是在黑客的网站上被诱导点击了按钮，请求也会带上有效凭证。**需要使用CSRF防御手段中的任意一种。**

- **性能瓶颈**：服务器必须保存所有在线用户的状态表。当系统用户量增大，需要增加多台服务器时，在这些服务器之间同步会话数据非常耗费资源，限制了系统处理高并发请求的能力。

    - **问题解决思路**：

        - 分析：

            交付给客户端的数据\(sessionId\)包含了“xx用户已经完成并且之后都跳过身份鉴权”信息，并且由于是鉴权信息还有保密的作用。

            因此具有特点：

            1. **与用户id存在转换逻辑，该转换逻辑代表“xx用户已经完成并且之后都跳过身份鉴权”信息；**

            2. **这种转换逻辑无法被破解伪造**。

            因此鉴权逻辑链路：token存在该转换逻辑——\>token存在“xx用户已经完成并且之后都跳过身份鉴权”信息信息——\>token合法。而“验证”转换逻辑的过程就是在证明第一步，从而证明token代表该信息。

        - 替代：具备这两个特点的，并且不在服务端存储已登录状态数据，不在服务端进行每次请求的检索验证逻辑。可以用数字签名进行替代。

#### 2\. 无状态鉴权模式 \(JWT \+ localStorage/cookie\)

##### 实现：

- 用户登录成功后，服务器生成一个 JWT（JSON Web Token）。这本质上是一串字符串，内部包含了用户 ID 等信息，并且附带了服务器使用私钥生成的“数字签名”。

1. localStorage

    - 服务器将这个字符串放在 HTTP 响应体（JSON 数据）中返回给前端。

    - 前端 JavaScript 接收到 JWT 后，将其保存在浏览器的 localStorage 中。

    - 前端在发起后续的业务请求时，必须通过 JavaScript 代码手动读取 localStorage 中的内容，并将其强制写入 HTTP 请求头中，协议格式通常为：Authorization: Bearer \<token\>。

2. cookie

    - 服务器通过 HTTP 响应头将这个字符串写入 Cookie 中，并严格设置安全属性：`Set-Cookie: token=<jwt>; HttpOnly; Secure; SameSite=Lax`

    - 浏览器后续向 服务器 发起请求时，会自动带上这个 Cookie。

##### “无状态”与高并发的原理：

所谓“无状态校验”，是指服务器不需要在数据库或 Redis 中保存用户的登录状态。当收到包含 JWT 的请求头时：

1. 服务器只需用自己的密钥进行数学计算，验证 JWT 尾部的“数字签名”是否正确。

2. 如果签名正确，说明该 Token 确实是自己签发的且未被篡改，说明登录状态有效。

3. 直接从中读取用户 ID 即可放行。

这省去了查询数据库的步骤，极大地提升了服务器处理高并发请求的能力。

##### 安全影响：

- localstorage

    - **防止 CSRF 攻击**：浏览器的底层网络模块不会自动发送 localStorage 中的数据，也不会自动添加 Authorization 请求头。黑客网站发起的跨站请求无法附带这个凭证，因此天然防止了 CSRF 攻击。

    - **极易被 XSS 窃取**：localStorage 没有任何类似 HttpOnly 的禁止读取保护。一旦页面存在 XSS 漏洞，黑客的恶意脚本只需执行 localStorage\.getItem\('token'\)，就能将用户的 JWT 完整偷走并发给黑客。**需要使用XSS防御手段中的任意一种。**

- Cookie

    - 设置了`HttpOnly` 和`SameSite=Lax` 就完成了xss和csrf的攻击防御了

#### 3\. 混合代理模式 \(BFF 层代理 \+ JWT 存入 Cookie\)

在2的基础上，将后端拆分成鉴权 \+ 微服务的架构

##### 实现：

- 架构中引入一个 BFF（Backend For Frontend，前端专用代理服务器，通常用 Node\.js 编写）。

- 前端将账号密码发给 BFF，BFF 转发给真正的后端验证服务。验证成功后，后端生成 JWT 返回给 BFF。

- **关键步骤**：BFF 拿到 JWT 后，不将其放在响应体中返回给前端 JS，而是通过 HTTP 响应头将其写入 Cookie 中，并严格设置安全属性：

- `Set-Cookie: token=<jwt>; HttpOnly; Secure; SameSite=Lax`

- 浏览器后续向 BFF 发起请求时，会自动带上这个 Cookie。

- BFF 收到请求后，从 Cookie 中提取出 JWT，执行“无状态的签名验证”。验证通过后，将解析出的用户信息转发给内部的各个微服务。

##### 安全与性能的完美平衡：

- **防止 XSS 窃取**：因为 JWT 被存入了带有 HttpOnly 标记的 Cookie 中，前端 JavaScript 代码无权读取它，黑客的脚本无法偷走 Token。

- **防止 CSRF 攻击**：因为使用了 Cookie，浏览器又会自动携带凭证了。为了防止 CSRF，我们通过设置 SameSite=Lax 限制凭证在跨站环境下的发送，同时在 BFF 层强制校验 HTTP 请求头中的 Origin 或 Referer 字段，确保请求只来源于受信任的前端域名。

- **保持高并发扩展性**：BFF 层对 JWT 的校验依然是基于数字签名算法，不需要查询数据库，保留了无状态模式的性能优势。
