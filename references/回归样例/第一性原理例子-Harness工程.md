# Harness工程

# Agent Harness 工程架构

## 一、 最终的目的

实现 AI 智能体应用（Agent \+ LLM）能够半自动乃至全自动地完成一个复杂大型软件项目的开发。

*\(核心指标：① 具备真实开发能力即代码落库；② 流程能自动化流转且符合人类预期。\)*

## 二、 当前的信息/现状 与 要解决的问题

单纯依赖现有的原生 LLM，存在以下不可逾越的物理与现实限制，这些限制直接推导出了我们需要解决的核心问题：

- **限制 1：全局上下文容量受限**

    - **现状：** 随着单次输入 Token 的增加，模型的注意力会不可避免地涣散，幻觉率陡增。

    - **推导说明：** 由多个子任务组成的复杂长程任务，绝对无法在单次对话或单一上下文中完成。

    - **要解决的问题总结：** 

        - 必须将宏大目标**拆分成多任务**

        - 并实现**跨对话**的任务流转机制。

- **限制 2：单次输出的长度与算力受限**

    - **现状：** 强行要求长篇输出会加剧逻辑发散与中断。

    - **推导说明：** 单个任务的极限代码量与逻辑复杂度受到了严格的物理天花板限制。

    - **要解决的问题总结：** 

        - 单个任务的复杂度有限，需要**降低单个任务的复杂度**。

- **限制 3：算力昂贵与经济性瓶颈**

    - **现状：** 现阶段顶级推理模型成本高昂，不同类型的任务（如简单路由与复杂编码）对于不同的模型有不同的性价比。

    - **要解决的问题总结：**

        - 系统需要能够灵活**切换模型**。

        - 必须尽可能地降低任务成本：

            - 通过提高任务输入的**信噪比**

            - 降低单个任务复杂度，来**提高任务的成功率**（减少反复报错重试带来的算力浪费）。

- **限制 4：安全性与容错率边界**

    - **现状：** 即使能解决以上问题，大模型的幻觉率依然不等于 0，AI 输出的任务结果可能会存在各种逻辑漏洞或破坏性行为。

    - **要解决的问题总结：** 

        - 需要可以提供**人力校验**的介入卡点

        - **AI 权限范围**的设置能力。

## 三、采取的方案

### 一、方案思路（核心破局点）

首先，必须为 LLM 解决物理操作的问题，提供操作计算机（即读/写）的能力。在此基础上，由于核心痛点在于如何实现“自动 \+ 有效/符合预期”，所需的应对措施呈现高度的系统性。因此，我们将所有零散的对策融合为一个整体架构方案：

👉 构建一个“单次执行复杂度有限的小任务 \+ 自动流转状态”的全局状态机。

这里需要先划清一个工程边界：Harness 工程不能把所有配置都当成“硬约束”。真实可落地的 Agent Harness 应该拆成两类机制：

1. **Agent / Harness 内部实现的硬机制**：由客户端、引擎、工具层、沙盒、状态修改器、检索器、上下文装配器、Hook、Exit Code、文件权限、配置解析器执行。它们的特点是：发生在模型生成前、工具调用时或状态流转时，不依赖模型自觉遵守。只要实现了底层拦截，就能形成确定性边界。

2. **通过提示词和语义索引实现的软约束**：包括 `AGENTS.md`、workflow skills、角色说明、治理提示词、`docs/INDEX.md`、policies、PRD、技术方案、memory、plan 等由模型阅读、理解和执行的文本。它们可以显著提高模型注意力集中程度和行为稳定性，但不能单独等同于安全边界。只要没有工具校验、文件权限、Hook 或 Exit Code 兜底，它们就仍然是软约束。

因此，Harness 的真实设计目标不是“写一套更长的提示词”，而是：用硬机制兜住不可越界的底线，用软约束提高模型在当前任务中的语义命中率，再用状态机把多个小任务串成一个长程自动化流程。

具体在状态机的各个生命周期阶段，我们的设计逻辑如下：

- 遍布于多个阶段：

    - 每一次发送给 LLM 提示词时：

        - 设计短期记忆与上下文压缩器：设定一个 LLM 上下文额度，当本次发送给 LLM 的提示词触及或超过额度时，不再只把过往对话压成一段不可逆摘要，而是优先把高体积、低密度的工具调用结果卸载到外部原文文件中，并在上下文中只保留可索引的轻量摘要、节点编号与任务地图。这样既降低了上下文体积，又保留了向下钻取原始证据的路径。虽然可以切换上下文，但是切换上下文的时机无法准确把握，这是提高了任务执行成功率，变相降低了任务复杂度，降低了算力成本。

        - 硬软边界：如果压缩、offload、摘要装配由 Harness 上下文装配器自动执行，这是硬机制；如果只是提示模型“请自己压缩上下文”，那只是软约束。

    - 每一次检索/读取工作空间的文件时：工作空间文件读取与检索机制。

        - 硬软边界：如果由引擎控制 ignore、文件树快照、确定性路径直读、AST 检索、grep、RAG、截断和行号装配，这是硬机制；如果只是让模型读 `docs/INDEX.md` 后自行决定路径，这是软索引。

a\. 提出任务描述阶段

- 设计 Skills 模块（收集不同任务的优秀实践 SOP），结合过往总结的解决方案（RAG 向量检索），减少 LLM 需要自行思考推演的内容，进而降低了算力成本。

- 这里的 Skills 应改为 workflow skills，而不是普通散落提示词。它可以有两种入口：

    - Native skill 入口：如果 Agent 客户端原生支持扫描并注册某类 `SKILL.md` 目录，用户说“产品经理 / 产品方案 / 写 PRD”时，客户端可以在模型回答前枚举、匹配并水合命中的 Skill。

    - Harness 阶段索引入口：即使 native skill 没命中，Agent 也可以根据 `lifecycle.yaml` 的当前阶段、`phase_contracts.yaml` 的 `active_skill`，或 `AGENTS.md` 中的路由规则，读取项目内的 workflow skill。

- 以 Codex 为例，Skill 是带 `SKILL.md` 的目录，Codex 会先把 skill 的 name、description、path 放入可用技能列表，只有命中后才读取完整 `SKILL.md`；这是一种典型的 progressive disclosure 机制。当前官方文档中的仓库级目录是 `.agents/skills`，用户级目录是 `$HOME/.agents/skills`，管理员级目录是 `/etc/codex/skills`。因此，项目内自定义的 `.agent/skills/**/SKILL.md` 或 `.harness/skills/**/SKILL.md` 可以作为 Harness 的事实源，但只有被同步、链接或适配到 Codex 当前可扫描的 native skill root 后，才属于 Codex native skill。

- 读取 `.cursorignore` / `.gitignore` / Harness ignore 规则进行文件屏蔽，有效降低了任务复杂度，进而降低了算力成本。

b\. 写规划阶段

- 设计 Memory 模块和 Plan 模块，分别记录长程任务中的系统级关键信息和当前阶段的任务拆解信息。Memory 模块不再只是单个 Memory\.md 或普通向量库，而是拆成长期记忆、短期任务记忆、计划状态三类介质：长期记忆负责跨对话、跨模型的稳定知识沉淀；短期任务记忆负责把单次任务中的工具日志和执行轨迹压缩成可恢复的任务地图；Plan 负责当前任务的游标推进。实现了任务状态的存储，实现了跨对话、跨模型。

- 硬软边界：Memory 和 Plan 的“文本内容”本身属于软事实源，模型需要读懂后执行；但如果 Harness 提供 `update_plan()`、`commit_memory()`、`offload_tool_result()` 这类状态修改器，并在工具层绑定读写权限，则这些读写边界属于硬机制。

- `plan.yaml` / `PLAN.md` 比普通软索引更强，因为它承载当前任务执行合同：当前 task、允许修改路径、必要 gate、验收标准、实现文档位置。它的约束力来自后续 allowed\_paths 校验、Hook、Exit Code 和审批，而不是来自文本本身。

c\. 行动执行阶段

- 设计 MCP 模块与沙盒模块，为 LLM 提供了真实的读/写操作能力。

- 设计 ReAct（行动\-观察\-修正，直至输出符合要求）流程循环。ReAct 流程天然地将任务进一步拆碎，再次降低了单个任务的复杂度。

- 沙盒模块可以设置底层执行权限，保证了系统的安全边界。

- 硬软边界：MCP 连接白名单、命令白名单、文件读写范围、超时、网络访问、审批策略属于硬机制；“请不要运行危险命令”属于软约束。

d\. 检验卡点阶段

- 设计 Governance 模块，设立状态流转的拦截钩子（Hooks）。将固定环节需要做的固定事情抽出来，降低了单个任务的复杂度。

- 在此处还可以设置人力校验（Approval）的能力，守住最终安全底线。

- 硬软边界：Hook、lint、test、typecheck、build、allowed\_paths、Exit Code、人工审批属于硬机制；代码风格说明、review checklist、防御性编码提示属于软约束。软约束可以提高模型一次性通过率，但最终流转必须由硬 gate 裁决。

e\. 总结复盘阶段

- 任务完结后，进行当前任务的经验总结，并向量化存储到数据库中。形成闭环飞轮。这些沉淀的经验，将精确对应到“阶段 1（提出任务描述阶段）”中的“过往总结的解决方案”模块，供未来的任务复用。

- 硬软边界：经验提取、向量化、写入记忆库、元数据绑定可以由后台任务硬执行；经验是否在后续任务中被模型正确理解和使用，仍然属于软召回效果，需要通过命名空间过滤、BM25 / FTS、向量召回、RRF 融合、路径直读和证据引用提高稳定性。

### 二、四大模块（按硬机制 / 软约束重组）

在模型基座之上，引入外部系统架构（即 Harness 工程），通过实体化、工程化的配置文件驱动引擎，赋能上述能力。

这里不再只按“文件夹名字”理解模块，而是按约束强度理解模块。四大模块仍然对应原来的四类问题：

- Action 层解决“能动手”和“权限边界”。

- Memory 层解决“能记住”和“状态持久化”。

- Context 层解决“能聚焦”和“上下文信噪比”。

- Governance 层解决“能受控”和“状态流转安全”。

#### A\. 硬机制层：Agent / Harness 内部实现的确定性机制

#### B\. 软约束层：提示词、语义索引与模型注意力约束

### 模块一：Action 层（执行能力层）

核心目标：让智能体“能动手”，安全触达物理/数字世界。提供标准化插座，只管“安全连通”，不管“为何连”。

Action 层必须优先归入硬机制层。原因是它控制的是模型能否触达外部系统、能否写文件、能否执行命令、能否访问网络、能否调用 MCP Server。只要这部分只写成提示词，就无法阻止模型误调用或越权调用；只有放到工具层、沙盒层、MCP 层、审批层，才具备确定性拦截能力。

\(注：带有 `.py` 的工具脚本为引擎内部核心组件，故保留具体文件名；用户自定义配置统称为 `xxx`。\)

### 模块二：Memory 层（记忆与计划层）

核心目标：让智能体“能记住”。实现跨对话、跨模型的状态持久化与注意力收束。通过解耦长期团队知识库、短期任务证据链与单次任务草稿纸，强迫模型在单次工作流中仅专注于当前的一个任务，防止长程任务目标发散。

Memory 层必须拆开看：记忆的存储、权限、索引、召回、写入工具是硬机制；记忆文本本身是软事实源。模型读到“项目使用四空格缩进”并不等于底层会强制格式化为四空格，除非后面有 formatter、lint、review gate 或 diff 检查兜底。

#### Harness 引擎对 Memory 和 Plan 的读写逻辑

核心机制：通过极度森严的权限隔离、分层存储与生命周期事件，确保大模型在执行高熵任务时，无法破坏系统级的长程状态，同时又能在需要时回溯原始证据。

- **机制 A：拓扑状态分层（Topological State Tiering）**

    - 机制描述：引擎在配置层建立抽象状态的拓扑树，将状态介质划分为“长期记忆 Long\-Term Memory”“短期任务记忆 Short\-Term Working Memory”和“计划状态 Plan State”。长期记忆继续细分为 L0 原始记录、L1 原子事实、L2 场景块、L3 项目基线；短期任务记忆保存工具输出原文、offload 索引和 Mermaid 任务地图；计划状态继续区分“全局宏观状态（Macro\-State）”和“局部微观状态（Micro\-State）”，并在底层物理隔绝两者的作用域。

    - 具象示例：在标准理论工程中，引擎将用于沉淀系统核心架构与全生命周期里程碑的 Memory\.md 定义为 Macro\-State（内核态）；将用于记录当前“正在排查哪个报错、分几步走”的临时拆解文件 Plan\.md 定义为 Micro\-State（用户态）；将一次 grep 的完整输出写入 refs/*\.md，仅把“检查了哪些文件、哪个节点异常”放入 mmds/*\.mmd。三者在安全级别、生命周期和注入方式上不同，不应该混成一个大文件。

- **机制 B：源 ID 与可回溯链路（Traceable Memory Chain）**

    - 机制描述：任何被抽象出来的记忆都必须保留向下钻取路径。L1 原子事实保存 source\_message\_ids；L2 场景块保存关联 L1 或原始消息引用；L3 项目基线保存 Scene Navigation 或索引入口；短期 Mermaid 节点保存 node\_id、tool\_call\_id 和 result\_ref。这样做不是为了让上下文无限膨胀，而是为了让摘要变成“索引”，而不是不可逆压缩。

    - 具象示例：如果 L3 中写入“项目统一使用四空格缩进”，Agent 后续可以从 L3 下钻到 L2 的“编码规范场景块”，再追溯到 L1 中的 instruction 类型事实，最后定位到原始用户消息 ID。这样当用户纠正“这个项目其实用两空格”时，引擎可以更新具体事实，而不是让新旧偏好在向量库里同时漂移。

- **机制 C：基于工具的权限绑定（Tool\-State Binding）**

    - 机制描述：引擎剥夺大模型对底层文件系统的原生读写 API（如原生 open\(\) 或 write\(\)），转而向其暴露高度封装的“状态修改器（Mutator Tools）”。引擎在路由注册表中，将特定 Mutator 与特定的拓扑状态介质进行强绑定，实现基于工具的物理越权拦截。

    - 具象示例：引擎向 Agent 提供 update\_plan\(\)、commit\_memory\(\)、capture\_memory\_atom\(\)、offload\_tool\_result\(\)、recall\_memory\(\) 等工具。在引擎底层源码中，update\_plan 的 I/O 指针被绑定为仅能覆写 Plan\.md，而 commit\_memory 被绑定为仅能向 Memory\.md 写入。如果 Agent 试图调用 update\_plan 并传入 Memory\.md 的内容，引擎会在 API 调用层直接抛出 Unauthorized Access 异常。

- **机制 D：高频迭代与短期 Offload（Micro\-State Mutation \& Context Offload）**

    - 机制描述：在 ReAct 执行闭环中，大模型被授予了对“微观状态修改器”和“短期任务记忆写入器”的高频调用权限。大模型基于维持自身上下文信噪比的内生需求，主动发起对微观状态的“覆写（Overwrite）”动作，并把大型工具结果卸载到 refs/\*\.md，只在上下文中保留 offload 索引和 Mermaid 任务地图，实现执行层的可恢复降维。

    - 具象示例：Agent 在执行复杂的逻辑调试时，每完成一个子步骤，就会主动调用一次 update\_plan\(\) 工具。它会将 10 分钟前已经失效的报错堆栈和废弃思路从 Plan\.md 中擦除，只保留“下一步准备检查的网络请求拦截器”。如果刚刚 grep 出 500 行命中结果，引擎不会把 500 行全部保留在上下文里，而是写入 refs/grep\_xxx\.md，并在 MMD 图中保留 N7\[grep 网络请求拦截器\] \-\-\> N8\{命中异常分支?\} 这类节点。模型需要细节时，再凭 node\_id 或 result\_ref 回读原文。

- **机制 E：事件驱动的低频跃迁（Macro\-State Mutation via Hooks）**

    - 机制描述：“宏观状态”在默认执行域中处于只读锁死状态。当且仅当系统进入特定的治理阶段，且底层的物理校验载荷（Payload）返回成功标志时，引擎将触发生命周期钩子（Lifecycle Hook）。该钩子通过临时鉴权（Temporary Entitlement）的方式，允许对宏观状态进行增量追加或状态变更，宣告一次长程状态机的物理跃迁。

    - 具象示例：平时 Agent 疯狂写代码时，Memory\.md 是绝对只读的。当且仅当进入治理阶段（如调用验收技能），且底层的沙盒测试脚本返回了 Exit Code 0（校验完美通过）时，引擎底层会触发 on\_validation\_success 事件钩子。这个事件瞬间激活了 commit\_memory\(\) 工具的写入权限，Agent 借此将刚刚跑通的架构经验作为“新能力”刻入 Memory\.md 账本中。操作一结束，事件销毁，Memory\.md 再次物理锁死。

- **机制 F：混合检索与降级链（Hybrid Recall \& Fallback）**

    - 机制描述：长期记忆召回不能只依赖向量相似度。工程上更稳妥的做法是先按命名空间、项目、角色、时间范围、优先级做硬过滤，再并行执行 BM25 / FTS 与向量召回，最后用 RRF 这类排序融合算法合并候选。向量服务不可用时降级到 BM25；全文索引不可用时降级到文件路径与元数据直读；所有降级都不应该阻断主任务执行。

    - 具象示例：用户说“继续上次那个订单网关的幂等问题”。引擎先按当前项目 namespace 过滤，再通过关键词“订单 / 网关 / 幂等”和 embedding 召回相关 L1/L2 记忆。如果向量库未完成索引，至少仍可通过 FTS 命中“订单网关幂等”场景块，避免 Agent 因为 embedding 不可用而完全失忆。

### 模块三：Context 层（上下文工程层）

核心目标：让智能体“能聚焦”，动态构建高效上下文。管理结构化指令、技能、文件索引、检索结果与上下文压缩，避免全量加载导致的 Token 溢出与幻觉。

Context 层是硬机制和软约束交界最复杂的一层。它既包含 native skill registry、文件检索、上下文装配器、RAG、压缩器这类硬机制，也包含 `AGENTS.md`、Skill 正文、文档索引、角色说明、治理提示词这类软约束。

#### Native Skill 与 Workflow Skill 的双通道设计

为了兼顾 Codex 这类客户端的 native skill 能力和跨 Agent 的项目自包含能力，Harness 的 Skill 设计应该采用“双通道”：

- **项目内事实源**：`.agent/skills/**/SKILL.md` 或 `.harness/skills/**/SKILL.md`

    - 这是 Harness workflow skill 的源目录。

    - 它不假设任何客户端都会自动扫描。

    - 它通过 `AGENTS.md`、`lifecycle.yaml`、`phase_contracts.yaml` 进行软索引。

    - 它适合作为 npm 包、模板工程、团队工程规范的一部分发到仓库里。

- **客户端 native projection**：`.agents/skills/**/SKILL.md`

    - 这是面向 Codex 当前设计的 native skill 目录。

    - 如果希望用户说“产品方案”时 Codex 首轮就能在可用技能列表中看到这个 Skill，需要把 Harness workflow skill 同步、复制或软链接到 Codex 可扫描的 native root。

    - 这个过程可以由 `sdlc-harness codex install-skills` 之类的 adapter 命令完成。

- **软索引兜底**：`AGENTS.md`

    - `AGENTS.md` 可以写：“本项目的 workflow skills 在 `.agent/skills/**`，执行前先读 `lifecycle.yaml`，再按 `active_skill` 读取对应 `SKILL.md`。”

    - 这能让模型在进入会话后按地图寻找技能。

    - 它不能让 `.agent/skills/**` 在启动前进入 Codex native skill registry。

#### 工作空间文件读取与检索机制

在 Harness 引擎中，Agent 对本地项目文件的读取绝非简单的“将文件内容一股脑塞给大模型”，而是由一套混合检索策略（Hybrid Retrieval Strategy）驱动的调度系统。其核心目的是在“全局信息饥渴”与“Token 物理上限”之间寻找最优解（即最大化信噪比）。

该机制的具体工程实现拆解如下：

一、视野边界与预处理（Vision Filtering \& Pre\-indexing）

在 Agent 真正开始读取之前，Harness 引擎首先会在物理层面对工作空间进行“降噪处理”。

1. 物理屏蔽名单（ignore 拦截）：引擎底层的拦截器会静默过滤掉如 `node_modules`、`.git`、`dist/` 等非人类编写或高度冗余的目录。从物理源头切断 Agent 检索到这些无效目录的可能，节省算力与索引时间。

2. 轻量级文件树快照（File Tree Snapshot）：每次任务开始时（水合阶段），引擎会自动扫描项目根目录，生成一份极简格式的 Tree 目录树（仅包含文件名和层级）。这份目录树会被作为“全局拓扑图”隐式注入 System Prompt，让 Agent 在脑海中建立对工程宏观结构的感知。

二、5 级混合检索机制（The 5\-Tier Hybrid Retrieval）

在 Harness 引擎中，Agent 对本地工作区的读取绝非简单的“全文塞入”或“无脑查库”。为了在“模糊的人类指令”与“精确的代码物理路径”之间建立桥梁，引擎采用了一套基于“执行成本优先与确定度降级”的动态路由策略。Agent 会遵循“先推理后动手、先精准后模糊”的原则，在以下 5 级机制中逐级降级兜底：

【极高确定度：精准直达】

- 第 1 级：确定性路径直读（Deterministic File Fetching）——精准狙击

    - 触发场景：Agent 明确掌握了目标文件的绝对或相对路径（例如通过阅读 INDEX\.md 知道了具体的 SOP 路径，或在报错日志中看到了准确的报错文件 `src/utils/math.js`）。

    - 行为表现：它会通过 Action 层的沙盒工具（如 read\_file\(path\)）发起点对点直读。

    - 特点：准确率最高，无检索损耗，是所有高级检索的最终落脚点。

- 第 2 级：结构化符号检索（Symbolic \& AST Retrieval）——代码级感知

    - 触发场景：Agent 明确掌握了具体的类名、函数名等代码符号，只需提取其具体实现。

    - 行为表现：引擎内置基于 AST 的解析器。Agent 不会去通读 2000 行的代码文件，而是向引擎下发指令精确提取特定方法的定义与类型签名，极大压缩 Token 消耗。

【中等确定度：推理与探查】

- 第 3 级：语义导航（Semantic Routing）——基于目录树和索引找路

    - 触发场景：用户使用了非标准的业务俗语（如“去看看清洗模块”），缺乏精确的代码路径，但在大局观上有迹可循。

    - 行为表现：在调用重度搜索工具前，大模型会优先基于自身加载的“轻量级全局目录树快照”和 `.docs/INDEX.md` 进行逻辑推演。它能凭借代码常识，将“清洗”与目录树上的 `src/data_init/` 建立关系，随后跃迁回第 1 级进行直读。

    - 特点：零额外工具调用开销，但属于软推理，必须允许后续用 grep / AST 校正。

- 第 4 级：主动式全局探查（Active Probing）——基于关键词和报错特征扫描

    - 触发场景：纯推理无法锁定路径，但 Agent 提取到了极其冷门的“精准特征词或报错变量”。

    - 行为表现：引擎赋予 Agent 类似 grep 的全局文本扫描权限，直接去文件正文中寻址。

    - 多目标兜底机制：为防止命中结果过多撑爆上下文，引擎底层强制执行切片预览。例如通过 `grep -n -C 2` 仅返回命中关键词及上下 2 行代码。若结果仍上百条，引擎会强制截断输出，并反向提示模型：“结果过多，请追加关键词缩小范围”。Agent 则通过返回的少量切片，凭借逻辑二次过滤掉无关文件，锁定最终目标。

【极低确定度：模糊兜底】

- 第 5 级：语义化向量检索 / 混合召回（Semantic RAG / Hybrid Recall）——模糊寻址与终极兜底

    - 触发场景：信息极度匮乏，Agent 面对极其模糊的自然语言意图（例如：“全局错误码是怎么定义的？”），无法通过常识脑补，且无特征词可供 grep 时的终极方案。

    - 行为表现：引擎将意图转化为高维向量，去底层的本地向量缓存库中进行相似度匹配，捞取相关的文档块（Chunk）并返回。更稳妥的实现是并行执行 BM25 / FTS 与向量召回，再用 RRF 进行融合排序。算力成本最高，但覆盖面最广。

    - 降级策略：如果 Embedding 配置缺失或向量服务不可用，引擎不应阻断主流程，而是降级到纯 BM25 / FTS、grep 或确定性路径直读。

三、底层基座：向量缓存库的结构与生命周期（Vector Cache Infrastructure）

上述“语义化向量检索”之所以能够快速响应，依赖于 Harness 引擎在后台静默维护的一个微型向量数据库。该缓存库的运作机制如下：

1. 物理数据结构（Data Structure）

缓存库中的每一条记录（Row）是一个严密的结构体，包含四个核心要素：

- 原始文本块（Raw Chunk）：引擎对项目大文件切片后得到的真实代码片段或 Markdown 段落。

- 高维向量（Embedding Vector）：将原始文本块经过 Embedding 模型转化后的一串浮点数数组。

- 全文索引字段（FTS / BM25 Field）：面向关键词检索的分词字段，用于补足纯向量召回对精确标识符、错误码、函数名不敏感的问题。

- 元数据（Metadata）：必须绑定的来源追踪信息，如所属文件路径、起始行号、代码类型、命名空间、更新时间等，确保 Agent 捞取信息后知道去哪里修改。

2. 缓存库的生命周期（Lifecycle）

- 冷启动建库期（Initial Indexing）：引擎首次在项目中初始化时，遍历有效工作区文件，进行全局切片、向量化并落盘存入本地库（如 ChromaDB 或 SQLite）。

- 热更新期（Incremental Sync / File Watcher）：引擎后台启动文件监听器。当开发者或 Agent 修改并保存了某个文件时，引擎捕获变更，仅针对该变动文件进行重新切片和向量化，覆盖旧记录。确保缓存库与当前代码库保持一致。

- 经验沉淀期（Memory Consolidation）：依托 Memory 层，当 Agent 完成一次复杂 Debug 或架构设计后，引擎会将“踩坑记录与解决方案”提炼、向量化，作为增量经验数据永久追加到缓存库中，实现智能体的越用越聪明。

四、动态拦截与行号装配（Dynamic Hydration \& Assembly）

当通过上述机制捞取到文件或代码块后，Harness 引擎中的上下文装配器（Context Assembler）会执行最后一道防线：

- 自适应截断（Adaptive Truncation）：如果 Agent 企图直读一个超大日志文件，装配器会强制拦截，并默认只返回头尾关键部分（如 head 和 tail \-n 500）。

- 行号映射（Line Numbering）：引擎在将所有进入『待编辑区（Editable Workspace）』的文本放入上下文之前，都会自动拼接行号。这使得 Agent 在后续需要修改这些内容时，能准确输出行号锚点，防止基于正则匹配修改代码引发的灾难性定位错误。

- 短期记忆装配（Short\-Term Memory Assembly）：对于已经被 offload 的工具结果，装配器只注入 Mermaid 任务地图、关键节点摘要与 result\_ref。只有当 Agent 明确需要证据细节时，才通过 node\_id / result\_ref 读取 refs/\*\.md 原文。

五、架构设计结论与最佳实践

基于上述底层机制，Harness 架构推导出的核心开发范式是：领域驱动的上下文隔离（Domain\-Driven Context）。

Agent 虽然拥有底层向量库带来的模糊检索能力，但这只是算力成本较高且容易引发逻辑断层的兜底方案。真正企业级的 Harness 工程，必须将需求文档和技术方案进行物理拆包（即按模块切分为独立的短文件，并在根目录提供强索引 INDEX\.md），迫使 Agent 尽可能采用“确定性路径直读”，从而将大模型的推理稳定性（信噪比）提升到极致。

### 模块四：Governance 层（工作流治理层）

核心目标：让智能体“能受控”，保障安全与合规。将人类工程经验转化为强制底线，阻断模型“自由发挥”。

Governance 层需要明确区分三类东西：

1. **硬 gate**：Exit Code、Hook、sandbox、allowed\_paths、审批、权限拦截、CI。

2. **机器可读 policy**：阶段契约、风险等级、路径边界、gate 定义。只有被引擎解析和执行时才是硬契约。

3. **模型可读 governance prompt**：防御性编码说明、审查 checklist、风险提示。它们是软约束，只能提高模型自我审查概率，不能代替测试和审批。

#### Policies 的定位

Policies 是机器可读的工作流规则，不是给用户看的说明文档。它们的作用是把工作流规则从长提示词里拆出来，变成可校验、可迁移、可同步的配置契约。

### 三、Harness 引擎

#### 架构局限性（必读）：

Harness 引擎能够通过沙箱隔离、状态机、工具权限、Hook、Exit Code、审批和状态修改器实现物理层面的绝对防线，但任何依赖 LLM 语义理解与自觉执行的交互环节，均受制于大模型的注意力衰减与原生推理本能（如 ReAct 暴走）。系统下发的自然语言指令对 LLM 而言永远是软约束，因此全自动工作流必须以强物理卡点和防守型熔断作为最终兜底。Harness 引擎会把信息发给 LLM，但是 LLM 有可能因为注意力问题导致交互环节中 Harness 侧预期做到的事情失败。随着模型能力提升，部分 Harness 机制会被模型原生能力覆盖或简化，但在可审计、可回滚、可控权限、可验收的工程场景中，硬 gate 仍然是安全边界。

#### 引擎启动时：注册表挂载解析。

核心机制：确立单次运行的 SSOT（唯一事实来源），解决引擎的寻址问题、Agent 的权限定界，以及路由缺失情况下的安全降级。系统代码与大模型认知之间的边界在此刻被明确划定。

##### 硬路由探针与启动锚点：

为了避免让大模型参与核心组件寻址而带来的延迟和幻觉风险，现代 Harness 引擎会在底层程序、插件、扩展或 CLI 启动脚本中硬编码特定探针。引擎启动时，强制按确定性顺序扫描当前工作区根目录、用户目录或系统目录下的配置锚点。例如 Codex 会读取 AGENTS\.md 作为项目指导，也会扫描规定的 skill root 以生成可用 Skill 列表。引擎的底层寻址权力必须收归宿主所有，大模型不参与这一层的路由推断。

##### Always\-on 指令注入：

AGENTS\.md 适合放置每次任务都应该知道的项目规则：仓库结构、构建命令、测试命令、提交规范、审查要求、目录级约束和完成定义。它的加载属于引擎 / 客户端行为，内容执行仍属于模型软约束。因此，AGENTS\.md 应保持短小、稳定、可维护，不应塞入长篇 SOP。长 SOP 应拆成 Skill、docs、policies 或 templates，再由索引规则按需读取。

##### Native Skill 注册与渐进披露：

Native Skill 的本质不是“一个普通提示词文件”，而是由客户端注册、枚举、匹配并按需读取的工作流能力包。Codex 当前设计中，一个 Skill 是包含 SKILL\.md 的目录，SKILL\.md 需要 name 和 description。客户端先把 name、description、path 放入初始可用技能列表，只有当用户显式调用或任务语义匹配 description 时，才读取完整 SKILL\.md。因此 native skill 的目录发现和 metadata 枚举属于硬机制，Skill 正文对模型的约束属于软约束。

##### Workflow Skill 软索引：

Harness 项目内的 \.agent/skills/**/SKILL\.md 或 \.harness/skills/**/SKILL\.md 应作为 workflow skill 的事实源。它可以被 lifecycle / phase\_contracts / AGENTS\.md 软索引读取，也可以通过 adapter 同步到 Codex native root。光在 AGENTS\.md 里写“skill 路径：\.agent/skills”不能让这些文件自动进入 Codex native skill registry；它只能告诉模型进入会话后按规则去读。

##### 动态路由表与 Bootloader 协议：

对于非硬编码的动态业务模块，引擎也可采用引导文件（Root Manifest）。该文件本身不直接承载全部业务逻辑，而是写入最小化的索引规则，例如：先读 lifecycle\.yaml，再按 current\_state 查 phase\_contracts\.yaml，再读取对应 workflow skill、docs、plan 和 gates。此时，充当“路由表解析器”的是大模型本身，所以这一路径属于软索引，需要后续硬 gate 兜底。

##### 双轨制结界生成：

无论是通过引擎硬编码探测还是大模型动态拉取，配置文件被读取后，都必须区分两条轨道：Track 1 是引擎可读区，必须是结构化 Schema，承载物理拦截、权限控制、路径绑定、Hook、Gate、状态机等硬机制；Track 2 是模型可读区，可以是自然语言 SOP、角色定义、治理提示和 checklist，承载软约束。只要涉及“物理拦截、权限控制、核心组件寻址、状态修改器绑定”，必须写入 Track 1。只要只是“希望模型这样做”，就属于 Track 2。

##### 路由缺失时的安全降级：

当引擎在启动阶段探测失败，无法寻址到核心路由锚点、Skill root、治理文件或状态机文件时，为防止大模型在缺乏物理红线与规范约束的情况下裸奔执行破坏性操作，引擎底层应强行阻断标准初始化水合流程，并进入三级降级防护：第一，物理权限熔断，默认进入沙盒白名单模式，仅保留只读能力；第二，兜底人设静默注入，告知模型当前处于受限安全模式；第三，引导式重启，只暴露初始化工作区的低风险工具，待基础路由闭环建立后再热重启解锁完整执行权限。

##### 总结：

经过上述机制，引擎的内存注册表中最终会固化以下维度的信息，确立单次任务的安全边界：

- 角色与权限注册表（Role \& Permission Route）：明确系统中有哪些 Agent 角色、每个角色具备哪些底层权限、这些角色描述来自客户端原生 role、profile、subagent，还是 Harness workflow role。

- Skill 注册表（Skill Registry）：明确哪些 Skill 是 native skill，哪些只是项目内 workflow skill；哪些可以被客户端首轮枚举，哪些需要通过生命周期状态机软索引。

- 全局与角色治理防线（Governance Route）：明确最高优先级的物理红线，以及特定角色不能逾越的专业边界。

- 状态机与寻址映射（State \& Memory Route）：明确业务的唯一事实来源路径及读写锁状态；同时明确长期记忆、短期任务记忆和 offload 文件的命名空间、生命周期和访问权限。

- Policies Route：明确 phase\_contracts\.yaml、gates\.yaml、allowed\_paths\.yaml、risk\_matrix\.yaml 等机器可读规则是否由引擎解析执行，还是仅作为模型可读说明。

- 外部工具与 Action 挂载（Tool / MCP Route）：明确允许拉起的子进程、外部 MCP Server、网络访问、文件写入范围和审批策略。

#### 单次任务生命周期剖析。

##### 遍布于多个阶段：

- 每一次发送给 LLM 提示词时：

    - 设计短期记忆与上下文压缩器：设定一个 LLM 上下文额度，当本次发送给 LLM 的提示词触及或超过额度时，对存储的过往对话进行压缩成摘要，并把大型工具结果卸载成 refs/\*\.md 原文文件，将 Mermaid 任务地图、节点编号和轻量摘要作为过往的执行轨迹拼进要发送的提示词中。虽然可以切换上下文，但是切换上下文的时机无法准确把握，这是提高了任务执行成功率，变相降低了任务复杂度，降低了算力成本。

- 每一次检索/读取工作空间的文件时：工作空间文件读取与检索机制。

##### 阶段 1：水合与预处理（Pre\-flight \& Context Hydration）。

核心机制：解决模型“盲目启动”的问题，在物理上隔离噪音，并将角色认知、业务技能、任务规范、动态记忆、工具声明与治理红线进行组装与注入。

###### 意图路由与 Skill 激活：

引擎拦截用户输入后，并非静态、盲目地加载全量配置。首先，引擎可以用轻量路由逻辑或路由模型对用户自然语言输入进行意图分析，并与挂载阶段已注册的 native skill 列表进行比对。匹配成功后，引擎提取对应 Skill metadata 和正文；如果 native skill 未命中，则进入 Harness workflow skill 软索引路径：读取 lifecycle\.yaml，确认当前阶段，再根据 phase\_contracts\.yaml 的 active\_skill 找到 \.agent/skills/\*\*/SKILL\.md。

###### 角色与身份上下文装配：

引擎根据当前 phase、role 或 subagent 配置，提取角色定义，确立“我是谁”。如果客户端原生支持 role/profile/subagent，这部分可以由客户端在模型生成前注入；如果只是 Harness 文件中写了 active\_role，则需要模型读取状态机后自行切换，属于软索引。对于你的工作流，role 本质上应定义为 workflow role：current\_phase \-\> active\_role / active\_skill \-\> 读取对应 skill，不要假设所有客户端都有原生 role 机制。

###### 记忆召回与向量检索：

切片、转化与打标、存储等重型操作通常在常态运行期的后台异步完成。本阶段实际触发的只有检索与捞出数据动作。引擎根据当前意图、项目命名空间、角色、实体标签、时间范围和记忆层级，去底层数据库进行硬过滤，再在过滤后的池子里并行执行关键词检索（BM25 / FTS）和向量检索，再通过 RRF 或等价排序策略融合候选结果。最终检索出历史经验文本及其绑定的完整元数据，交给引擎准备拼接。

###### 短期任务地图装配：

如果当前任务已经产生大量工具调用记录，引擎不会把所有 Observation 原文重新注入，而是读取 offload\.jsonl 和 mmds/\.mmd，提取当前任务 Mermaid 图中的关键节点、状态和边关系。大型工具结果仍保存在 refs/\.md 中，只在 Agent 明确要求“查看 N7 原始输出”时读取。

###### 治理层与红线约束读取：

引擎读取项目根目录的全局最高宪法，以及当前被激活角色的专属治理文件。在这里，治理规则应拆成两类：可被工具、Hook、sandbox、approval 执行的规则进入 Track 1；只能指导模型行为的规则进入 Track 2。对于模型可读 governance，尽量放在最终 System Prompt 的靠后位置，以提高近因权重，但不能把它当成安全边界。

###### 系统提示词的水合组装：

组装完成后的最终 System Prompt 应至少包含三类区域：顶部区域注入身份、Skill SOP、工具声明；中部区域注入当前环境、目录树、动态记忆、任务地图和 result\_ref；底部区域注入最高红线、治理提示和阶段完成定义。这个结构的目标不是让提示词更长，而是让模型在有限上下文内看到最相关、最可执行、最靠近当前任务的信息。

##### 阶段 2：规划生成与状态实例化。

核心机制：克服 LLM 无状态的缺陷，将发散的自然语言转化为可被物理追踪的工程进度条。

###### 计划创建：

引擎强制拦截模型急于写代码的冲动，要求其必须先调用 create\_plan 工具，输出结构化任务拆解。对于复杂项目，Plan 不应该只是自然语言 checklist，而应该包含 task\_id、目标、输入文档、允许修改路径、验收标准、必跑 gate、产出文档位置、下一阶段条件。

###### 模板实例化：

引擎遍历读取 templates/\.md 或 templates/\.yaml 模板目录，找到与当前任务匹配的格式定义，并按照模板约束在工程中物理生成实例化状态文件。从此开始，该文件成为本次任务的唯一真实状态源（SSOT）。模型可以读它、通过工具更新它，但不应该绕过工具任意改写全局记忆。

###### Policies 绑定：

计划生成后，引擎读取 phase\_contracts\.yaml、gates\.yaml、allowed\_paths\.yaml、risk\_matrix\.yaml，将当前任务绑定到明确的阶段契约、出口闸门、修改边界和风险等级。此处的 policies 如果由引擎解析，就具备硬约束意义；如果只是放进上下文让模型参考，则仍然只是软约束。

##### 阶段 3：执行与观察闭环（The ReAct Loop）。

核心机制：赋予“缸中之脑”安全、受控地触达数字世界的能力，并通过高频的状态新陈代谢和短期 offload 防止上下文崩溃。

###### ReAct 认知与执行流：

引擎强制大模型在单次任务流中遵循 Thought \-\> Action \-\> Observation 的认知范式。大模型首先产生当前判断，随后发起确定的工具调用请求。引擎执行动作后，将真实的终端输出或接口响应作为物理事实返回。大模型基于新的观察结果再次修正，形成闭环，直至满足任务完成条件。

###### 工具调用分发：

模型输出工具调用请求后，引擎通过工具白名单进行权限拦截与路由分发。调用外部能力时，引擎作为 MCP Client 与独立 MCP Server 建立 JSON\-RPC 握手；调用本地系统时，引擎将命令发往本地沙盒终端执行，并截获 stdout / stderr；调用状态修改器时，引擎检查该工具是否被允许写入目标状态文件；触发大体积输出时，引擎调用 offload\_tool\_result\(\)，将原文写入 refs/\*\.md。

###### 微观状态覆写：

在经历多次 ReAct 循环试错后，大模型为了防止自身上下文窗口被大量废旧报错堆栈撑爆，会主动或被引擎要求调用 update\_plan 工具。引擎执行该调用，将 Plan 上已失效的历史日志擦除，仅写入最新当前聚焦点。这种执行期“主动新陈代谢”确保上下文保持精简。

###### 死循环与异常熔断：

如果同一类错误多次出现、工具调用次数超过阈值、文件内容没有实质变化、上下文水位持续升高或命令超时，引擎必须触发防守型熔断。熔断动作不是让模型继续猜，而是冻结当前任务、保留现场证据、总结失败路径，并请求人类断言或切换策略。

##### 阶段 4：治理层强制校验（Governance Interception）。

核心机制：用物理底线取代模型的“盲目自信”，强制执行工程验收标准。

###### finish 拦截：

模型自认为代码无误，调用 finish\_task。引擎强行挂起该请求，不允许模型直接宣布完成。

###### 规则读取：

引擎遍历读取 workflow / policy 目录，提取用户定义的状态机流转规则，例如“从状态 A 到状态 B 必须满足什么条件”“当前 task 的 allowed\_paths 是哪些”“必须跑哪些 gate”。

###### 载荷执行：

根据声明文件的指向，引擎动态调用 hooks/xxx\.sh 或 hooks/xxx\.py，例如跑 lint、单测、类型检查、build、快照测试、安全扫描、diff 检查。

###### 裁决反馈：

Exit Code 为 0 时放行流转。当且仅当进入治理阶段，且底层校验载荷返回成功标志时，引擎底层才触发 on\_validation\_success 事件钩子，临时激活 commit\_memory\(\) 工具的写入权限。若 Exit Code 非 0，则将报错日志截获，作为新的 Prompt 强行打回给大模型进行下一轮 ReAct 循环。

##### 阶段 5：经验沉淀与状态销毁（Consolidation \& Teardown）。

核心机制：实现智能体的自我进化，并清理战场。

###### 任务绿灯闭环：

引擎拉起后台的低成本总结模型，扫描本次多轮对话记录、Plan 状态、offload 索引、Mermaid 任务地图和报错修正过程。

###### 经验提炼：

引擎提取出高价值增量经验，调用 Embedding 模型转化为向量，并打上本次任务的元数据标签。此时，Agent 借助阶段 4 刚刚激活的 commit\_memory\(\) 工具写入权限，将刚刚跑通的架构经验作为“新能力”正式刻入 Memory\.md 账本中。

###### 记忆分层更新：

对于可复用的用户偏好、项目约束、架构决策和 Debug 经验，引擎可以进一步生成 L1 原子事实；当同类事实积累到一定程度后，再合并为 L2 场景块，并在必要时更新 L3 项目基线。

###### 临时状态清理：

引擎清理临时工作流文件，释放上下文缓存。Plan 可以归档到 archive，也可以移动到 \.trash，但不能直接无记录删除。对于跨版本迭代，应保留旧版本计划和对应验证结果，避免后续需求变更时失去基线。

#### 常态运行时：全局切分与向量化存储（Embedding 的异步与增量机制）。

核心理念：为了保障开发者体验，避免 IDE 启动卡死，引擎在启动阶段仅挂载数据库访问路径与文件监听器；真正耗费算力的全局代码切片与向量化操作，被解耦并后置到常态运行阶段，分为以下三个生命周期异步执行：

##### 阶段一：冷启动建库期（Background Indexing）

- 触发时机：首次导入全新项目，或底层向量缓存库被清空时。

- 机制描述：引擎在后台开启低优先级处理线程，逐步读取工作区有效文件，执行物理切片、调用 Embedding 模型转化为高维向量，并绑定对应物理路径等元数据，最终落盘存入本地微型库。

- 非阻塞特性：这是异步操作。在建库进度条跑完之前，Agent 依然可以正常对话，且能够流畅使用第 1\~4 级检索机制。只有当任务被迫降级触发第 5 级语义化向量检索时，才会因索引未完成而受限。

##### 阶段二：热更新期（Incremental Sync）

- 触发时机：冷启动全量建库完成后，开发者或 Agent 随时修改并保存文件时。

- 机制描述：引擎启动时注册的文件监听器捕获变更事件。引擎仅针对发生变动的文件进行重新切片与向量化，并在数据库中覆写旧记录。

- 设计目的：避免全量扫描，以较低算力损耗确保底层向量知识库与当前物理代码库保持一致。

##### 阶段三：经验沉淀期（Memory Consolidation）

- 触发时机：伴随单次任务生命周期进入阶段 5 时。

- 机制描述：Agent 刚跑通的架构方案或排查出的深度 Bug，经过提炼后会被送入 Embedding 模型向量化，作为增量“业务经验”永久追加到缓存库中。这让检索库不仅包含“死代码”，还包含了“活经验”，实现智能体的飞轮进化。
