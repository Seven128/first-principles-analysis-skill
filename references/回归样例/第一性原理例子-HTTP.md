# HTTP

# HTTP/1\.1 \(持久连接与报文定界\)

**1\. 最终目的 \(The Absolute Objective\)** 相比 HTTP/1\.0 进一步提升底层物理通信链路的利用率，在单位时间内实现更多有效数据的平均传输。

**2\. 目前现状与要解决的问题 \(Current Status \& The Root Conflict\)**

- **无法减少的底层网络时间成本**

    - 受制于光速与物理距离，网络数据包的往返延迟（RTT）绝对存在且无法降为 0。

    - 建立 TCP 可靠信道必须强制支付“三次握手”的固定时间开销。

    - 为避免突发流量导致全网拥塞瘫痪，TCP 连接初期被底层协议强制要求执行“慢启动（Slow Start）”，导致冷连接状态下带宽利用率极低。

- **高频的重复冷启动损耗**

    - **客观限制**：HTTP/1\.0 协议默认采用“发完即关”的短连接模型，服务端响应完毕后立刻销毁底层 TCP 物理链路。

    - **实际冲突**：现代 Web 页面通常包含数十个甚至上百个碎片化资源（如小图、脚本）。获取每个微小资源都要重新经历“建立握手 → 慢启动预热 → 断开销毁”的死循环，导致海量带宽被白白浪费在连接层的重建上，累计延迟极高。

**3\. 采用的方案 \(First\-Principle Solutions\)**

- **3\.1 方案思路 \(Conceptual Solutions\)**

    - **针对“重复冷启动”的思路：物理链路常态化**

        - 修改协议契约，默认开启长连接，禁止单次传输完毕后立即销毁物理通道。

        - 让后续所有 HTTP 请求复用同一条已“预热”的 TCP 链路，彻底豁免重复的握手 RTT 与慢启动惩罚。

    - **配套防御机制：叠加数学边界契约（解决长连接导致的数据粘连）**

        - *引入原因*：物理链路常开后，失去了“TCP 断开”这一天然的数据终结信号，导致管道内不同请求的纯文本二进制数据首尾相连。

        - *解决策略*：在物理字节流之上叠加逻辑维度的长度声明或特殊的截断终结符，强制框定每一份报文的物理终点。

- **3\.2 方案实现 \(Implementation Details\)**

    - **核心架构/机制**：基于纯文本的持久连接（Persistent Connection）与强约束的报文定界模型。

    - **关键模块/流转过程**：

        - **持久连接 \(Keep\-Alive\)**：HTTP 响应头默认启用 `Connection: keep-alive`。客户端与服务端在单次事务结束后保持 Socket 处于挂起状态，承接同域名的后续请求。

        - **静态定界 \(Content\-Length\)**：对于已知大小的静态资源，服务端下发精确的字节长度，客户端底层网络模块按此长度在缓冲区中精准截取，成功拆包。

        - **动态定界 \(Chunked Transfer\)**：针对大小未知的流式数据，引入 `Transfer-Encoding: chunked`。将数据切割为带有十六进制长度标识的数据块（Chunk），并最终以一个长度为 0 的空块作为报文传输结束的绝对信号。

        - **历史死穴 \(应用层队头阻塞\)**：虽引入管线化（Pipelining）尝试批量发送请求，但因基于文本的报文缺乏“请求 ID”标识，服务端被强制要求**严格按序返回**。一旦队首请求耗时过长，后续所有已就绪的资源将被彻底堵死在服务端缓冲区，这就引出了下一代协议（HTTP/2）必须解决的终极痛点。

# HTTP/2 

## 1\. 最终目的 \(The Absolute Objective\)

**在 HTTP/1\.1 的基础上，进一步提升底层数据传输的效率。**

## 2\. 目前现状与要解决的问题 \(Current Status \& The Root Conflict\)

### 纯文本流按序交付导致应用层队头阻塞

#### 客观限制：

- **无切片的连贯文本**：HTTP/1\.1 的报文是基于回车换行符分割的纯文本流，一旦开始发送必须连续发送完毕，物理层面无法中途打断并交错插入其他请求的数据。

- **单通道先进先出**：在单条 TCP 连接内，服务端必须严格按照客户端请求的先后顺序进行响应返回（FIFO）。

#### 实际冲突：

- **慢请求阻塞全局**：服务端处理耗时长的请求或传输大文件时，会长时间霸占整条物理数据通道，导致后续已经就绪的小文件响应被迫在应用层排队等待（即应用层队头阻塞）。

- **并发受限与资源损耗**：为绕开单链路阻塞，浏览器被迫对同域名开启多条（通常为 6 条）TCP 连接，极大加剧了系统端口、内存消耗以及多次 TCP 握手的时间开销。

### 无状态的纯文本头部导致冗余带宽浪费

#### 客观限制：

- **协议无状态且无内建压缩**：HTTP/1\.1 协议本身不记忆之前发送过的头部信息，且采用纯 ASCII 明文传输，底层不具备针对字符串的压缩机制。

#### 实际冲突：

- **无效载荷侵占带宽**：每次请求都必须重复携带完整且冗长的 Cookie、User\-Agent 等元数据。在现代前端极多小请求（如 API 轮询、埋点）的场景下，头部体积经常超过业务 Payload 负载，严重浪费物理上下行带宽。

## 3\. 采用的方案 \(First\-Principle Solutions\)

### 3\.1 方案思路 \(Conceptual Solutions\)

#### 针对纯文本流按序交付导致应用层队头阻塞

- **具体突破点**：协议层引入二进制分帧。将连贯的纯文本报文彻底粉碎为更小粒度的二进制帧（Frame），并为每个帧打上所属的流标识（Stream ID）。这使得不同请求的数据帧可以在同一条 TCP 链路上无序交错发送，接收端再根据 ID 进行重新组装还原。

- **配套防御机制**：无序交错传输会导致所有并发请求在同一通道内混战，可能引发低优资源（如大体积图片）抢占关键资源（如 CSS/JS）带宽的副作用。因此引入了“流优先级（Stream Priority）”机制，并配合逻辑层的“流量控制（Flow Control）”防止单条并发流撑爆接收窗口。

#### 针对无状态的纯文本头部导致冗余带宽浪费

- **具体突破点**：引入维持连接状态的字典表替换机制。在客户端和服务端的物理内存中各自维护一份生命周期等同于当前 TCP 连接的字典表。后续通讯仅发送发生变化的差异头部，以及对应已有表项的整数索引（Index），将百字节级的字符串极致压缩为几个字节的二进制位。

### 3\.2 方案实现 \(Implementation Details\)

- **核心架构/机制**：在原有的 HTTP 应用层语义与 TCP 传输层之间，强行插入一层对上层绝对透明的“二进制分帧层（Binary Framing Layer）”。上层继续使用原有的 HTTP 方法、状态码等语义，该层负责将语义映射并转换为底层的二进制帧序列。

- **关键模块/流转过程**：

    - **数据载体降维映射 \(Stream/Message/Frame\)**：Stream（流）是逻辑上的双向独立通道，包含唯一的整数 ID；Message（消息）对应一次完整的 HTTP 请求或响应；Frame（帧）是最小的物理传输单元（分为 Headers 帧、Data 帧等），所有帧头部均附带所属的 Stream ID。

    - **HPACK 状态机同步**：通讯双方建立连接时初始化静态与动态哈希表。发送端查表，若命中则直接发送极小的索引值；若遇全新自定义头部，则发送完整数据并写入本地动态表。接收端根据收到的索引或新数据同步更新本地动态表，实现两端状态的绝对同频。

    - **服务端主动推送 \(Server Push\)**：服务端在处理主请求（如 HTML）时，可利用特殊的 `PUSH_PROMISE` 帧，抢在浏览器解析 DOM 树并发起资源请求之前，主动将页面必需的 CSS/JS 等关键资源帧预先推送到客户端的物理网络缓存中。
