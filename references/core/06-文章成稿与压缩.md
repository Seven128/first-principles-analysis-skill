# 文章成稿与压缩

## 1. 成文层的位置

文章成稿发生在完整分析之后。分析阶段负责证明事实、因果、替代解释、边界和方案；成文阶段负责把这些已经成立的内容转换成读者容易获得的正确理解。

最高原则是：

> 先保证读者得到与完整推演一致的正确理解，再用结构、句法、具体化和信息选择降低理解成本。不要为了短而删掉必要因果，也不要为了生动增加新的理解任务。

成文只能改变：

- 哪些信息进入主文；
- 信息按什么顺序出现；
- 一条关系怎样拆成句子和段落；
- 需要展开到什么程度；
- 是否使用例子、表格、代码或类比。

执行本规则时，还要读取：

- `references/writing/01-写作规则卡.md`；
- `references/writing/02-文章任务适配.md`；
- `references/writing/03-成文检查.md`。

三份材料分别提供局部变换、文章类型组织和成稿诊断。它们只作用于成文，不覆盖推理层。

成文不能改变：

- 已确认的事实；
- 因果方向和依赖关系；
- 条件、范围和不确定性；
- 用户选择的评价标准；
- 分析阶段没有证据支持的内容。

文章不是完整推演记录，也不是推演的短摘要。它应保留读者形成正确理解所需的最小完整因果，并删除研究过程、重复和无关细节。

## 2. 有效信息密度

本 Skill 追求的是有效信息密度，可以内部理解为：

```text
读者正确理解并能够使用的关键信息
÷
获得这些信息所需的理解成本
```

这不是需要计算的固定分数，而是成文时的判断方向。

有效信息包括关键事实、必要因果、重要边界、必要区别和真正影响行动的步骤。理解成本包括回读、指代确认、同时维护过多新概念、自行补全省略因果，以及处理无关例子或修辞。

因此：

- 字数减少但因果断裂，不算更简洁；
- 内容很多但依赖清楚、局部负担可控，可以是高密度文章；
- 术语很多、关系平铺、需要读者自行组装，不算高质量密度；
- 句子短但彼此像电报一样断裂，也会提高理解成本。

## 3. 先确定文章任务并锁定推演不变量

进入成文前，先从完整分析中列出不能被改动的内容：

1. 核心问题和最终结论；
2. 关键事实与限制；
3. 结论成立所需的因果边；
4. 主要条件、边界和不确定性；
5. 用户采用的评价标准；
6. 必须保留的替代解释；
7. 用户明确要求展开的机制、路径或细节。

这些内容形成成文回查表。后续任何压缩、重排和改写都要能回到这张表。

### 文章任务与读者

成文前在内部明确：

- 读者读完后需要理解、判断或执行什么；
- 交付属于原理解释、完整方案、决策备忘录、经营分析、人的行为解释，还是其他类型；
- 读者已经知道哪些概念；
- 用户要求简要、标准还是完整详细；
- 是否有指定结构；
- 语气应保持中性直接，还是用户明确要求叙事、口语或个人表达；
- 哪些事实需要引用或注明版本边界。

用户没有指定时，默认：

- 面向具备基本背景知识的读者；
- 使用平静、中性、直接的语气；
- 保留标准详细程度；
- 不强制第一人称、故事开头、口头禅、情绪标点或哲学升华。

不同文章任务的组织方式见 `references/writing/02-文章任务适配.md`。

## 4. 提取最小完整因果主线

从完整分析中提取：

1. 一句话回答核心问题；
2. 读者必须知道的起始事实和限制；
3. 从起始事实到结论之间不能删除的因果步骤；
4. 会改变结论的重要边界、代价和不确定性；
5. 用户要求行动时，真正对应差距的执行路径。

先把主线写成简短的关系序列。例如：

```text
旧架构只靠调用栈保存递归进度
→ React 自己没有稳定的暂停位置
→ 需要把进度变成可保存的数据
→ 进度可保存后，计算才能暂停和恢复
→ 计算可中断后，中间结果不能直接污染真实界面
→ 需要在内存中准备完整结果，再集中提交
```

检查多个机制之间的关系：

- 完整推演已经证明先有 A 才能推出 B：按依赖顺序写。
- A、B、C 本来就是并行条件：保留并列、列表或表格。
- 当前材料无法判断关系：保持不确定，不为了流畅制造因果。

文章结构应让读者看见已经成立的关系，而不是把相关机制压成属性清单。

## 5. 控制信息层级

把完整分析中的材料分为三层：

- 主文必须保留：核心结论、关键事实、必要因果和会改变结论的边界；
- 按理解需要选择：代表性例子、关键取舍、必要对比和直接证据；
- 默认不进入主文：内部检查过程、全部候选分支、完整字段盘点、重复案例和弱相关旁支。

用户明确要求实现细节时，可以从第三层选择相关内容，但仍按问题来源和依赖关系展开，不能把全部材料无选择地搬进正文。

## 6. 生成段落骨架

正式写句子前，先为每段写一句内部段落结论。连续读这些段落结论，应当能够看出文章怎样从起点走到结论。

每个段落围绕一个主要新结论展开：

```text
本段新结论
→ 支撑它所需的事实或因果
→ 必要时补边界或一个例子
→ 结论闭合
```

下一句仍在证明当前结论时，留在本段。下一句开始提出新的机制、边界、例子或行动时，通常换段。

不要固定每段几句话。段落边界应与逻辑单元一致：

- 不能为了留白把一条因果拆成多个孤立句；
- 不能在同一段连续完成多个不同问题；
- 列表项本身已经形成清晰边界时，不必再强行拆段。

## 7. 压缩时保留因果桥梁并执行句子变换

按段落骨架逐句写作，并执行以下变换。

### 7.1 一句推进一个主要关系

一个句子以一个主要新结论或主要关系为中心。若一句话同时说明“是什么、为什么需要、怎样工作、产生什么结果”，优先拆开。

拆句后保留真实连接词，避免变成互不相干的短句。

### 7.2 从平铺属性中恢复真实依赖

看到“需要 A、B、C、D”时，回到推演检查：

- B 是否由 A 成立后才出现；
- C 是否处理 A 带来的新问题；
- D 是否只是独立条件。

有依赖就按顺序表达；没有依赖就保留并列。成文不能创造新的因果边。

### 7.3 把抽象名词还原成动作

能写成“谁做什么，改变了什么”时，不优先写“能力建设、机制实现、体系支撑、层面优化”。

例如：

```text
需要实现执行状态的持久化能力
```

改为：

```text
系统要把当前执行到哪一步保存下来，下次才能从这里继续。
```

专业术语确实必要时保留，但先说明它在当前过程中的具体作用。

### 7.4 细节在成为答案时出现

字段属于某个结构，不代表第一次介绍该结构时就要全部展开。

只有当一个字段、模块、协议或术语第一次成为当前因果问题的必要答案时，才进入主文。后续若需要源码级说明，再在对应位置展开。

这样可以避免：

```text
介绍 Fiber
→ 一次列出 child、sibling、return、lanes、flags、alternate 等全部字段
→ 读者还不知道每项为什么出现
```

更合适的顺序是：

```text
先解释为什么要保存遍历位置
→ 此时介绍 child、sibling、return
→ 再解释为什么要保存优先级
→ 此时介绍 lanes
→ 再解释中间结果隔离
→ 此时介绍 alternate
```

详细规则和成对示例见 `references/writing/01-写作规则卡.md`。

## 8. 一条结论只说明一次

判断一个信息是否进入主文：

- 删除后，读者还能否理解结论为什么成立？
- 删除后，是否会误解适用范围或作出不同判断？
- 它是否只是研究过程、被排除的候选分支或一种实现的全部字段？
- 它是否已经在别处表达过同一结论？
- 用户是否明确要求展开这项细节？

通常保留前两个问题涉及的内容，删除、合并或后置后三类内容。

### 简要回答

保留核心结论、最关键事实和最短完整因果链。

### 标准文章

保留核心因果主线、主要机制、重要边界；需要时加入一个例子。

### 完整详细文章或方案

展开所有会影响理解、设计和执行的关键分支、取舍、边界和验证方式。用户点名的机制必须保留，但每项细节仍要有问题来源，并在第一次成为当前答案时出现。

详细不等于：

- 同一目录、字段或流程在多个章节重复；
- 每个模块都附完整定义、代码、例子和代价；
- 把研究记录和资料盘点全部写进主文；
- 为了完整感加入没有问题来源的内容。

## 9. 具体化、例子与比喻

抽象内容难以理解时，按以下阶梯处理：

```text
准确的字面因果
→ 具体主体、动作和状态变化
→ 一个代表性真实例子
→ 必要时使用局部类比或比喻
```

### 例子 Gate

例子至少要完成一项工作：

- 让抽象机制可以观察；
- 串联多个关键因果；
- 区分两个容易混淆的概念；
- 展示适用边界；
- 帮助读者检验是否理解。

加入后检查：

> 删除这个例子，正文的理解成本是否明显增加？

若没有明显增加，删除或缩短。一个例子能够串起主线时，不要在每个章节重新讲同一场景。

### 比喻 Gate

只有以下条件同时满足时才使用：

1. 读者确实缺少目标概念的心智模型；
2. 存在读者更熟悉的参照对象；
3. 对应关系局部、清楚；
4. 不会带入目标对象没有的属性；
5. 比字面机制更短、更容易理解。

使用后立即回到字面机制。不要连续使用多个意象解释同一个概念，也不要让比喻承担证据作用。

## 10. 按文章任务适配

通用成文规则先保证理解效率，再根据文章任务调整组织方式。

- 原理和机制文章：按“已有能力—缺少条件—新机制—新问题—后续机制”推进。
- 完整方案：按“目标—关键差距—机制职责—协作顺序—验证与代价”推进。
- 决策备忘录：尽快给出条件化结论，再围绕评价标准比较。
- 经营和行动分析：围绕结果链、关键断点、干预路径和验证指标组织。
- 人的行为与社会解释：从可观察事件进入感知、解释、候选原因和证据边界。
- 定义和分类：直接给边界、必要属性、例子和反例，不强行写形成史。

具体规则见 `references/writing/02-文章任务适配.md`。文章类型只改变组织方式，不改变分析结论。

## 11. 四层检查与局部重写

完成初稿后，按 `references/writing/03-成文检查.md` 检查：

```text
L1 语言问题
→ L2 结构与关系
→ L3 内容保真与信息选择
→ L4 整体阅读感受
```

发现问题时优先局部修复：

- 句子超载：拆句并恢复连接；
- 段落混杂多个结论：按逻辑单元重组；
- 平铺机制：回到推演恢复真实依赖；
- 抽象：改成主体、动作和状态变化；
- 例子或比喻负担过高：删除、缩短或换成直接过程；
- 重复：保留最适合的位置，其余直接引用或删除。

不要为了通过检查重新生成一篇改变事实和因果的文章。

## 12. 详细程度校准

详细程度由用户任务和读者需要决定。简要回答保留最短完整因果链；标准文章保留主线、主要机制和重要边界；完整方案展开会影响设计、执行与验证的关键分支。

详细不等于重复字段、流程和案例。简洁也不等于只给结论。只要删除某一步会让读者无法准确说明结论为什么成立，就应保留。

## 13. 成稿检查与最终回查

逐项对照第 3 节的推演不变量：

1. 核心结论是否保持一致；
2. 关键事实是否完整且没有新增；
3. 重要因果边是否全部保留；
4. 并列关系是否被误写成因果；
5. 条件、范围和不确定性是否仍在对应结论附近；
6. 用户评价标准是否被替换；
7. 用户点名的关键机制或路径是否保留；
8. 示例和比喻是否没有改变目标机制；
9. 读者是否能沿段落结论从起点走到最终结论。

若不一致，回到对应段落局部修改，再重新检查。

## 14. 常见失败

- **压缩报告型**：删除了重复，但仍把抽象名词和模块清单压在一起，读者需要自行组装关系。
- **研究记录型**：把资料范围、候选分支和检查过程直接写进正文。
- **模块百科型**：每个模块都展开字段、代码、流程和案例，没有信息优先级。
- **属性平铺型**：把有依赖的能力写成“A、B、C、D”，隐藏了形成顺序。
- **虚假因果型**：为了行文顺滑，把并行条件改写成未经证明的先后关系。
- **表面高密度**：术语和结论很多，但局部认知负担过高。
- **过度压缩**：只保留结论，删除了读者理解结论所需的因果桥。
- **比喻驱动型**：意象比目标机制更复杂，或带入错误属性。
- **碎片短句型**：机械拆句和留白，真实连接被切断。
- **模板驱动型**：为了固定标题和数量加入无关内容。
- **作者模仿型**：把口头禅、情绪、故事或固定结构当成跨任务通用规则。
