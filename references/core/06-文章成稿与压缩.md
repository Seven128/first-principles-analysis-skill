# 文章成稿与压缩

## 1. 成文层的位置

文章成稿发生在分析完成之后。

分析阶段追求的是：

- 事实和限制没有漏掉；
- 因果链能够连续推导；
- 主要替代解释得到检查；
- 证据和不确定性边界清楚；
- 方案能够追溯到目标和差距。

成文阶段追求的是：

- 读者能用较低阅读成本获得正确理解；
- 文章只展开当前问题需要的内容；
- 同一结论只在最合适的位置说明一次；
- 句子直白，段落持续推进；
- 详细程度符合用户要求。

文章不是完整推演记录。分析时可以保留大量候选分支和检查过程，正文只保留支撑最终回答所需的内容。

## 2. 适用范围

用户要求以下交付时使用本规则：

- 文章或技术原理文章；
- 报告、备忘录或长篇说明；
- 完整方案、架构说明或系统设计文档；
- 需要把多条分析整理为连续正文的任务。

简短问答、单个判断、局部建议和纯清单不必强行套用文章结构，但仍应遵守去重和直白表达要求。

## 3. 先确定文章任务

成文前在内部明确：

- **读者要解决的核心问题**：读完后应理解、判断或能够做什么；
- **文章用途**：解释原理、支持决策、指导执行，还是记录完整方案；
- **读者已有知识**：哪些概念无需从头解释；
- **用户要求的详细程度**：简要、标准、完整详细，或明确字数；
- **指定结构**：是否必须沿用“最终目的—现状与问题—方案”等结构；
- **证据要求**：是否需要引用、版本边界或事实核验。

用户没有指定时，默认写成面向具备基本背景知识读者的标准解释文章：足够回答问题，但不展开与主线无关的实现清单。

## 4. 提取最小完整因果主线

从完整分析中先提取五类内容：

1. 一句话回答核心问题；
2. 读者必须知道的起始事实和限制；
3. 从起始事实到结论之间不能删除的因果步骤；
4. 会改变结论的重要边界、代价和不确定性；
5. 用户要求行动时，真正对应差距的执行路径。

判断一个信息是否应进入主文，可以问：

- 删除它后，读者是否还能够理解结论为什么成立？
- 删除它后，是否会误解适用范围或作出不同决定？
- 它是否只是研究过程、候选分支或某一种实现的细节？
- 它是否已经在别处表达过同一个结论？

前两个问题为“是”时通常保留。后两个问题为“是”时通常删除、合并或放入补充部分。

## 5. 控制信息层级

把分析材料分成三层。

### 第一层：主文必须保留

- 核心定义或结论；
- 关键事实和限制；
- 不可省略的中间因果；
- 主要机制或路径；
- 会改变结论的重要边界。

### 第二层：按理解需要选择

- 一个有代表性的例子；
- 关键方案的取舍；
- 有助于区分相邻概念的对比；
- 对主要结论有直接支撑的证据说明。

### 第三层：默认不进入主文

- 内部路由和检查过程；
- 已被排除的全部候选解释；
- 每个模块的完整字段、接口和执行流程；
- 与主线关系很弱的历史旁支；
- 多个作用相同的例子；
- 为证明“做过研究”而保留的资料盘点。

用户明确要求实现细节、源码级说明或完整设计时，可以展开第三层中相关内容，但仍要按问题来源组织，不能把所有材料无选择地堆进正文。

## 6. 按读者理解顺序重组

文章顺序不必复制内部推理顺序。通常可以按以下顺序组织：

```text
先给出对象或核心结论
→ 说明结论成立前必须面对的事实和限制
→ 沿因果关系解释关键机制或方案
→ 说明代价、边界和不确定性
→ 在确有帮助时加入例子或执行建议
```

人为设计系统常见的展开方式是：

```text
原有能力已经能做什么
→ 当前任务还要求什么
→ 原有能力为什么做不到
→ 因此需要哪类新能力
→ 新能力引入后又产生什么问题
→ 后续机制怎样处理这些问题
```

行动方案常见的展开方式是：

```text
目标怎样算达成
→ 必须具备哪些条件
→ 当前缺少什么
→ 哪些路径能补足
→ 在用户约束下怎样排序和验证
```

这些是组织方向，不是固定标题。用户指定结构时保留用户结构，但每个部分内部仍应按因果推进。

## 7. 压缩时保留因果桥梁

压缩文章时可以删除重复和旁支，不能删除让结论成立的中间步骤。

例如：

```text
模型只能输出动作意图
→ 动作意图不会直接改变外部状态
→ 需要外部执行器完成真实操作
→ 执行结果还要返回模型，后续判断才能依据现实变化
```

不能只留下：

```text
模型只能输出文本
→ 所以 Agent 需要工具、权限、状态和记忆
```

后一种写法看起来短，但中间关系没有说明，读者只能接受结论，不能理解结论。

可用的压缩方法包括：

- 把作用相同的多个例子收束为一个代表性例子；
- 把同一问题下的相邻机制合并为一个因果段落；
- 用一句普通语言概括一组字段，只保留会影响理解的字段；
- 用表格替代真正需要逐项比较的重复描述；
- 把实现细节移到补充部分，而不是在主线中逐层展开。

## 8. 一条结论只说明一次

常见重复包括：

- 开头定义一次，方案思路再定义一次，结尾又总结一次；
- “现状与问题”已经说明限制，模块章节再次完整复述限制；
- 正文解释完机制，完整案例按相同顺序重新讲一遍；
- “新旧对比”和“总结”再次逐项重复正文。

处理方式：

- 核心定义放在开头，后文直接使用；
- 每个问题只在首次推出对应机制时解释；
- 案例只展示正文尚未直观看出的部分；
- 对比只保留差异，不复述双方全部内容；
- 总结只在文章较长或用户要求时使用，并压缩为结论索引，不逐段重写正文。

## 9. 段落必须增加新信息

一个有效段落通常承担一种作用：

- 提供新事实；
- 完成一个因果步骤；
- 解释一个关键机制；
- 说明边界或替代解释；
- 给出例子；
- 推出行动。

如果一段只是换一种说法强调上一段，应合并或删除。

段落首句优先直接给出该段的新结论，随后说明原因。例如：

> 模型不能直接修改文件，因此 Agent 需要独立的工具执行器。模型输出的工具调用仍然只是数据，执行器负责校验参数、检查权限、调用文件系统，并把真实结果返回模型。

不要先写几句背景和评价，最后才说这一段要表达什么。

## 10. 句子要直白

优先写具体对象和动作：

- “运行时读取文件并把结果返回模型”；
- “权限层在执行前检查路径和命令”；
- “测试失败后，错误信息进入下一轮判断”。

少写：

- 多层抽象名词连续叠加；
- 一个句子塞入多个括号和补充说明；
- “从某种角度看”“进一步可以发现”“这一层的核心本质是”等不增加信息的开场；
- 为了显得严谨而重复同一限制。

句子长度没有固定上限，但一个句子包含多个独立结论时，应拆开。

## 11. 示例、表格、代码和引用

### 示例

示例应满足至少一个条件：

- 把抽象机制变成可观察过程；
- 用一个场景串联多个关键因果；
- 区分两个容易混淆的概念；
- 说明适用边界。

如果示例只是把正文逐项换成具体名词再讲一次，就删除或缩成几句。

### 表格

只有需要横向比较多项内容时使用表格。因果关系优先用连续文字说明，不要把整条推理拆成表格中的孤立名词。

### 代码

代码只用于展示难以用文字准确表达的接口、状态或关键执行流。默认不为每个模块附一段代码。

### 引用

引用应靠近它支撑的事实。证据边界用简洁语言说明，不把资料来源、调研过程和免责声明堆在开头阻断正文。

## 12. 详细程度校准

### 简要回答

保留一句结论、最关键的事实和最短完整因果链。

### 标准文章

保留核心因果主线、主要机制、重要边界；需要时加入一个例子。

### 完整详细文章或方案

展开所有会影响理解、设计和执行的关键分支、取舍、边界和验证方式。可以包含实现细节，但每项细节都要有明确的问题来源。

“详细”不意味着重复，也不意味着把每个字段、历史旁支和研究记录都写入正文。

“简洁”也不意味着只给结论。只要删掉某一步会让因果断裂，就应保留。

## 13. 成稿检查

输出前逐段检查：

1. 这一段提供了什么新信息？
2. 它与前一段是什么关系？
3. 删除后是否会影响理解、判断或行动？
4. 同一结论是否已经在别处出现？
5. 是否展开了用户没有要求的实现细节？
6. 是否因为压缩而删掉了必要因果？
7. 示例、表格和代码是否比直接说明更有效？
8. 文章是否符合用户要求的详细程度？
9. 成文过程是否改变了事实、结论或不确定性？
10. 开头是否尽快进入核心问题，结尾是否避免重复全文？

检查失败时先删减、合并、重排或补回因果，再输出。

## 14. 常见失败

- **研究记录型文章**：把完整推演、资料摘录、候选解释和检查过程全部写给读者。
- **模块百科型文章**：每个模块都展开定义、字段、代码、流程、例子和代价，却没有信息优先级。
- **层层重复型文章**：问题、方案、案例、对比和总结不断复述同一结论。
- **表面高密度**：术语很多、句子很长，但中间因果不清楚。
- **过度压缩**：为了短而只保留结论，读者看不到结论怎样成立。
- **模板驱动**：为了固定标题和数量加入与当前问题无关的内容。
- **元叙述过多**：频繁解释“本文怎样分析”，而不是直接解释对象。
