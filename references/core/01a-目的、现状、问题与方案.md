# 目的、现状、问题与方案

## 1. 位置与作用

这一步发生在输入内容已经分离、核心问题已经确定之后，进入“为什么”或“怎么做”的具体推演之前。

它要解决的是一个通用关系：当对象存在明确目标时，分析不能只列现状和方案，还要先说明最终希望什么结果成立，再由目标与现状之间的差距推出问题，由问题推出方案。

内部默认关系是：

```text
最终目的与完成标准
→ 当前状态、已有能力与客观限制
→ 尚未成立的必要条件，也就是要解决的问题
→ 解决问题所需的设计原则或改变方向
→ 具体方案、机制或行动路径
→ 验证、代价与适用边界
```

这是一组稳定的语义节点，不是所有问题都必须使用的标题模板。是否启用，先由当前对象和问题性质决定。

## 2. 先判断对象是否承载明确目的

### 默认启用

以下场景通常有明确目的：

- 用户或其他行动主体准备达到一个尚未实现的目标；
- 设计、改造或优化技术系统、产品、制度、工作流；
- 解释人为设计物为什么逻辑上需要某些能力，并形成当前结构；
- 分析有意识选择，并且当前材料能够支持主体想获得或避免的结果；
- 比较方案时，用户已经给出目标和评价标准。

### 不应强行启用

以下场景通常应从“要解释的结果”开始，而不是虚构一个最终目的：

- 纯定义、分类或当前事实确认；
- 自然、生物、生态或其他没有设计者的形成过程；
- 市场、行业、舆论、组织文化等由多人局部行动共同形成、没有统一行动主体的结果；
- 愤怒、恐惧、冲动、习惯等自动或半自动反应，且没有证据表明它们是为实现一个明确目标而产生；
- 真实历史中的设计者动机尚无材料支持。

这类问题继续使用：

```text
要解释的结果
→ 形成前条件
→ 直接触发
→ 中间作用过程
→ 维持和放大因素
→ 替代解释与证据
```

如果同一问题同时包含有目的行动和无统一目的的外部结果，分别建立两条链，再说明它们怎样相互影响。

## 3. 最终目的与完成标准

最终目的回答：

> 最终希望什么结果成为事实？

它决定现状中的哪些差异构成问题，也决定后续方案怎样验收。

最终目的应满足：

- 描述主体希望得到、保持、减少或避免的外部结果；
- 能说明达到什么程度算完成；
- 使用用户已经选择的评价标准；
- 不提前写入具体模块、协议、算法和实现属性；
- 多个目标冲突时，说明优先级或给出条件分支。

### 防止方案泄漏

“设计一个可中断、可恢复、可调度的渲染架构”已经写入了解法，不能直接作为最高层目的。

更上位的目的可以是：

> 在浏览器主线程资源有限的条件下，保持界面更新正确，并让重要交互在可接受时间内得到响应。

随后再由旧执行方式无法满足该结果，推出可保存进度、可暂停和可按优先级处理等能力。

同样，“建立一个使用状态机、沙箱和 Gate 的 Harness”也是方案描述。最终目的应先说明希望复杂开发任务达到什么可观察结果，再分析现状缺少哪些条件。

## 4. 当前状态、已有能力与客观限制

当前状态只回答：

> 现在已经有什么，真实发生什么，哪些边界无法忽略？

这里可以包含：

- 已确认事实；
- 已有能力和资源；
- 当前行为、流程或运行方式；
- 计算、时间、成本、规则和权限限制；
- 当前材料中仍未知的部分。

当前状态不能把评价和方案混进事实。例如“架构落后”“需要状态机”“必须加缓存”都不是未经证明即可接受的现状。

“当前状态”和“要解决的问题”可以在最终文章中共用一个大标题，但内部语义必须分开。事实先成立，问题再由事实与目的之间的关系推出。

## 5. 要解决的问题

问题回答：

> 当前状态为什么还不能使最终目的成立，具体缺少什么条件？

它不是对现状换一种负面说法，也不是提前命名某个方案。正确关系是：

```text
最终目的要求结果 R 成立
+
当前状态只能提供条件 A、B
+
R 还依赖尚未成立的条件 C
→ C 的缺失构成当前要解决的问题
```

问题应处在能够指导方案、又没有提前写入实现的层级。

过粗：

- 系统不够智能；
- 性能不好；
- 用户体验差。

过细：

- 缺少某个类；
- 必须增加某个字段；
- 必须使用某个协议。

合适表达：

- 模型能够提出动作，但当前没有执行者把动作变成外部变化，也没有把真实结果送回下一轮判断；
- 渲染进度只存在于同步调用栈中，系统没有可保存和恢复的工作位置；
- 任务状态分散在对话和文件中，阶段切换后无法稳定确认当前事实与完成条件。

复杂问题可以有多个缺口，但必须说明它们是并行条件，还是前一个方案产生新状态后暴露出的后续问题。

## 6. 设计原则与具体方案

### 设计原则

设计原则回答：

> 要补足缺失条件，系统或主体需要发生哪一类改变？

它比具体实现更上位。例如：

- 让行动意图经过受控执行，并把真实结果反馈回来；
- 把临时调用栈中的进度变成可保存的数据；
- 让阶段完成由可执行检查裁决，而不是只依赖模型自我声明。

### 具体方案、机制或行动路径

具体方案回答：

> 用什么实际办法实现上述改变？

每项方案必须能够指出自己处理的是哪个已经证明的问题。没有问题来源的模块、字段、流程和扩展能力，不进入主线。

一种方案通常不是唯一答案。若多条路径都能补足同一个条件，应区分：

- 真正必要的上位条件；
- 当前采用的一种实现；
- 替代路径；
- 选择当前实现所依据的环境和取舍。

## 7. 新状态、新问题与后续方案

技术系统、制度和复杂工作流通常不是一次从问题直接跳到完整答案。更真实的形成过程是：

```text
目的与当前状态
→ 第一个关键问题
→ 第一项方案
→ 系统进入新状态
→ 新状态暴露新的风险、成本或协作问题
→ 第二项方案
→ 继续验证与收敛
```

例如，系统获得真实执行能力后，模型错误会产生外部副作用，因此权限和沙箱成为后续问题；任务跨越多轮后，当前进度可能丢失，因此状态保存和恢复成为后续问题。

后续机制必须由新状态实际产生的问题推出，不能为了“系统完整”一次列出全部模块。

## 8. 逻辑重建与真实历史分开

对技术、产品和制度，可以从任务与限制推出：

> 为了完成该任务，系统逻辑上需要某类能力。

这不能自动证明：

> 历史设计者当时正是以这个目的、按照同一顺序引入该机制。

“最终目的”在原理文章中可以表示系统承担的外部任务或逻辑上的设计目标；若要描述真实历史动机、版本触发和人物意图，仍需一手材料支持。

## 9. 不同问题的结构变体

### 目标与方案

```text
最终目的与完成标准
→ 当前状态
→ 关键差距
→ 多条路径
→ 比较、执行、验证和调整
```

### 人为设计系统的原理

```text
系统承担的外部任务
→ 形成前已有能力与限制
→ 当时最先缺少的条件
→ 设计原则与机制
→ 新状态与后续问题
→ 当前结构、代价和边界
```

### 判断和选择

```text
希望获得或避免的结果
→ 评价标准与优先级
→ 当前事实和预测
→ 各选项怎样影响标准
→ 条件化结论与验证信息
```

这类问题不一定使用“采用的方案”作为标题，因为多个选项可能都保留。

### 无明确目的的结果解释

```text
要解释的结果
→ 条件、触发与作用过程
→ 维持、放大和削弱因素
→ 替代解释与证据
```

不得为了统一格式，把自然结果、群体涌现或自动情绪写成某个主体主动采用的方案。

## 10. 推理层与表达层的关系

推理层固定的是语义关系：目的决定问题，现状提供事实，问题指出缺失条件，方案改变条件，验证判断是否达到目的。

最终输出是否显式使用三个标题，由任务决定：

- 技术原理、系统设计、产品方案、制度设计和完整行动方案，默认可以显式使用“最终目的—当前状态与要解决的问题—采用的方案”；
- 简短回答可以隐含这条链，只保留必要因果；
- 定义、事实确认、自然结果、自动情绪和无统一目的的群体结果，使用与其性质匹配的结构；
- 用户指定其他结构时，在不破坏因果关系的前提下服从用户要求。

固定语义关系不能退化成固定三段模板。标题只帮助读者定位，不能替代真实推导。

## 11. 输出前检查

对适用目的结构的问题，至少检查：

1. 是否先确认存在明确行动主体、设计任务或用户目标，而不是虚构最终目的。
2. 最终目的是否描述外部结果和完成标准，没有提前写入具体方案。
3. 当前状态是否只包含事实、已有能力、限制和未知项。
4. 要解决的问题是否由目的与现状之间缺失的条件推出。
5. 当前状态与问题是否被区分，即使最终共用一个标题。
6. 每项方案是否对应一个已经证明的问题。
7. 是否把一种具体实现误写成排他的必要条件。
8. 方案加入后产生的新问题是否继续被分析，而不是一次平铺全部机制。
9. 验证方式是否真的判断最终目的，而不只检查过程动作。
10. 不适用目的结构的问题是否使用了更合适的结果解释、定义或比较结构。
