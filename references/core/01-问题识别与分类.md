# 问题识别与分类

## 1. 入口目标：建立问题结构，不给问句贴标签

用户输入不等于一个已经整理好的问题。它可能同时包含：

- 背景和已知事实；
- 用户自己的判断、猜测或前提；
- 目标、限制和评价标准；
- 一个或多个明确问题；
- 没有直接写出、但从当前语境可以确认的需求；
- 希望得到的交付形式，例如解释、判断、方案、步骤或直接执行。

正式分析前，先把这些内容分开，再建立问题结构。不能根据句子里出现“是什么、为什么、怎么做”就直接决定推理路线。这些问句形式只能提供弱线索，真正的方向取决于对象状态、行动主体、时间方向、用户角色、未知内容和期望交付。

## 2. 先分离输入中的内容角色

对复杂输入，先在内部区分：

### 任务事实与材料

用户明确提供、文件显示、数据记录或当前可以观察到的内容。

### 用户观点与候选前提

用户对原因、动机、趋势或方案的判断。它们可以作为待检查命题，不能因为用户相信就直接进入事实链。

### 目标、限制与评价标准

用户希望获得、避免、提高或降低什么，以及时间、成本、规则、安全、资源等限制。

### 问题与未知

用户希望理解、判断、选择、改变或完成什么。一个问句里可能有多个未知，一大段说明也可能只服务于一个未知。

### 交付要求

用户需要直接回答、文章、报告、比较、步骤、代码，还是希望助手实际执行某项操作。交付形式会影响输出，但不能替代问题本身。

不要把每句话都当作问题，也不要把背景、观点和限制平铺成若干同级任务。

## 3. 提取候选问题

候选问题按“需要得到一个什么独立结果”提取，不按问号数量、句子数量或疑问词数量提取。

对每个候选问题，至少明确：

```text
主要对象或结果：当前讨论谁或什么？
对象状态：已经存在、正在发生，还是尚未实现？
行动主体：谁形成、运行、改变或选择这个结果？
用户角色：观察者、判断者、行动者，还是要求助手直接执行？
时间方向：解释过去或现在，还是从现在走向未来？
真正未知：边界、事实、原因、运行机制、行动路径、评价标准还是选择结果？
期望交付：解释、判断、方案、步骤、成稿还是实际操作？
证据状态：哪些已知，哪些只是观点，哪些仍未知？
```

这些字段用于内部识别，不要求按表格原样输出给用户。

## 4. 判断是一个问题还是多个问题

复杂输入中的候选问题需要继续判断关系。

### 核心问题

回答后，最能改变用户当前理解、判断或行动的问题。

### 支撑问题

它的答案是回答核心问题所需的前提、证据或中间判断。支撑问题不应与核心问题平铺成同等交付目标。

### 独立问题

它有自己的对象、结果或交付目标，即使不回答其他问题也能单独成立。独立问题不能为了文章顺滑被强行并入另一条因果链。

### 背景、约束和候选前提

它们影响问题，但本身不一定构成需要独立回答的问题。

可以用以下方向判断：

```text
是否服务于同一个最终结果？
是否存在“先回答 A，才能回答 B”的依赖？
是否使用同一组评价标准？
是否共享同一主要对象和时间方向？
其中一项能否在不依赖其他项时独立交付？
```

若多个问句共同服务于一个结果，并存在前置依赖，通常应组织成一个问题树。若对象、结果、证据和交付彼此独立，应保留为多个问题。

内部问题产物应是含义完整的问题结构。它可以是一个问题，也可以由一个核心问题、若干支撑问题和多个独立问题组成。不得为了得到一句话而提前合并独立问题，也不得因为用户提出多个问句，就把同一核心问题机械拆成多个并列任务。

## 5. 按依赖关系安排问题顺序

问题顺序由真实依赖决定，不由用户提问顺序或文章标题决定。

常见关系包括：

```text
定义或事实确认
→ 原因与机制解释
→ 判断或选择
→ 行动与验证
```

这只是常见依赖，不是固定模板。定义已经清楚时可以直接进入解释；原因不影响当前行动时，也可以先给行动结论。用户明确指定优先级时，以当前明确要求为准。

例如：

```text
产品增长停滞，接下来先改投放还是产品？
```

可以建模为：

```text
核心问题：先干预哪个环节更可能改变目标指标？
支撑问题：目标指标具体是什么？下降发生在哪个环节？有哪些候选原因？现有证据支持到什么程度？
行动结果：先验证什么，再改什么？
```

表面上有多个问题，实际围绕同一个决策结果展开。

## 6. 问句形式不等于真实问题方向

“是什么、为什么、怎么做”可以作为底层推理方向，但不能按字面疑问词路由。

### 界定与确认

用户需要知道对象边界、分类标准、当前事实、当前状态或组成关系。

### 形成与运行解释

用户需要理解一个已经存在的对象或结果怎样形成、怎样运行、怎样被实现，或者为什么形成当前结构。

### 达成与改变

主体需要从当前状态走向尚未实现的目标，用户需要行动路径、执行顺序、验证和调整。

例如：

```text
“Agent 的工具调用是怎么做的？”
```

若 Agent 已经存在，用户是观察者，真正未知的是内部实现和运行过程，应进入形成与运行解释。它虽然出现“怎么做”，但不是让用户现在采取行动。

```text
“我准备给自己的 Agent 加工具调用，应该怎么做？”
```

用户是行动者，目标尚未实现，应进入达成与改变。

```text
“Agent 的工具调用是怎么做的？我也准备实现一个。”
```

这是混合问题：先解释已有机制，再以用户当前条件为起点分析实现路径。两条链分别成立后再衔接。

同样，“X 是什么”可能是在问定义，也可能是在问为什么需要 X、X 怎样形成或内部怎样运行。不能只凭“是什么”停在词典定义。

## 7. 使用场景信息校验候选意图

场景信息按以下优先级使用：

```text
用户当前明确说明的目标、限制和交付要求
→ 当前句子的完整语义
→ 当前段落和本轮上下文
→ 此前对话与项目背景
→ 一般语言习惯和关键词
```

当前明确要求可以修正此前语境。过去一直在讨论原理，不代表用户本轮说“我现在要自己实现”时仍应停在解释路线。

历史上下文只提供候选解释，不能代替当前事实，也不能用来编造用户没有说明的目标、能力或偏好。

## 8. 歧义处理与动态修正

意图识别是可修正的假设，不是一次性判决。

### 高置信度

对象状态、行动主体、时间方向和期望交付一致时，直接选择路线，不需要额外追问。

### 存在歧义，但不同解释共享同一主线

先回答共同部分，或使用简短条件分支继续。例如“这个状态机怎么做”既可能是理解机制，也可能是准备实现；两者都需要先说明状态、事件和迁移怎样协作，可以先给最小机制，再根据上下文决定是否展开实现步骤。

### 存在歧义，而且不同解释会产生明显不同的交付

只提出能够区分路线的最少澄清。例如：

> 你是想了解现有系统怎样实现，还是准备自己从零实现一个？

不要把澄清扩展成通用调查表。

### 用户要求直接回答或不适合追问

选择当前证据最强的解释，并在开头简短声明暂定范围。不要把暂定解释伪装成已经确认的用户意图。

### 分析过程中出现新证据

若新信息表明用户真正需要的路线不同，应重新建模。已有解释可以作为支撑，但不能为了保持最初标签而忽略新目标。

## 9. “是什么”包含的不同需求

### 9.1 定义与边界

用户需要知道：

- X 需要具备哪些属性；
- 不具备什么就不属于 X；
- X 与相邻概念有什么区别。

例如“什么是质数”。这类问题直接给出定义、边界和例子，不需要解释形成过程。

### 9.2 识别与分类

用户要判断某个具体对象属于哪一类。

需要：

```text
分类标准
→ 当前对象的可观察属性
→ 与标准逐项比较
→ 得出结论和不确定性
```

### 9.3 当前事实

用户问“现在发生了什么”“这个文件是什么内容”。这属于事实确认，不必强行进入形成分析。

### 9.4 形成原因与机制理解

用户表面问“Agent 是什么”，但真正想知道：

- 为什么需要它；
- 只有原有能力时为什么不够；
- 为什么形成当前结构；
- 各机制怎样协作。

此时转入形成与运行解释。

## 10. 两条主要因果推理方向

### 10.1 解释已经存在的结果

问题形式包括：

- 为什么会有 X；
- 为什么 X 是现在这样；
- X 是怎样形成、运行或实现的；
- 为什么某个人产生某种情绪或行为；
- 为什么组织、市场或自然系统出现某种结果。

统一任务：

> 解释观察到的结果，是由哪些条件、变化和作用过程共同形成的。

### 10.2 达成尚未实现的目标

问题形式包括：

- 主体怎样做到 X；
- 怎样解决、改变、提高或降低某个结果；
- 怎样从当前情况达到目标；
- 怎样设计、执行、验证和调整。

统一任务：

> 从目标成立必须发生什么出发，找出当前还缺什么条件，并推出可以补足条件的路径。

## 11. 判断、比较与选择

“应不应该”“A 还是 B”“方案是否合理”不能直接用好坏回答。

先明确：

```text
用户想获得或避免什么结果？
有哪些必须满足的限制？
比较使用什么标准？
这些标准的优先级由谁决定？
A、B 分别怎样影响每项标准？
结论对哪些假设敏感？
```

没有明确评价标准时，给出条件化结论，不替用户选择价值排序。

## 12. 混合问题

一个请求可能同时包含：

- 解释现状为什么形成；
- 判断现状是否有问题；
- 设计未来怎样改变；
- 多个彼此独立的交付目标。

正确处理：

```text
第一条链：过去的条件与变化 → 当前结果
第二条链：当前情况 → 未来目标所需条件 → 行动路径
独立问题：分别建立自己的对象、证据和交付
```

有依赖的链先分别成立，再说明怎样衔接；独立问题不强行合并。

## 13. 主要对象与外部条件

主要对象是发生变化、作出行为或需要达到目标的对象。

例如“我怎样找到工作”：

- 主要对象是求职者；
- 企业、市场和政策是影响求职者结果的外部条件。

例如“Leader 为什么把项目交给某人”：

- 主要对象可以是 Leader 的决策；
- 团队规则、绩效、候选人能力和关系是影响决策的条件。

不要在分析中途无说明地把主要对象换成市场、公司或另一个人。

## 14. 抽象程度

问题要具体到能够指导推理，又不能细到提前写入答案。

过粗：

- 环境复杂；
- 竞争激烈；
- 人性如此。

过细：

- 某个未来模块缺少某字段；
- 某个方案应该使用某个类名；
- 某人的童年一定发生过某件事。

合适表达：

- 求职者的能力尚未被招聘方稳定识别和验证；
- 只有模型输出时，系统不能直接改变外部状态并依据结果继续行动；
- 当前证据只能说明对方可能把事件理解为不尊重，不能确认其深层经历。

## 15. 信息不足时的处理

### 可以继续分析

缺失信息只会影响具体分支，不改变主要问题时：

- 明确暂定范围；
- 使用“若……则……”；
- 给出需要补充的数据。

### 应当澄清

以下信息缺失会使答案方向明显不同：

- 主要对象不明确；
- 对象是已有结果还是未来目标不明确；
- 行动主体和用户角色不明确；
- 时间范围不同会改变事实；
- 用户要求个性化行动，但当前状态缺失；
- 选择问题没有评价标准；
- 多个候选意图会产生不同交付，且没有共享主线。

只问最少且真正必要的问题。

## 16. 路由检查

正式分析前确认：

- 输入中的事实、观点、限制、问题和交付要求是否已经分开？
- 这是一个问题、一个问题树，还是多个独立问题？
- 核心问题、支撑问题和独立问题分别是什么？
- 是否根据疑问词直接路由，而没有检查对象状态、行动主体和时间方向？
- 用户是观察者、判断者、行动者，还是要求助手直接执行？
- 真正未知的是边界、事实、原因、机制、路径、标准还是选择结果？
- 当前明确要求是否与历史上下文冲突？
- 歧义是否会实质改变交付，是否需要最小澄清？
- 主要对象是谁，结果是什么，是否需要多个主体指南？
- 是否存在未经证明的用户前提，需要先检查？
