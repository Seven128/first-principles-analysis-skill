# 输出与表达规则

## 1. 正文服务于问题，不展示内部工具

内部可以使用分类、路由、检查表和结构化记号，但正文默认只保留：

- 对象和结果；
- 已知事实；
- 连续因果；
- 方案与依据；
- 证据边界；
- 用户需要的行动或判断。

避免写：

- “本次问题类型是……”
- “本文选择形成前基线……”
- “主体 S、目标 O、缺口 G……”
- “下面按照第一性原理框架……”
- “这一段的推理逻辑是……”

除非用户明确要求查看分析方法。

## 2. 先判断交付形式

同一份分析可以有不同交付形式，不能默认都写成长文。

- 用户只问一个判断、原因或下一步：直接回答。
- 用户要求比较：围绕评价标准组织结论。
- 用户要求清单、步骤或方案：按依赖顺序输出行动。
- 用户要求文章、报告、技术说明或完整方案：完成分析后，再使用 `references/core/06-文章成稿与压缩.md` 整理成稿。

交付形式只改变表达和信息展开程度，不改变事实、因果和不确定性。

## 3. 结构由问题决定

### 定义与分类

可以使用：

1. 简洁定义；
2. 必要属性；
3. 排除边界；
4. 相邻概念；
5. 例子与反例。

### 解释结果

可以使用：

1. 要解释的结果；
2. 结果前已有条件；
3. 长期条件与直接触发；
4. 中间作用过程；
5. 维持、放大和替代解释；
6. 证据与边界。

### 达成目标

可以使用：

1. 目标与完成标准；
2. 目标成立的必要条件；
3. 当前情况和关键差距；
4. 路径与因果依据；
5. 取舍；
6. 执行、验证和调整。

### 判断与选择

可以使用：

1. 目标和评价标准；
2. 关键事实与未知；
3. 各选项对标准的影响；
4. 不同偏好下的结论；
5. 需要进一步验证的信息。

不为了统一格式强制所有输出使用固定三个标题。

## 4. 先证明，再命名方案

不要在问题成立之前大段使用具体模块名、机制名或热门方法。

优先写：

```text
任务要求发生真实外部变化
→ 单纯生成文本不能完成
→ 因此需要受控的环境操作和结果反馈能力
→ 再说明可以怎样实现
```

而不是：

```text
系统需要工具调用、MCP、沙箱和状态机
→ 再解释它们为什么有用
```

## 5. 段落应形成完整因果单元

每个关键段落尽量回答：

```text
已知什么
→ 为什么会产生下一步影响
→ 因此形成什么问题、原因或选择
→ 对最终结果有什么作用
```

一段可以包含多个句子，但应围绕一个新结论推进。避免名词堆叠、并列清单和只有结论没有中间过程。

## 6. 普通语言

优先使用日常表达：

- “当时已经有什么”；
- “还缺什么条件”；
- “为什么做不到”；
- “采用这种做法后”；
- “新出现的问题”；
- “需要什么证据确认”。

专业术语不可避免时：

1. 先给普通语言含义；
2. 再给术语；
3. 之后保持一致使用。

优先使用能够说明动作的动词，例如读取、保存、比较、执行、阻止、恢复和验证。少用把动作包装成抽象名词的长句。

## 7. 控制绝对化语言

谨慎使用：

- 必然；
- 绝对；
- 所有人；
- 任何情况；
- 完美；
- 唯一；
- 本质上都是；
- 彻底解决。

只有逻辑定义、数学命题或明确约束确实支持时才使用，并说明范围。

## 8. 保持信息密度

删除：

- 重复结论；
- 只起气氛作用的修辞；
- 对读者无价值的内部准备过程；
- 与目标无关的完整知识百科；
- 为了显得完整而加入的孤立模块；
- 已经在正文解释过、又在案例和总结中重复的内容。

保留：

- 会改变结论的事实；
- 关键中间因果；
- 重要替代解释；
- 方案取舍；
- 验证方式。

信息密度不是把很多术语塞进一句话。高密度输出应当让每个段落都增加可用于理解、判断或行动的新信息。

## 9. 示例、表格和代码的作用

示例用于：

- 让抽象机制可观察；
- 检查因果链是否真的成立；
- 说明适用边界；
- 对比不同条件下结果怎样变化。

表格适合真正需要横向比较的内容。代码适合展示接口、关键状态或一段难以用文字说清的流程。

示例、表格和代码不能只是把正文换一种形式再重复一次，也不能替代证明。

## 10. 输出前语言检查

- 是否出现读者无法理解的内部黑话？
- 是否用夸张词代替证据和机制？
- 是否把推断写成事实？
- 是否把个人偏好写成客观结论？
- 是否先列答案后补理由？
- 每段是否对理解或行动有实际价值？
- 是否有两段表达同一个结论，只是换了措辞？
- 是否能用更直接的动词和更短的句子表达同样含义？
