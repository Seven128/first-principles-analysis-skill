# 输出与表达规则

## 1. 正文服务于问题，不展示内部工具

内部可以使用分类、路由、检查表和结构化记号，但正文默认只保留：

- 对象和结果；
- 已知事实；
- 连续因果；
- 方案与依据；
- 证据边界；
- 用户需要的行动或判断。

避免写：

- “本次问题类型是……”；
- “本文选择形成前基线……”；
- “主体 S、目标 O、缺口 G……”；
- “下面按照第一性原理框架……”；
- “这一段的推理逻辑是……”。

除非用户明确要求查看分析方法。

用户需要文章、报告或完整方案时，正文还应在标题之后尽快写出补全后的实际分析问题。它是读者要理解的分析任务，不是内部路由说明；不能用一个宽泛主题、文章目的或已经得出的结论代替。

## 2. 先判断交付形式

同一份分析可以有不同交付形式，不能默认都写成长文。

- 用户只问一个判断、原因或下一步：直接回答。
- 用户要求比较：围绕评价标准组织结论。
- 用户要求清单、步骤或方案：按依赖顺序输出行动。
- 用户要求文章、报告、技术说明或完整方案：完成分析后，先形成分析定稿和文章契约，再使用 `references/core/06-文章成稿与压缩.md` 整理成稿。

交付形式只改变信息选择、排列方式和展开程度，不改变事实、因果和不确定性。

## 3. 结构由问题决定

### 定义与分类

可以使用：

1. 简洁定义；
2. 必要属性；
3. 排除边界；
4. 相邻概念；
5. 例子与反例。

### 解释结果

可以使用：

1. 要解释的结果；
2. 结果前已有条件；
3. 长期条件与直接触发；
4. 中间作用过程；
5. 维持、放大和替代解释；
6. 证据与边界。

### 达成目标

可以使用：

1. 目标与完成标准；
2. 目标成立的必要条件；
3. 当前情况和关键差距；
4. 路径与因果依据；
5. 取舍；
6. 执行、验证和调整。

### 判断与选择

可以使用：

1. 目标和评价标准；
2. 关键事实与未知；
3. 各选项对标准的影响；
4. 不同偏好下的结论；
5. 需要进一步验证的信息。

不为了统一格式强制所有输出使用固定三个标题。

对目的型技术、产品、制度和完整行动方案，默认在“要分析的问题”之后继续显式保留“最终目的—当前状态与要解决的问题—采用的方案”。这些节点承担不同职责，不能被有效信息密度或压缩要求删除。对不承载明确目的的对象，只保留实际分析问题，并使用与对象性质匹配的后续结构。

## 4. 先证明，再命名方案

不要在问题成立之前大段使用具体模块名、机制名或热门方法。

优先写：

```text
任务要求发生真实外部变化
→ 单纯生成文本不能完成
→ 因此需要受控的环境操作和结果反馈能力
→ 再说明可以怎样实现
```

而不是：

```text
系统需要工具调用、MCP、沙箱和状态机
→ 再解释它们为什么有用
```

专业术语、模块和字段应在它第一次成为当前因果问题的必要答案时出现。属于某个结构，不等于需要在第一次介绍该结构时全部展开。

## 5. 句子和段落围绕关系推进

### 句子

一个句子以一个主要新结论或主要关系为中心。若一句话同时要求读者接受多个可以独立成立的结论，优先拆开，并保留“因此、但、只有、同时”等真实关系。

若多个事实或条件本来并行成立，可以使用并列、列表或表格。只有完整推演已经证明先后依赖时，才按因果顺序改写，不能为了行文顺滑制造新的因果。

### 段落

一个段落围绕一个主要新结论展开。该结论及支撑它所需的最小解释闭合后，再进入下一段。

下一句仍在证明当前结论时，留在本段；下一句开始提出新的机制、边界、例子或行动时，通常换段。不要固定每段句数，也不要为了留白把一条完整因果拆成孤立短句。

## 6. 普通、具体、稳定的语言

能用“谁做什么，改变了什么”表达时，优先写清主体、动作和状态变化。

优先写：

- “系统把当前进度保存下来，下次从这里继续”；
- “运行时读取文件并把结果返回模型”；
- “权限层在执行前检查路径和命令”；
- “测试失败后，错误信息进入下一轮判断”。

少写：

- “进行状态持久化能力建设”；
- “实现执行闭环的体系化支撑”；
- 连续使用“能力、机制、体系、层面、赋能”等抽象名词包装动作。

专业术语确实提高准确性时：

1. 先用普通语言说明它在当前过程里做什么；
2. 再给出术语；
3. 后文保持同一名称，不为追求变化替换多个俗称。

## 7. 控制绝对化语言

谨慎使用：

- 必然；
- 绝对；
- 所有人；
- 任何情况；
- 完美；
- 唯一；
- 本质上都是；
- 彻底解决。

只有逻辑定义、数学命题或明确约束确实支持时才使用，并说明范围。

## 8. 追求有效信息密度

目标不是单位字数塞入最多概念，而是让读者以较低理解成本，获得尽可能多的正确、可用信息。

这里的有效信息包括：

- 会改变结论的事实；
- 不可省略的因果关系；
- 重要边界和区别；
- 真正影响判断或行动的步骤；
- 用户要求掌握的机制和取舍。

理解成本包括：

- 需要回读才能确认主体、指代或关系；
- 一处同时引入过多新概念和新关系；
- 读者必须自行补全被省略的因果；
- 抽象名词、复杂句法或无关细节造成误解；
- 例子和修辞本身又需要额外解释。

因此：

- **简洁**：删除不影响理解、判断或行动的内容。
- **直白**：尽快写出主体、动作、结果和当前结论。
- **直接**：不让元叙述、铺垫和修辞挡在核心信息前。
- **信息密度高**：每段持续增加有效信息，不重复已经建立的内容。
- **不密**：每个局部只要求读者处理有限的新关系，并按真实依赖展开。
- **准确**：成文不能改变推演中的事实、因果方向、成立条件和不确定性。

高信息密度不等于句子都短，也不等于段落都长。句子和段落的长度应服从当前关系是否已经讲清。

## 9. 先具体化，再选择辅助材料

抽象内容难以理解时，按以下顺序处理：

```text
准确的字面因果
→ 具体主体、动作和状态变化
→ 一个代表性真实例子
→ 必要时使用局部类比或比喻
```

示例只有在完成至少一项任务时保留：

- 让抽象机制可以观察；
- 串联多个关键因果；
- 区分容易混淆的概念；
- 展示适用边界；
- 帮助读者检验是否理解。

表格适合横向比较；代码适合展示接口、关键状态或难以用文字说清的执行流。它们不能只是把正文换一种形式再重复一次。

类比或比喻只有在比直接解释更短、更清楚，且不会带入错误属性时使用。使用后要回到字面机制，不能让意象取代事实和因果。

## 10. 文章定位、读者与叙述口吻

文章的目标读者默认是当前提出问题的人。读者视角通过选择其需要的信息、控制解释深度和安排阅读顺序体现，不通过暴露生成上下文体现。技术原理、系统说明和一般报告默认使用中性、自包含的说明口吻，不把读者称为“用户”，不写“用户当前材料”“用户此前提到”“你的求职材料”“本轮对话中”等内容。个人行动建议确有必要时可以使用“你”；只有用户明确要求以自己的口吻发表时才使用“我”。全文视角保持一致。

有效信息密度是成稿质量指标，不是文章定位。文章先明确类型、读者任务、职责范围和范围外内容，再决定哪些信息进入主文。

## 11. 输出前语言检查

- 标题之后是否尽快出现补全后的实际分析问题？
- 目的结构适用时，最终目的、当前状态与要解决的问题、采用的方案是否仍然可见？
- 文章类型、读者任务和职责范围是否保持稳定？
- 是否出现“用户当前材料”等生成上下文，或在“我、你、用户”之间无理由切换？
- 核心问题或结论是否尽快出现？
- 是否出现读者无法理解的内部黑话？
- 是否用夸张词代替证据和机制？
- 是否把推断写成事实？
- 是否把个人偏好写成客观结论？
- 是否先列答案后补理由？
- 一句话是否承担多个独立结论？
- 已被证明的依赖是否被压成名词清单？
- 是否为了顺滑制造了原推演没有的因果？
- 每段是否围绕一个主要新结论并完成必要解释？
- 是否能把抽象名词还原为明确主体和动作？
- 同一概念是否保持同一名称？
- 示例、表格、代码或比喻是否确实降低理解成本？
- 是否有两段表达同一个结论，只是换了措辞？
- 删除内容后，必要因果桥梁是否仍然存在？
