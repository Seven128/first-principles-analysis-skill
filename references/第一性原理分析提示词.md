# 第一性原理推演提示词

```text
【第一性原理推演】

[总任务]

请以第一性原理分析用户真正需要解决的问题，并输出一篇因果关系与事实边界严密、面向读者实际理解或决策需要的分析文章。

第一性原理分析始终针对一个具体问题。用户给出的可能是明确问题，也可能只是一个主题、学习目标、事物名称、已有结论、现象、方案或模糊诉求。正式推演前，必须先判断用户最终想获得什么，再将原始请求转换成最能达成该目标的分析问题。

本提示词包含两类主要问题：

1. **目标求解型**：用户知道想达到什么结果，但不知道怎样实现。
2. **原理还原型**：用户已经知道一个事物的大致结论、概括或当前形态，但不知道它为什么出现、为什么形成当前这种形态，以及各机制如何成立。

两类问题使用不同的时间基线，但都必须遵守同一原则：

> 先由客观目标、事实、环境与约束推出必要条件，再用固定主体、固定基线与最终目的之间的差异建立顶层问题，最后在方案部分逐项更新基线并正向推出设计原则与具体机制。不得先看到现有答案，再为答案补写理由。

全文优先级固定为：

**分析问题正确 > 时间基线正确 > 主体、比较端点与抽象层级正确 > 事实正确 > 因果闭合 > 读者价值 > 范围完整 > 方案或原理可成立 > 结构清晰 > 措辞风格。**

---

[输入]

用户原始诉求：
【填写用户提出的请求。可以是明确问题、主题、学习目标、已有结论、现有方案或待分析对象】

用户希望最终获得的结果（可选）：
【例如：得到可执行方案、做出决策、理解某项技术原理、弄清某种行为原因、判断现有方案是否成立】

用户已知或要求保留的锚点（可选）：
【用户已经知道或明确认可的对象概括、结论、范围、术语、事实和文章视角】

用户未知或希望重点弄清的内容（可选）：
【例如：不知道怎样达成目标；知道 X 是什么，但不知道为什么会有 X、为什么 X 采用当前形态、内部机制如何协作】

文章定位与读者：
【例如：知识类原理文章、新方案设计、现有方案优化、商业分析、行为原因分析、决策材料；读者已有知识水平】

已知材料：
【文档、代码、调研报告、数据、历史资料、现有方案、用户描述】

材料角色说明（可选）：
【哪些是核心事实来源，哪些只是背景，哪些只参考语言与信息密度，哪些属于待审查观点】

可复用的通用结论（可选）：
【过去通过第一性原理得到的结论；每条都只是候选论据，必须重新检查适用范围与成立条件】

范围与约束（可选）：
【时间范围、对象层级、系统边界、成本、不能改变的条件、期望深度、是否允许外部检索】

表达要求（可选）：
【语言、篇幅、是否需要代码、流程图、实例、表格或引用】

---

[最高约束一：先确定最优分析问题]

正式推演前，先在内部回答：

1. 用户读完后希望能够理解、判断、选择或完成什么？
2. 用户已经知道什么，真正不知道什么？
3. 用户给出的是待解决问题，还是为了学习某个已有事物而提出的主题？
4. 直接照抄表面题目，是否足以达成用户目标？
5. 哪一个具体问题最能解释用户真正关心的内容？

在内部形成一句任务定义：

**本次最优分析问题是：______。**

除非用户要求展示分析方法，否则不要把这句内部任务定义写进正文。

不得把以下内容直接当作分析问题：

- “写一篇文章”；
- “介绍一下 X”；
- “总结资料”；
- “让内容更专业”；
- 背景材料中被反复强调、但未必属于本题主线的局部指标。

这些只是交付形式、主题或线索，需要继续还原成一个可分析的问题。

### A. 目标求解型问题

当用户希望达成一个尚未实现的结果时，将问题规范为：

**在当前主体、资源、环境与约束下，怎样补足达成目标 O 所需的条件，并最终实现 O？**

此类问题的分析时间点是**当下**。现状必须写用户或主体当前真实具备的能力、资源、限制、执行方式和问题。

示例：

- 原始诉求：怎样找到前端开发工程师工作？
- 最优分析问题：当前求职者怎样满足岗位发现、能力匹配、履历识别、面试验证和双方选择所需的条件，最终获得合适的前端开发工作？
- 最终目的：找到符合个人目标与现实条件的前端开发工程师工作。

### B. 原理还原型问题

当用户知道 X 的概括、结论或当前形态，但希望理解实际细节和原理时，将问题规范为：

**为什么会有 X；在 X 尚未形成时，已有能力为什么不足以完成 X 所承担的任务；它与最终目的之间缺少哪些顶层条件；这些条件为什么会逐步形成 X 当前采用的机制与结构？**

此类问题的分析时间点不是今天已经拥有完整 X 的状态，而是预设在：

**X 尚未形成，或本次要解释的核心机制尚未加入时。**

这个时间点称为**形成前基线**。它可以是：

- 真实历史上 X 出现前的状态；
- 构成 X 的基础能力已经存在、但尚未组合成 X 的状态；
- 为解释因果关系而建立的“移除 X 后”逻辑基线。

若使用逻辑基线而非可证实的历史事实，必须按逻辑假设表达，不能伪装成真实历史。

示例：

- 原始诉求：介绍 Agent 原理，让我弄清 Agent 是什么。
- 最优分析问题：为什么会出现 Agent；只有大模型接口时，为什么还不是通用任务执行应用；它与 Agent 的最终概括之间缺少哪些顶层条件；这些条件为什么会逐步形成当前机制？
- 最终目的：Agent 是基于接口式调用大模型的通用任务执行应用。

该示例只说明问题转换和最终目的的写法，不得机械套用其中的机制。

### C. 混合问题

若用户同时要求理解现有原理和设计改进方案：

1. 先使用原理还原型解释现有对象为什么形成；
2. 再把时间点切换到当下，使用目标求解型分析新目标与新约束；
3. 两条因果链分别成立后再衔接；
4. 不得把原设计目的、当前实现和未来优化目标混成一条链。

若不同分析问题会显著改变答案，且上下文无法判断，应提出一个必要的澄清问题；若差异不影响主线，则直接选择最有解释力的问题并明确范围。

---

[最高约束二：最终目的只锁定分析终点]

“最终目的”是本次分析要抵达并证明或实现的终点，不负责承载完整解释。

### 目标求解型

最终目的写用户要达成的目标状态，不写方案。

### 原理还原型

最终目的写用户已知或需要掌握的对象概括、核心结论。模型限制、宿主条件、性能、成本、安全、质量与技术取舍，除非它们本身就是用户要求解释的对象定义，否则进入后续问题或方案，不附加在最终目的后。

最终目的必须满足：

- 原则上只写一句；
- 只有目标本身确实包含两个不可分割的结果时，才允许第二句；
- 不使用列表；
- 不展开过程、条件、问题、限制、模块和机制；
- 不在这里解释为什么；
- 不堆叠“高性能、可观察、可验证、安全、低成本”等质量指标；
- 不把某个子类型、产品或内部组件的目标泛化为整个对象；
- 不把文章写作任务当成最终目的。

最终目的之后，不要立即增加“主体的最小稳定定义”“分析边界与证据等级”等方法论式章节。对象定义如确有必要，用一两句话自然融入后续因果说明；资料角色和证据方法通常只需通过引用与措辞体现。

---

[最高约束三：原理还原型必须逐项正向推出机制]

这是原理还原型最重要的行文与推理规则。

不得采用以下写法：

1. 先列出 X 的完整组成、必要过程或模块清单；
2. 再逐项为这些既有结论寻找理由；
3. 因为现有 X 含有某机制，就反向声称该机制必然必要；
4. 用“一个系统至少需要 A、B、C、D”直接跳过条件为何成立的论证。

正确方法是：

1. 在“现状与要解决的问题”中，用固定主体、固定形成前基线 A₀ 与固定最终目的 O 建立顶层缺口；
2. 在“核心原理与实现机制”中，从 A₀ 开始按依赖关系逐项构造 X；
3. 每加入一项机制，才把结果更新为 A₁、A₂，并继续分析新基线上真实出现的派生问题。

对每一个能力或机制，都必须完成以下因果单元：

**外部任务在当前步骤提出的具体要求
→ 当前基线已经具备什么
→ 当前基线为什么无法满足该要求
→ 缺少的抽象能力或成立条件是什么
→ 为补足该条件应采用什么设计原则
→ X 实际用什么机制落实该原则
→ 该机制加入后，基线发生什么变化
→ 在新的基线上继续分析下一项要求。**

这是一条递进链，不是一组并列清单。后一个问题可能正是前一个能力加入后才产生的新问题，但这种新基线推演应在方案与机制部分展开，不能提前压进固定基线的“现状与要解决的问题”。

例如，通用任务要求外部状态发生真实变化；若当前只有生成信息的模型接口，则系统无法形成行动—反馈闭环，因此先推出“需要环境交互与连续推进能力”。在机制部分落实该能力后，概率性决策才会转化为真实且可能不可逆的副作用，再继续推出权限、隔离与确认边界。不能在现状部分先把工具、循环、队列、沙箱、状态、验证和子代理等完整运行结构全部展开。

具体要求：

- 每一项机制出现前，正文必须先证明它所补足的条件；
- 机制名称不得早于其问题来源大段出现；
- 每推出一项机制，立即把它加入后续方案推演基线；
- 若两项机制并无依赖关系，可以并列，但仍需分别完成因果单元；
- 若某机制只是性能优化、成本优化或特定场景扩展，必须等基础闭环已经成立后再推出；
- 只有全部机制完成正向推导后，才可以给出总览图、完整流程或模块清单；
- 总览用于总结已经证明的结论，不能替代证明过程。

原理还原型的核心推演形式为：

**形成前基线 A₀
→ 顶层缺口 G₁
→ 必要能力 C₁
→ 机制 M₁
→ 更新后的基线 A₁
→ 派生问题 G₂
→ 必要能力 C₂
→ 机制 M₂
→ ……
→ 能完成核心任务的最小形态
→ 当前阶段的性能、成本、安全与场景化优化。**

[最高约束四：正文只保留读者需要的事实、因果和机制]

内部推演可以使用“最优分析问题、形成前基线、对象层级、材料角色、证据等级、缺口公式、审计清单”等工具，但正文默认不得展示这些工具本身。正文应直接陈述对象事实、因果关系、方案机制与边界，让读者理解事物，而不是理解分析者如何组织分析。

默认不得在正文中出现以下方法过程式表达：

- “本次最优分析问题是……”；
- “为了还原 X 的形成原理，形成前基线设为……”；
- “本文采用的分析基线/分析框架/证据等级是……”；
- “下面按照第一性原理分几步分析……”；
- “主体的最小稳定定义、对象层级树、材料角色分类”等内部校准标题。

应把内部判断改写为直接面向对象的事实陈述。例如：

```text
内部判断：为了还原 Agent 的形成原理，形成前基线设为只有大模型接口。
正文表达：只有大模型接口时，系统能够生成信息，但生成结果本身不会读取或改变外部状态。
```

```text
内部判断：需要说明资料的证据等级不足。
正文表达：公开资料能够确认 A；B 的具体实现尚无可靠材料支持，因此这里只能作为合理推断。
```

正文中的每一段至少应帮助读者理解以下一项内容：

- 当前要完成什么；
- 已经具备什么；
- 为什么仍然做不到；
- 缺少什么条件；
- 为什么选择这一设计；
- 具体机制怎样工作；
- 它带来什么结果、成本或边界。

执行“读者价值删除测试”：删除一段后，如果不影响读者理解目标、事实、缺口、机制、结果或边界，则删除；如果只需一句即可交代，就不得扩写成独立章节。

分析范围说明仅在以下情况出现：

- 同一术语存在多个显著不同的对象；
- 不说明范围会导致核心结论被误解；
- 用户明确限定版本、行业或实现。

即使需要，也应直接说明对象范围，通常一两句足够，不得把正文开头写成研究方法报告。

---

[最高约束五：现状与要解决的问题使用固定比较框架]

“现状与要解决的问题”的职责，是证明为什么最终目的在当前或形成前状态下不能成立；“采用的方案/核心原理与实现机制”的职责，才是说明用什么设计恢复条件以及具体怎样实现。两部分之间必须有明确边界。

本节始终使用同一组比较端点：

**固定主体 S
+ 固定当下或形成前基线 A₀
+ 固定最终目的 O
→ A₀ 与 O 之间尚未成立的顶层条件 G。**

不得在本节中：

- 假设已经加入某个未来机制，并把基线改写成 A₁、A₂；
- 用局部任务步骤、一次失败过程或未来运行流程取代主体；
- 从应用、系统或类别层级下钻到接口字段、循环、队列、数据结构和代码层级；
- 把性能、成本或特定场景优化混入决定核心目标能否成立的基础缺口；
- 为了完整而列出未来系统的全部模块和故障模式。

“逐项正向推出机制”是一条跨越第二、第三部分的完整因果链，但职责不同：

- 第二部分完成：**最终目的要求 → 固定基线事实 → 顶层缺口/固有限制 → 根问题与后果**；
- 第三部分完成：**根问题 → 设计原则 → 具体机制 → 新基线 → 派生问题 → 后续机制与验证**。

### 主体一致性

谁或什么要从 A₀ 变成 O，主线就持续围绕谁。外部任务、用户、市场、文件、进程、测试、数据库或环境只作为这个主体需要面对的要求与约束，不能无说明地替代主体。

例如，分析 Agent 时，主线是“只有大模型接口的系统为什么还不是通用任务执行应用”。测试失败、用户补充约束和文件被其他进程修改，可以用于说明任务环境会变化，但不应被展开成现状部分的主体和完整执行故事。

### 层级一致性

问题的抽象层级必须与最终目的匹配。若最终目的定义的是一种应用、系统、能力或商业结果，现状部分应描述同层级的能力缺口与固有限制，而不是直接描述未来模块如何运行。

每个问题单元只写到以下位置：

**最终目的或任务提出的顶层要求
→ A₀ 已经具备的最少必要事实
→ 哪项顶层条件没有成立
→ 形成什么根问题
→ 怎样阻碍最终目的。**

本节可以得出“缺少某类抽象能力或条件”，但必须停在能力与条件层。不得继续回答“采用什么模块、协议、数据结构、算法或流程实现”。

### 顶层缺口的两类来源

1. **能力缺口**：基线缺少完成最终目的核心动作所需的能力。
2. **固有限制**：基线已有能力存在会显著约束目标可靠性、持续性、性能、成本或风险边界的限制。

例如，为解释 Agent 为什么需要形成，可以在现状部分概括：

```text
通用任务执行要求应用能够感知并改变外部状态，并依据真实结果持续推进；
只有大模型接口时，系统只能生成候选信息或动作表示，不能自行形成行动—反馈闭环。
```

还可以在同一层级说明：

```text
大模型输出具有概率性，上下文有限，Token 生成需要时间且调用产生费用；
这些限制会约束任务执行的可靠性、持续性、速度与经济性。
```

这两类问题不能被摊成未来模块清单，也不能在此处展开工具调用 JSON、宿主循环、沙箱规则、状态持久化、上下文压缩、并行调度或模型路由。

### 最少充分信息原则

描述现状时，只保留足以证明顶层缺口的最少事实。删除某项细节后若因果链仍然成立，该细节应移到方案部分或删除。

单向边界判断：

- 回答“为什么 A₀ 还不能达到 O、缺少什么顶层条件”的内容，属于现状与问题；
- 回答“用什么实现、怎样组织、具体如何运行”的内容，属于方案与机制；
- 回答“加入 M₁ 后又发生什么”的内容，属于方案部分的新基线推演；
- 同一句同时回答多层内容时，拆开并分别放入对应部分；
- 具体产品名、模块名、协议名、字段名、数据结构、算法名和代码示例，默认放在方案部分；只有它们是形成前状态中不可省略的客观事实时，才可在现状部分简短出现。

完成本节后执行三项检查：

1. **固定端点检查**：每段是否都在比较同一个 A₀ 与 O？
2. **层级检查**：每个问题是否与最终目的处于同一抽象层，而非未来实现层？
3. **压缩检查**：删除运行步骤、例子细节和模块名后，缺口是否仍然成立？若成立，就只保留压缩后的表达。

[最高约束六：版本比较按条件启用]

形成前基线不等于“上一代版本比较”。分析“为什么会有 X”时，可以从没有 X 或尚未形成核心机制的状态出发，但这不意味着必须讨论版本史、上一代产品或新旧差异。

只有满足以下任一条件时，才专门分析版本、代际或升级差异：

- 用户明确要求比较版本、前后代或新旧方案；
- 最优分析问题本身是“为什么从 A 升级到 B”；
- 最终目的明确包含升级、替代、演进或版本变化；
- 某项机制只有通过兼容旧版本或迁移约束才能解释。

未触发时：

- 不设置“上一代系统的真实状态”“新旧架构对比”“版本演进”等章节；
- 不为了讲故事强行寻找上一代方案；
- 只描述完成因果推导所需的形成前基线；
- 不把版本差异当作知识文章的固定组成部分。

触发版本分析时，仍需保证：

- 只写真实存在且有证据的历史状态；
- 区分旧方案已有能力与新约束下暴露的不足；
- 不把新方案引入的副作用倒写成旧方案原本的问题；
- 不用后见之明把当时未知的因素写成设计者必然预见的原因；
- 当前版本特征不能泛化为整个历史阶段共同特征。

[统一内部推演步骤]

正式写作前，在内部完成以下推演。不要输出草稿式思考过程，只输出整理后的文章。

## 第一步：锁定对象、范围与资料角色

确定：

- 本题真正分析的对象；
- 大类、子类型、具体产品或方案、内部组件之间的层级；
- 分析采用的时间点；
- 哪些能力属于对象，哪些来自模型、宿主运行时、外部工具、用户或组织；
- 哪些内容不在本次范围；
- 用户明确指定的文章定位与材料用途。

对象层级可在内部表示为：

**大类 → 子类型 → 具体方案或产品 → 内部组件。**

对每个关键判断检查：

> 该判断是否适用于本题所讨论的层级？

若只适用于子类型、版本或单一产品，必须降回对应层级，不能上推为整个类别的本质。

材料在内部分为：

1. 任务定义材料；
2. 核心事实材料；
3. 子类型或局部实现材料；
4. 背景材料；
5. 风格材料；
6. 待审查观点。

防止：

- 背景材料替换本题对象或主线；
- 子类型特征被泛化为父类别本质；
- 某个产品架构被写成整个类别的必然结构；
- 风格参考中的观点被当作事实；
- 调研资料最关注的局部问题被误写成本次最终目的。

## 第二步：确定最终目的与固定时间基线

### 目标求解型

- 最终目的是当前要实现的目标状态；
- 时间基线是当下真实状态 A₀。

### 原理还原型

- 最终目的是对象概括或核心结论 O；
- 时间基线是对象或核心机制尚未形成的状态 A₀；
- A₀ 只包含当时已经具备的基础能力、环境、约束和真实任务；
- 不得把完整对象已经拥有的能力提前放回 A₀。

执行检查：

1. 最终目的是否原则上只有一句；
2. 时间点是否与问题类型一致；
3. 是否把限制、取舍或未来机制偷渡进最终目的；
4. 是否把未来机制偷渡进形成前现状；
5. 是否误把形成前基线写成版本比较。

## 第三步：从最终目的提取同层级顶层要求

不要先看现有模块。先根据最终目的、参与者、环境和客观事实，提取目标成立所需的少量顶层要求。

### 目标求解型

从最终目的反推必须发生的状态变化，例如：

**当前状态 → 中间必要状态 → 目标状态。**

每一步都需要说明为什么是必要状态，而不是凭经验罗列流程。

### 原理还原型

先问：

- X 的对象概括中，哪些核心动作必须由该对象真实完成？
- 完成这些动作，最低需要哪些顶层能力？
- 现有基础能力有哪些固有限制，会显著约束可靠性、持续性、性能、成本或风险？
- 哪些只是未来实现、当前产品优化或特定场景扩展？

检查方向可以包括：

- 是否需要获取或改变外部状态；
- 是否需要连续多步决策；
- 是否需要保存中间状态；
- 是否需要真实反馈；
- 是否涉及并发、时序或资源限制；
- 是否会产生不可逆副作用；
- 是否需要权限、责任或信任边界；
- 是否需要判断完成和失败；
- 是否存在性能、成本或法律约束。

这些只是内部寻找要求的方向，不是必须全部存在的固定清单，也不得原样作为正文答案。必须合并同一根因，保持与最终目的同层级。

## 第四步：用固定 A₀ 与 O 推出顶层缺口和根问题

在进入任何方案前，固定：

**主体 S + 基线 A₀ + 最终目的 O。**

对每项顶层要求追问：

> 这项要求要真实成立，至少需要什么条件？A₀ 是否已经稳定具备？

计算：

**顶层必要条件 − A₀ 已稳定具备的条件 = 顶层缺口。**

每个根问题必须形成完整因果链：

**最终目的或客观任务
→ A₀ 中与该要求直接相关的最少必要事实
→ 某项顶层条件不成立
→ 最终目的中的某项核心结果无法成立或成本失控。**

本步骤不得：

- 假设已经采用某个机制；
- 更新为 A₁、A₂；
- 展开未来系统循环、队列、调度或恢复；
- 用某个具体任务的完整失败过程替代根问题；
- 解释基线系统的完整输入格式、内部模块、字段、协议、算法或执行流程。

根问题必须：

- 解释症状，不重复症状；
- 位于可设计、可干预、可规避或可取舍的层级；
- 与最终目的处于同一抽象层级；
- 与其他问题不重复；
- 解决后相关失败应消失或显著缓解；
- 无法消除的内容应写成边界或代价。

对性能、成本、质量取舍，必须说明：

- 哪些变量参与取舍；
- 每个变量怎样影响目标；
- 变量为什么冲突；
- 哪些下限不能突破；
- 选择一侧会付出什么代价。

## 第五步：在方案部分逐项推出设计原则与机制

### 目标求解型

对每个根问题按以下链路推导：

**根问题
→ 需要恢复的必要条件
→ 可干预层级
→ 设计原则
→ 具体方案
→ 预期结果
→ 成本与边界。**

### 原理还原型

严格使用递进链：

1. 从 A₀ 的顶层缺口选择当前首先需要恢复的条件；
2. 推出所需抽象能力；
3. 推出设计原则；
4. 再说明 X 实际采用的机制；
5. 把机制加入基线形成 A₁；
6. 只在此时分析 A₁ 中真实出现的派生问题；
7. 继续推出后续机制，直至形成最小成立形态。

不得让实际模块名替代前面的条件推导。

## 第六步：区分不同性质的问题与机制

分析已有事物时，将当前形态拆分为：

1. **顶层能力缺口**：固定 A₀ 与 O 之间缺少什么；
2. **固有限制**：基础能力自身会怎样约束目标；
3. **派生问题**：某项能力或机制加入后才出现或显著放大的问题；
4. **基础必要能力**：缺少后无法完成核心任务；
5. **实现该能力的具体机制**：可能存在其他替代实现；
6. **当前约束下的工程选择**：性能、成本、安全、兼容性与维护性的取舍；
7. **当前技术阶段的优化**：核心闭环已经成立后，为提升表现加入；
8. **特定场景扩展**：只属于某个子类型、行业、版本或产品；
9. **历史路径依赖或遗留复杂度**：不能反向美化成逻辑必然。

第一性原理可以推出“必须具备什么能力”，通常不能仅凭逻辑证明“现有具体实现是唯一方案”。

若存在替代机制，应说明：

- 它们共同满足什么必要条件；
- 当前机制为何在给定约束下被采用；
- 替代路径的主要成本与收益；
- 哪些判断是事实，哪些属于合理推断。

## 第七步：说明完整运行过程

完成逐项推导后，再把已经证明的机制组合成完整流程。

复杂命题使用同一个连续场景串起：

**外部输入或初始状态
→ 当前机制接收与处理
→ 关键中间状态变化
→ 模块之间的协作
→ 冲突、异常或安全处理
→ 最终输出
→ 验证结果。**

完整运行过程只能出现在机制已经逐项证明之后，不能倒灌进“现状与要解决的问题”。

同一例子必须连续推进，不要给每个模块安排互不相关的小例子。

目标求解型检查方案是否把当前状态推进到最终目的。

原理还原型检查：移除某机制后，哪项已经证明的条件会再次失效；恢复该机制后，为什么系统重新成立。

## 第八步：事实、证据与通用结论检查

- 用户对主题、范围、视角和材料角色的说明属于任务契约；
- 用户给出的对象概括可以作为分析锚点，但其中的事实判断仍需证据支持；
- 核心材料只能支持其覆盖范围内的结论；
- 子类型资料不能直接上推到父类别；
- 背景材料不能改变最优分析问题、最终目的和主线；
- 风格材料只影响表达，不提供事实依据；
- 资料未覆盖的内容不得静默补齐，应标为推断、外部知识或待验证；
- 多份资料冲突时，应呈现冲突与选择依据；
- 技术版本、源码、历史、市场数据、法律规则和公司行为等可验证事实，应优先依据可靠来源；
- 不得为填满结构编造数据、源码细节、历史原因、用户动机或内部实现；
- 不使用“绝对、100%、完美、必然、物理上不可能”等强词，除非由定义、数学或明确约束保证。

使用过去沉淀的通用结论前，检查：

- 结论通过什么机制成立；
- 适用于什么主体、层级和范围；
- 依赖哪些前提；
- 在什么情况下失效；
- 在本题中具体解释哪一环；
- 证据等级属于事实、成熟规律、合理推断还是待验证猜测。

若通用结论不能改变当前因果链，不要为了引用而引用。

[正文组织规则]

文章必须服务于读者理解问题或原理，而不是展示分析方法。正文直接陈述对象、事实、条件、问题与机制，不说明“本文如何推演”。标题应描述真实对象、问题、条件或机制，不使用“主体最小稳定定义”“形成前基线设定”“分析边界与证据等级”“上一代系统的真实状态”等内部方法名称，除非用户明确要求。

## 1. 最终目的

只写分析终点：

- 目标求解型：一句话写明目标状态；
- 原理还原型：一句话写明对象是什么或核心结论。

本节不解释、不列举、不展开，不附加模型限制、技术取舍、性能成本或方案条件。

## 2. 现状与要解决的问题

本节只证明“为什么固定基线 A₀ 还不能达到最终目的 O”，不说明“具体怎样解决”。

全文使用同一主体、同一 A₀ 与同一 O。每个问题使用最少充分事实，保持在“最终目的的顶层要求—固定基线—顶层缺口或固有限制—根问题”的层级；详细模块、协议、数据结构、算法、代码、运行步骤和方案加入后的新基线全部留到下一节。

每个问题单元按以下顺序写：

**最终目的或任务的顶层要求
→ A₀ 已经具备的最少必要事实
→ 尚未成立的顶层条件或固有限制
→ 根问题及后果。**

### 目标求解型

时间点是当下。围绕主体当前真实状态，说明达成目标需要哪些状态或条件、当前缺少什么，以及缺口怎样阻碍目标。可以给出必要过程总览，但每一步都要说明必要性，不能先列行动清单或具体方案。

### 原理还原型

时间点是 X 尚未形成或核心机制尚未加入时。本节回答“为什么需要 X”，但正文不写“为还原 X，本文将形成前基线设为……”等方法过程，而是直接陈述“只有基础能力而没有 X”时的事实。

本节优先压缩成少量顶层问题：

1. 基线缺少哪些完成核心任务所需的能力；
2. 基础能力自身有哪些会显著限制目标成立的固有边界；
3. 哪些是决定最小形态能否成立的问题，哪些只是后续性能、成本或场景优化。

例如，Agent 命题的现状可以停在：

- 只有大模型接口时，系统能够生成候选信息或动作表示，但不能自行读取和改变外部状态，也不能根据真实结果持续推进任务；
- 大模型的概率性、有限上下文、生成时延与调用成本，会限制任务执行的可靠性、持续性、速度和经济性。

本节不得继续展开：

- 工具调用 JSON、宿主解析器、ReAct 循环、队列、流水线或子代理；
- 沙箱、权限白名单、状态机、上下文压缩、并行调度或模型路由的具体设计；
- “加入执行能力后”“第一次测试失败后”等 A₁ 之后的完整运行故事；
- 某个具体任务所有可能发生的动态事件。

子标题应直接概括同层级真实问题，例如：

- “模型输出不能形成真实行动—反馈闭环”；
- “模型固有限制约束任务执行的可靠性与经济性”。

不要使用：

- “为了还原 X 的形成原理，形成前基线设为……”；
- “主体的最小稳定定义”；
- “分析边界与证据等级”；
- “上一代系统的真实状态”；
- 与读者问题无直接关系的方法论标题。

完成本节后执行边界检查：

- 若某段不再比较 A₀ 与 O，而是在描述 A₁ 之后发生什么，将其移到下一节；
- 若某段已经回答“用什么实现、参数是什么、模块怎样协作”，将其移到下一节；
- 若某段只是介绍基础系统或具体任务的内部细节，删除到只剩能够证明顶层缺口的事实；
- 若多个小问题可以由同一能力缺口或固有限制解释，合并为更高层的问题。

## 3. 采用的方案 / 核心原理与实现机制

根据任务选择标题：

- 目标求解型使用“采用的方案”；
- 原理还原型使用“核心原理与实现机制”；
- 优化任务使用“优化方案与机制变化”。

### 3.1 方案思路

按上一节的问题顺序逐项承接：

**根问题
→ 需要恢复的条件
→ 设计原则
→ 为什么这样设计
→ 预期作用
→ 代价与取舍。**

不得新增没有问题来源的设计，也不得打乱依赖顺序。

### 3.2 完整方案或机制设计

原理还原型从 A₀ 开始，只有在一项机制已经被推出并加入基线后，才分析新基线中的派生问题。不要把所有派生问题一次性提前列在现状部分。

对每个核心机制说明：

- 设计来源：承接哪个顶层或派生问题和条件；
- 职责与边界：负责什么、不负责什么；
- 输入、状态与输出；
- 核心数据结构、流程、协议、算法、规则或激励；
- 与前后机制怎样协作；
- 异常、失败、冲突、越权或不一致怎样处理；
- 怎样验证局部机制和整体目标；
- 增加了什么成本、延迟、资源消耗、复杂度或风险。

组织顺序固定为：

1. 基础闭环成立所需的机制；
2. 机制加入后出现的可靠性、安全、状态与恢复问题；
3. 当前技术阶段的性能、成本与质量优化；
4. 特定场景扩展。

只有完成逐项论证后，才可给出完整模块图或运行流程图。

### 3.3 完整运行、业务或行为例子

复杂命题必须提供。沿同一场景从输入推进到结果，展示关键状态、机制协作、异常和验证。该例子用于证明已经推出的机制，不得反向充当现状部分的问题定义。

### 3.4 边界、代价与待验证项

只在确有内容时保留，说明：

- 不能解决什么；
- 引入哪些新成本与风险；
- 哪些结果依赖特定条件；
- 哪些判断仍需数据、实验、源码、历史资料或实际运行验证。

### 可复用结论（可选）

只在确实得到跨案例稳定结论时输出，并写明：

- 结论；
- 作用机制；
- 适用主体与范围；
- 成立条件；
- 不适用边界；
- 证据等级。

[领域补充检查]

技术类问题额外区分：

- 模型、Agent 或应用、宿主运行时、外部工具与环境分别负责什么；
- 基础能力、具体实现、派生问题与工程优化；
- 数据结构与执行流程；
- 逻辑阶段与真实同步或异步边界；
- 当前内部状态、候选状态和外部已生效状态；
- 可中断计算与不可中断副作用；
- 并发、并行、抢占、批处理、重试与取消的真实边界；
- 基础成立机制与性能优化的区别。

商业类问题额外说明：

- 目标用户与真实需求；

个人、群体或社会类问题额外说明：

正式输出前，在内部检查以下链路：

### 目标求解型

**用户真实目标 U
→ 最优分析问题 Q
→ 最终目的 O
→ 固定当下基线 A₀
→ 顶层必要过程与条件 C
→ 顶层缺口 G
→ 根问题 R
→ 设计原则 D
→ 方案 M
→ 结果、证据、成本与边界 E。**

### 原理还原型

**用户理解目标 U
→ 最优分析问题 Q
→ 最终概括 O
→ 固定形成前基线 A₀
→ 顶层要求 N
→ 顶层缺口与固有限制 G
→ 根问题 R
→ 必要能力 C₁
→ 机制 M₁
→ 新基线 A₁
→ 派生问题 G₂
→ ……
→ 最小成立形态
→ 当前阶段优化、证据与边界 E。**

逐项审计：

1. **问题类型**：目标求解与原理还原是否选择正确；混合任务是否分开处理。
2. **时间点**：目标求解是否立足当下；原理还原是否立足 X 尚未形成的基线。
3. **最终目的**：是否原则上只有一句，只写分析终点，没有附加限制、取舍或方案。
4. **固定端点**：“现状与要解决的问题”是否始终比较同一个主体、A₀ 与 O。
5. **对象层级**：大类、子类型、产品与内部组件是否混写；问题层级是否与最终目的匹配。
6. **主体一致性**：外部任务、用户、市场、文件、进程、测试和环境是否只作为主体面对的要求，而没有取代主体。
7. **读者价值**：正文是否直接陈述对象事实，而没有出现“为了还原 X，基线设为……”“本文按……”等分析过程语言。
8. **现状压缩**：现状是否只使用证明顶层缺口所需的最少事实；同根症状是否合并；是否误写具体任务的完整动态过程。
9. **现状边界**：是否停在顶层能力缺口、固有限制、根问题与后果；是否误写模块、协议、字段、数据结构、代码、循环、队列或实现流程。
10. **禁止基线偷跑**：现状部分是否假设加入 M₁ 后再讨论 A₁、A₂；若有，移到方案部分。
11. **正向推导**：每项能力是否先由任务要求和当前基线缺口推出。
12. **禁止答案前置**：是否在论证前列出了完整过程、模块或机制清单；若有，删除或移到论证完成后的总览。
13. **基线递进**：方案部分中，前一项机制加入后，是否成为下一项派生问题的真实新基线。
14. **无反向合理化**：是否因为现有机制存在，就假定它必要、唯一或最优。
15. **问题生成**：每个根问题是否来自必要条件与固定基线状态的差异；每个派生问题是否来自新基线。
16. **方案映射**：每个问题是否有对应设计原则与机制；每个机制是否有明确问题来源。
17. **机制层次**：顶层缺口、固有限制、派生问题、基础能力、具体实现、工程选择、阶段优化、场景扩展与历史遗留是否分开。
18. **版本触发**：未明确涉及升级或演进时，是否擅自加入版本对比；若有，删除。
19. **责任归属**：模型、应用、宿主、工具、用户和组织的能力、状态与成本是否归属正确。
20. **事实边界**：事实、来源观点、合理推断与待验证信息是否清楚区分。
21. **连续运行**：同一场景中的数据、状态、控制权、价值或责任是否连续流向结果。
22. **删除测试**：移除任一机制后，能否指出哪项条件重新失效；若不能，该机制可能是孤儿设计。
23. **反向追溯**：从任意机制向上追溯，是否能找到设计原则、根问题、缺口、基线、任务要求与最优分析问题。
24. **代价反噬**：方案成本是否可能破坏最终目的或硬约束。
25. **表达审计**：是否存在重复解释、方法论泄漏、无必要章节或空泛修辞。

任何一项不成立，先修正再输出。

[表达要求]

- 默认使用中文；
- 使用客观陈述视角，不使用“你应该”“我们可以看到”等对话式表达，除非用户明确要求；
- 语言直接、准确、紧凑，保持高信息密度；
- 标题直接概括真实结论、问题或机制，不使用自问自答式标题；
- 优先使用正向定义与因果陈述，减少“不是 X，而是 Y”式反复对照；
- 用具体对象、动作、状态、约束与结果替代“赋能、优化、解耦、提升体验、建立体系”等空泛表达；
- 不为显得底层而滥用“物理、绝对、降维、跃迁、无脑、完美”等修辞；
- 不固定问题数量、模块数量或标题层级，结构服从真实因果关系；
- 不把存在父子、依赖、条件或先后关系的内容摊成同级列表；
- 不重复同一事实、问题或设计动作；
- 不在正文中讨论提示词、生成过程或背景文章之间的比较，除非任务明确要求；
- 不写“为了还原 X，形成前基线设为……”“本文采用……分析框架”“下面按第一性原理……”等方法过程式过渡，直接陈述对象事实；
- “现状与要解决的问题”固定比较 A₀ 与 O，只写同层级的顶层能力缺口、固有限制、根问题与后果；
- 不在现状部分展示方案加入后的新基线、具体任务的完整动态过程、方案名、接口字段、数据结构、循环、队列、代码和实现步骤；
