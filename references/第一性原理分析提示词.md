# 第一性原理推演提示词

```text
【第一性原理推演】

[总任务]

请以第一性原理分析用户真正需要解决的问题，并输出一篇因果关系与事实边界严密、面向读者实际理解或决策需要的分析文章。

第一性原理分析始终针对一个具体问题。用户给出的可能是明确问题，也可能只是一个主题、学习目标、事物名称、已有结论、现象、方案或模糊诉求。正式推演前，必须先判断用户最终想获得什么，再将原始请求转换成最能达成该目标的分析问题。

本提示词包含两类主要问题：

1. **目标求解型**：用户知道想达到什么结果，但不知道怎样实现。
2. **原理还原型**：用户已经知道一个事物的大致结论、概括或当前形态，但不知道它为什么出现、为什么形成当前这种形态，以及各机制如何成立。

两类问题使用不同的时间基线，但都必须遵守同一原则：

> 先由客观目标、事实、环境与约束推出必要条件，再由必要条件与基线状态之间的差异推出问题，最后逐项正向推出方案原则与具体机制。不得先看到现有答案，再为答案补写理由。

全文优先级固定为：

**分析问题正确 > 时间基线正确 > 对象与层级正确 > 事实正确 > 因果闭合 > 读者价值 > 范围完整 > 方案或原理可成立 > 结构清晰 > 措辞风格。**

---

[输入]

用户原始诉求：
【填写用户提出的请求。可以是明确问题、主题、学习目标、已有结论、现有方案或待分析对象】

用户希望最终获得的结果（可选）：
【例如：得到可执行方案、做出决策、理解某项技术原理、弄清某种行为原因、判断现有方案是否成立】

用户已知或要求保留的锚点（可选）：
【用户已经知道或明确认可的对象概括、结论、范围、术语、事实和文章视角】

用户未知或希望重点弄清的内容（可选）：
【例如：不知道怎样达成目标；知道 X 是什么，但不知道为什么会有 X、为什么 X 采用当前形态、内部机制如何协作】

文章定位与读者：
【例如：知识类原理文章、新方案设计、现有方案优化、商业分析、行为原因分析、决策材料；读者已有知识水平】

已知材料：
【文档、代码、调研报告、数据、历史资料、现有方案、用户描述】

材料角色说明（可选）：
【哪些是核心事实来源，哪些只是背景，哪些只参考语言与信息密度，哪些属于待审查观点】

可复用的通用结论（可选）：
【过去通过第一性原理得到的结论；每条都只是候选论据，必须重新检查适用范围与成立条件】

范围与约束（可选）：
【时间范围、对象层级、系统边界、成本、不能改变的条件、期望深度、是否允许外部检索】

表达要求（可选）：
【语言、篇幅、是否需要代码、流程图、实例、表格或引用】

---

[最高约束一：先确定最优分析问题]

正式推演前，先在内部回答：

1. 用户读完后希望能够理解、判断、选择或完成什么？
2. 用户已经知道什么，真正不知道什么？
3. 用户给出的是待解决问题，还是为了学习某个已有事物而提出的主题？
4. 直接照抄表面题目，是否足以达成用户目标？
5. 哪一个具体问题最能解释用户真正关心的内容？

在内部形成一句任务定义：

**本次最优分析问题是：______。**

除非用户要求展示分析方法，否则不要把这句内部任务定义写进正文。

不得把以下内容直接当作分析问题：

- “写一篇文章”；
- “介绍一下 X”；
- “总结资料”；
- “让内容更专业”；
- 背景材料中被反复强调、但未必属于本题主线的局部指标。

这些只是交付形式、主题或线索，需要继续还原成一个可分析的问题。

### A. 目标求解型问题

当用户希望达成一个尚未实现的结果时，将问题规范为：

**在当前主体、资源、环境与约束下，怎样补足达成目标 O 所需的条件，并最终实现 O？**

此类问题的分析时间点是**当下**。现状必须写用户或主体当前真实具备的能力、资源、限制、执行方式和问题。

示例：

- 原始诉求：怎样找到前端开发工程师工作？
- 最优分析问题：当前求职者怎样满足岗位发现、能力匹配、履历识别、面试验证和双方选择所需的条件，最终获得合适的前端开发工作？
- 最终目的：找到符合个人目标与现实条件的前端开发工程师工作。

### B. 原理还原型问题

当用户知道 X 的概括、结论或当前形态，但希望理解实际细节和原理时，将问题规范为：

**为什么会有 X；在 X 尚未形成时，已有能力为什么不足以完成 X 所承担的任务；为补足这些缺口，为什么会逐步形成 X 当前采用的机制与结构？**

此类问题的分析时间点不是今天已经拥有完整 X 的状态，而是预设在：

**X 尚未形成，或本次要解释的核心机制尚未加入时。**

这个时间点称为**形成前基线**。它可以是：

- 真实历史上 X 出现前的状态；
- 构成 X 的基础能力已经存在、但尚未组合成 X 的状态；
- 为解释因果关系而建立的“移除 X 后”逻辑基线。

若使用逻辑基线而非可证实的历史事实，必须按逻辑假设表达，不能伪装成真实历史。

示例：

- 原始诉求：介绍 Agent 原理，让我弄清 Agent 是什么。
- 最优分析问题：为什么会出现 Agent；只有大模型接口时，为什么不足以完成通用任务；为补足执行、反馈、状态、安全与性能等条件，为什么会形成 Agent 当前的结构？
- 最终目的：
  “Agent 是基于接口式调用大模型的通用任务执行应用。由于技术仍处于早期，Agent 需要在宿主机性能、模型能力、模型调用成本与 Agent 执行性能之间进行技术优化和选择取舍。”

该示例只说明问题转换和最终目的的写法，不得机械套用其中的机制。

### C. 混合问题

若用户同时要求理解现有原理和设计改进方案：

1. 先使用原理还原型解释现有对象为什么形成；
2. 再把时间点切换到当下，使用目标求解型分析新目标与新约束；
3. 两条因果链分别成立后再衔接；
4. 不得把原设计目的、当前实现和未来优化目标混成一条链。

若不同分析问题会显著改变答案，且上下文无法判断，应提出一个必要的澄清问题；若差异不影响主线，则直接选择最有解释力的问题并明确范围。

---

[最高约束二：最终目的只锁定分析终点]

“最终目的”是本次分析要抵达并证明或实现的终点，不负责承载完整解释。

### 目标求解型

最终目的写用户要达成的目标状态，不写方案。

### 原理还原型

最终目的写用户已知或需要掌握的对象概括、核心结论；必要时可增加一句当前技术阶段的主要限制或取舍。

最终目的必须满足：

- 以一句为主，最多两句；
- 不使用列表；
- 不展开过程、条件、问题、模块和机制；
- 不在这里解释为什么；
- 不堆叠“高性能、可观察、可验证、安全、低成本”等质量指标；
- 不把某个子类型、产品或内部组件的目标泛化为整个对象；
- 不把文章写作任务当成最终目的。

最终目的之后，不要立即增加“主体的最小稳定定义”“分析边界与证据等级”等方法论式章节。对象定义如确有必要，用一两句话自然融入后续因果说明；资料角色和证据方法通常只需通过引用与措辞体现。

---

[最高约束三：原理还原型必须逐项正向推出机制]

这是原理还原型最重要的行文与推理规则。

不得采用以下写法：

1. 先列出 X 的完整组成、必要过程或模块清单；
2. 再逐项为这些既有结论寻找理由；
3. 因为现有 X 含有某机制，就反向声称该机制必然必要；
4. 用“一个系统至少需要 A、B、C、D”直接跳过条件为何成立的论证。

正确方法是从形成前基线出发，按依赖关系一项一项构造 X。

对每一个能力或机制，都必须完成以下因果单元：

**外部任务在当前步骤提出的具体要求
→ 形成前基线已经具备什么
→ 基线为什么无法满足该要求
→ 缺少的抽象能力或成立条件是什么
→ 为补足该条件应采用什么设计原则
→ X 实际用什么机制落实该原则
→ 该机制加入后，基线发生什么变化
→ 在新的基线上继续分析下一项要求。**

这是一条递进链，不是一组并列清单。后一个问题可能正是前一个能力加入后才产生的新问题。

例如，通用任务需要改变外部环境；若当前只有生成文本的模型接口，则真实环境不会变化，因此先推出“需要受控执行能力”。执行能力加入后，概率性决策开始可能产生不可逆副作用，才进一步推出“需要权限、隔离与确认边界”。不能在开头直接把“工具、沙箱、状态、验证”等全部列为答案。

具体要求：

- 每一项机制出现前，正文必须先证明它所补足的条件；
- 机制名称不得早于其问题来源大段出现；
- 每推出一项能力，立即把它加入后续分析基线；
- 若两项机制并无依赖关系，可以并列，但仍需分别完成因果单元；
- 若某机制只是性能优化、成本优化或特定场景扩展，必须等基础闭环已经成立后再推出；
- 只有全部机制完成正向推导后，才可以给出总览图、完整流程或模块清单；
- 总览用于总结已经证明的结论，不能替代证明过程。

原理还原型的核心推演形式为：

**形成前基线 A₀
→ 缺口 G₁
→ 必要能力 C₁
→ 机制 M₁
→ 更新后的基线 A₁
→ 缺口 G₂
→ 必要能力 C₂
→ 机制 M₂
→ ……
→ 能完成核心任务的最小形态
→ 当前阶段的性能、成本、安全与场景化优化。**

---

[最高约束四：内部分析脚手架不得无必要地进入正文]

以下内容主要用于内部校准：

- 最优分析问题的生成过程；
- 对象层级树；
- 主体最小稳定定义测试；
- 材料角色分类；
- 证据等级清单；
- 范围覆盖测试；
- 提示词采用了什么推理步骤。

除非它们直接影响读者对结论的理解、存在真实争议，或用户明确要求展示，否则不要为这些内容单独设节，也不要长篇展开。

正文中的每一段至少应回答以下一个问题：

- 当前要完成什么？
- 在当时或当下已经具备什么？
- 为什么仍然做不到？
- 缺少什么条件？
- 为什么需要这一设计原则？
- 具体机制怎样工作？
- 它带来什么结果、成本或新问题？

若一段内容只是在展示分析者做了哪些校准，而不帮助读者理解问题、机制、方案或边界，应删除或压缩成一句。

分析范围说明仅在以下情况出现：

- 同一术语存在多个显著不同的对象；
- 不说明范围会导致核心结论被误解；
- 用户明确限定版本、行业或实现。

即使需要，也应简短说明，不得把正文开头写成研究方法报告。

---

[最高约束五：版本比较按条件启用]

形成前基线不等于“上一代版本比较”。分析“为什么会有 X”时，可以从没有 X 或尚未形成核心机制的状态出发，但这不意味着必须讨论版本史、上一代产品或新旧差异。

只有满足以下任一条件时，才专门分析版本、代际或升级差异：

- 用户明确要求比较版本、前后代或新旧方案；
- 最优分析问题本身是“为什么从 A 升级到 B”；
- 最终目的明确包含升级、替代、演进或版本变化；
- 某项机制只有通过兼容旧版本或迁移约束才能解释。

未触发时：

- 不设置“上一代系统的真实状态”“新旧架构对比”“版本演进”等章节；
- 不为了讲故事强行寻找上一代方案；
- 只描述完成因果推导所需的形成前基线；
- 不把版本差异当作知识文章的固定组成部分。

触发版本分析时，仍需保证：

- 只写真实存在且有证据的历史状态；
- 区分旧方案已有能力与新约束下暴露的不足；
- 不把新方案引入的副作用倒写成旧方案原本的问题；
- 不用后见之明把当时未知的因素写成设计者必然预见的原因；
- 当前版本特征不能泛化为整个历史阶段共同特征。

---

[统一内部推演步骤]

正式写作前，在内部完成以下推演。不要输出草稿式思考过程，只输出整理后的文章。

## 第一步：锁定对象、范围与资料角色

确定：

- 本题真正分析的对象；
- 大类、子类型、具体产品或方案、内部组件之间的层级；
- 分析采用的时间点；
- 哪些能力属于对象，哪些来自模型、宿主运行时、外部工具、用户或组织；
- 哪些内容不在本次范围；
- 用户明确指定的文章定位与材料用途。

对象层级可在内部表示为：

**大类 → 子类型 → 具体方案或产品 → 内部组件。**

对每个关键判断检查：

> 该判断是否适用于本题所讨论的层级？

若只适用于子类型、版本或单一产品，必须降回对应层级，不能上推为整个类别的本质。

材料在内部分为：

1. 任务定义材料；
2. 核心事实材料；
3. 子类型或局部实现材料；
4. 背景材料；
5. 风格材料；
6. 待审查观点。

防止：

- 背景材料替换本题对象或主线；
- 子类型特征被泛化为父类别本质；
- 某个产品架构被写成整个类别的必然结构；
- 风格参考中的观点被当作事实；
- 调研资料最关注的局部问题被误写成本次最终目的。

## 第二步：确定最终目的与时间基线

### 目标求解型

- 最终目的是当前要实现的目标状态；
- 时间基线是当下真实状态。

### 原理还原型

- 最终目的是对象概括或核心结论；
- 时间基线是对象或核心机制尚未形成的状态；
- 形成前基线只包含当时已经具备的基础能力、环境、约束和真实任务；
- 不得把完整对象已经拥有的能力提前放回基线。

执行检查：

1. 最终目的是否一句为主、最多两句；
2. 时间点是否与问题类型一致；
3. 是否把未来机制偷渡进了形成前现状；
4. 是否误把形成前基线写成版本比较。

## 第三步：确定目标或外部任务的真实要求

不要先看现有模块。先根据目标、参与者、环境和客观事实，判断任务真正要求什么。

### 目标求解型

从最终目的反推必须发生的状态变化，例如：

**当前状态 → 中间必要状态 → 目标状态。**

每一步都需要说明为什么是必要状态，而不是凭经验罗列流程。

### 原理还原型

从形成前基线出发，先选择当前最先无法完成的一项真实要求，而不是一次性列出完整答案。

可检查：

- 是否需要获取或改变外部状态；
- 是否需要连续多步决策；
- 是否需要保存中间状态；
- 是否需要真实反馈；
- 是否涉及并发、时序或资源限制；
- 是否会产生不可逆副作用；
- 是否需要权限、责任或信任边界；
- 是否需要判断完成和失败；
- 是否存在性能、成本或法律约束。

这些只是寻找要求的检查方向，不是必须全部存在的固定清单，也不得原样作为正文答案。

## 第四步：推出成立条件、缺口与根问题

对当前步骤追问：

> 这项要求要真实成立，至少需要什么条件？形成前或当前基线是否已经稳定具备？

计算：

**必要条件 − 基线已稳定具备的条件 = 缺口。**

每个根问题必须形成完整因果链：

**客观任务或约束
→ 基线能力与执行方式
→ 某项必要条件不成立
→ 某个过程无法完成或成本失控
→ 最终目的受损。**

根问题必须：

- 解释症状，不重复症状；
- 位于可设计、可干预、可规避或可取舍的层级；
- 与其他问题不重复；
- 解决后相关失败应消失或显著缓解；
- 无法消除的内容应写成边界或代价。

对性能、成本、质量取舍，必须说明：

- 哪些变量参与取舍；
- 每个变量怎样影响目标；
- 变量为什么冲突；
- 哪些下限不能突破；
- 选择一侧会付出什么代价。

## 第五步：逐项推出设计原则与机制

### 目标求解型

对每个根问题按以下链路推导：

**根问题
→ 需要恢复的必要条件
→ 可干预层级
→ 设计原则
→ 具体方案
→ 预期结果
→ 成本与边界。**

### 原理还原型

严格使用“逐项正向推出机制”的递进链：

1. 证明当前缺口；
2. 推出所需抽象能力；
3. 推出设计原则；
4. 再说明 X 实际采用的机制；
5. 把该机制加入新基线；
6. 在新基线上继续推出下一机制。

不得让实际模块名替代前面的条件推导。

## 第六步：区分不同性质的机制

分析已有事物时，将当前形态拆分为：

1. **基础必要能力**：缺少后无法完成核心任务；
2. **实现该能力的具体机制**：可能存在其他替代实现；
3. **当前约束下的工程选择**：性能、成本、安全、兼容性与维护性的取舍；
4. **当前技术阶段的优化**：核心闭环已经成立后，为提升表现加入；
5. **特定场景扩展**：只属于某个子类型、行业、版本或产品；
6. **历史路径依赖或遗留复杂度**：不能反向美化成逻辑必然。

第一性原理可以推出“必须具备什么能力”，通常不能仅凭逻辑证明“现有具体实现是唯一方案”。

若存在替代机制，应说明：

- 它们共同满足什么必要条件；
- 当前机制为何在给定约束下被采用；
- 替代路径的主要成本与收益；
- 哪些判断是事实，哪些属于合理推断。

## 第七步：说明完整运行过程

完成逐项推导后，再把已经证明的机制组合成完整流程。

复杂命题使用同一个连续场景串起：

**外部输入或初始状态
→ 当前机制接收与处理
→ 关键中间状态变化
→ 模块之间的协作
→ 冲突、异常或安全处理
→ 最终输出
→ 验证结果。**

同一例子必须连续推进，不要给每个模块安排互不相关的小例子。

目标求解型检查方案是否把当前状态推进到最终目的。

原理还原型检查：移除某机制后，哪项已经证明的条件会再次失效；恢复该机制后，为什么系统重新成立。

## 第八步：事实、证据与通用结论检查

- 用户对主题、范围、视角和材料角色的说明属于任务契约；
- 用户给出的对象概括可以作为分析锚点，但其中的事实判断仍需证据支持；
- 核心材料只能支持其覆盖范围内的结论；
- 子类型资料不能直接上推到父类别；
- 背景材料不能改变最优分析问题、最终目的和主线；
- 风格材料只影响表达，不提供事实依据；
- 资料未覆盖的内容不得静默补齐，应标为推断、外部知识或待验证；
- 多份资料冲突时，应呈现冲突与选择依据；
- 技术版本、源码、历史、市场数据、法律规则和公司行为等可验证事实，应优先依据可靠来源；
- 不得为填满结构编造数据、源码细节、历史原因、用户动机或内部实现；
- 不使用“绝对、100%、完美、必然、物理上不可能”等强词，除非由定义、数学或明确约束保证。

使用过去沉淀的通用结论前，检查：

- 结论通过什么机制成立；
- 适用于什么主体、层级和范围；
- 依赖哪些前提；
- 在什么情况下失效；
- 在本题中具体解释哪一环；
- 证据等级属于事实、成熟规律、合理推断还是待验证猜测。

若通用结论不能改变当前因果链，不要为了引用而引用。

[正文组织规则]

文章必须服务于读者理解问题或原理，而不是展示分析方法。标题应描述真实对象、问题、条件或机制，不使用“主体最小稳定定义”“分析边界与证据等级”“上一代系统的真实状态”等内部方法名称，除非用户明确要求。

## 1. 最终目的

只写分析终点：

- 目标求解型：一句话写明目标状态；
- 原理还原型：一句话写明对象是什么或核心结论；必要时第二句写当前技术阶段的主要限制或取舍。

本节不解释、不列举、不展开。

## 2. 现状与要解决的问题

### 目标求解型

时间点是当下。按因果顺序说明：

**目标要求
→ 必要状态或条件
→ 当前已经具备什么
→ 哪些条件不成立
→ 形成什么根问题
→ 怎样阻碍最终目的。**

可以先给出必要过程总览，但每一步仍需说明必要性，不能只列常识清单。

### 原理还原型

时间点是 X 尚未形成或核心机制尚未加入时。本节回答“为什么需要 X”。

正文必须按递进顺序展开：

**形成前的真实任务与基础能力
→ 第一项无法成立的条件
→ 需要补足的抽象能力
→ 加入该能力后的新状态
→ 在新状态中出现的下一项问题
→ ……**

本节可以推出“需要何种能力”，但不要在开头列出 X 的完整模块清单。具体实现机制放在下一节按同一顺序承接。

子标题应直接概括真实因果，例如：

- “模型输出不能直接改变外部环境”；
- “执行能力引入了不可逆操作风险”；
- “多步任务需要保存可继续使用的中间状态”。

不要使用：

- “主体的最小稳定定义”；
- “分析边界与证据等级”；
- “上一代系统的真实状态”；
- 与读者问题无直接关系的方法论标题。

## 3. 采用的方案 / 核心原理与实现机制

根据任务选择标题：

- 目标求解型使用“采用的方案”；
- 原理还原型使用“核心原理与实现机制”；
- 优化任务使用“优化方案与机制变化”。

### 3.1 方案思路

按上一节的问题顺序逐项承接：

**根问题
→ 需要恢复的条件
→ 设计原则
→ 为什么这样设计
→ 预期作用
→ 代价与取舍。**

不得新增没有问题来源的设计，也不得打乱依赖顺序。

### 3.2 完整方案或机制设计

对每个核心机制说明：

- 设计来源：承接哪个问题和条件；
- 职责与边界：负责什么、不负责什么；
- 输入、状态与输出；
- 核心数据结构、流程、协议、算法、规则或激励；
- 与前后机制怎样协作；
- 异常、失败、冲突、越权或不一致怎样处理；
- 怎样验证局部机制和整体目标；
- 增加了什么成本、延迟、资源消耗、复杂度或风险。

组织顺序固定为：

1. 基础闭环成立所需的机制；
2. 当前技术阶段的性能、成本、安全与质量优化；
3. 特定场景扩展。

只有完成逐项论证后，才可给出完整模块图或运行流程图。

### 3.3 完整运行、业务或行为例子

复杂命题必须提供。沿同一场景从输入推进到结果，展示关键状态、机制协作、异常和验证。

### 3.4 边界、代价与待验证项

只在确有内容时保留，说明：

- 不能解决什么；
- 引入哪些新成本与风险；
- 哪些结果依赖特定条件；
- 哪些判断仍需数据、实验、源码、历史资料或实际运行验证。

### 可复用结论（可选）

只在确实得到跨案例稳定结论时输出，并写明：

- 结论；
- 作用机制；
- 适用主体与范围；
- 成立条件；
- 不适用边界；
- 证据等级。

[输出前审计]

正式输出前，在内部检查以下链路：

### 目标求解型

**用户真实目标 U
→ 最优分析问题 Q
→ 最终目的 O
→ 当下必要过程 P
→ 成立条件 C
→ 当前状态 A
→ 缺口 G
→ 根问题 R
→ 设计原则 D
→ 方案 M
→ 结果、证据、成本与边界 E。**

### 原理还原型

**用户理解目标 U
→ 最优分析问题 Q
→ 最终概括 O
→ 形成前基线 A₀
→ 任务要求 N₁
→ 缺口 G₁
→ 必要能力 C₁
→ 机制 M₁
→ 新基线 A₁
→ ……
→ 最小成立形态
→ 当前阶段优化、证据与边界 E。**

逐项审计：

1. **问题类型**：目标求解与原理还原是否选择正确；混合任务是否分开处理。
2. **时间点**：目标求解是否立足当下；原理还原是否立足 X 尚未形成的基线。
3. **最终目的**：是否一句为主、最多两句，没有承担后文职责。
4. **对象层级**：大类、子类型、产品与内部组件是否混写。
5. **读者价值**：是否删除了只服务于分析者校准、但不帮助读者理解的内容。
6. **正向推导**：每项能力是否先由任务要求和基线缺口推出。
7. **禁止答案前置**：是否在论证前列出了完整过程、模块或机制清单；若有，删除或移到论证完成后的总览。
8. **基线递进**：前一项能力加入后，是否成为下一项问题的真实新基线。
9. **无反向合理化**：是否因为现有机制存在，就假定它必要、唯一或最优。
10. **问题生成**：每个根问题是否来自必要条件与基线状态的差异。
11. **方案映射**：每个问题是否有对应设计原则与机制；每个机制是否有明确问题来源。
12. **机制层次**：基础能力、具体实现、工程选择、阶段优化、场景扩展与历史遗留是否分开。
13. **版本触发**：未明确涉及升级或演进时，是否擅自加入版本对比；若有，删除。
14. **责任归属**：模型、应用、宿主、工具、用户和组织的能力、状态与成本是否归属正确。
15. **事实边界**：事实、来源观点、合理推断与待验证信息是否清楚区分。
16. **连续运行**：同一场景中的数据、状态、控制权、价值或责任是否连续流向结果。
17. **删除测试**：移除任一机制后，能否指出哪项条件重新失效；若不能，该机制可能是孤儿设计。
18. **反向追溯**：从任意机制向上追溯，是否能找到设计原则、根问题、缺口、基线、任务要求与最优分析问题。
19. **代价反噬**：方案成本是否可能破坏最终目的或硬约束。
20. **表达审计**：是否存在重复解释、方法论泄漏、无必要章节或空泛修辞。

任何一项不成立，先修正再输出。
```
