# 产品发现与验证

## 适用问题

- 判断某类用户是否存在值得解决的问题，以及某项产品或功能是否值得继续。
- 从访谈、试用、反馈或产品数据中判断：还缺哪些会改变决策的证据。
- 产品方案仍有相互依赖的未决问题，需要组织澄清或选择验证方式。

本指南提供可参考的方法和候选检查方向。它不提供本题事实，也不把某个产品框架变成第二套分析主链。目标、问题、方案、反证和实验优先级继续使用通用规则；只调用下面实际命中的部分。

## 优先检查

### 1. 按依赖关系解决真正影响决策的缺口

**触发条件：** 一个尚未明确的需求或选择，会改变后续方案、范围或验证方式。目标与约束已经清楚时，直接继续分析。

先利用当前对话、已有材料与可查证事实，把未决项分成三类：

- **事实缺口：** 查资料、读源码、读记录或检查环境；不能把本可查证的问题交给用户猜。
- **选择缺口：** 仅当目标取舍或必要授权无法从已有信息确定、且不同回答会实质改变结果时询问。
- **实测缺口：** 体验、行为或效果不能靠讨论确定时，转成原型、观察或实验候选。

沿当前问题结构标明依赖，不为遍历整个产品而生成新的问题目录：

1. 只处理前置条件已经明确的未决项；互不依赖的问题可以一起处理。
2. 如果 B 的选项会随 A 的回答改变，先解决 A，再重写 B；尚未返回的查证结果也算未决前置条件。
3. 复用用户已经给出的选择和授权。资料能回答、当前判断不受影响或可合理暂定的问题，不反复确认。
4. 新回答只重开受影响的分支；不把整份分析从头再问一遍。
5. 关键未知已能决定下一步时停止追问；其余未知说明影响，必要时保留条件分支。用户要求直接回答时采用有依据的暂定范围，不强迫进行访谈。

**回到主链的产物：** 更新“已确定选择、依据、仍未知的前置条件、受影响的方案”，用于修正现状、约束或候选路径。提问本身不证明方案正确。

**失效边界：** 当事人也不知道真实效果时，多问几轮不会产生效果证据。不同选择有已知取舍时可直接比较；需要观察时只提出适当验证，不把发现缺口当作执行外部实验的授权。

### 2. 采集真实任务证据，并标明观察如何被影响

**触发条件：** 判断需求、使用障碍或采用意愿时，主要材料来自访谈、演示、候补登记或少量试用。

从一次具体任务还原“当时的情境、要完成的结果、实际做法、遇到的阻碍、已付出的代价”。保留用户原话与可核实行为的区别，先了解经历，再讨论方案；避免用带答案的提问诱导认同。

现有替代可能是别的产品、人工协作、临时做法、延期或暂时不做。没有采取行动时，继续区分缺少动机、预算、权限、可用方案或触达机会；不能单凭未行动否定问题存在。

记录会改变观察含义的条件：

- 参与者怎样招募，是否属于目标对象，观察覆盖了什么任务和时间段。
- 研究者是否提示、讲解、代操作；补贴、折扣或额外服务是否改变行为。
- 数据来自本人叙述、直接观察、行为记录还是实际交易；不把这些来源合并成同一种证据。
- 提到比例或提升时，分母、对照和观察周期是否已知；不知道就保留未知。

| 当前观察 | 可以支持的局部判断 | 尚不能直接推出 |
| --- | --- | --- |
| 赞同、点赞、候补登记 | 对表达、主题或尝试机会有兴趣 | 愿意支付、持续使用、获得预期结果 |
| 回忆一次具体困难及替代做法 | 该参与者报告过问题和处理成本 | 问题在目标人群中的普遍程度 |
| 研究者提示后完成任务 | 这些协助条件下可以完成 | 无人协助时也能完成 |
| 目标用户自行完成任务 | 该情境下具备一定可用性 | 任务值得做、会重复使用、交付能扩大 |
| 实际付费或重复使用 | 当前条件下出现了相应行为 | 收入覆盖总成本、需求可持续或可推广 |

**回到主链的产物：** 为相关事实或假设补充“对象与情境、观察、支持范围、未验证部分”。把主要混淆因素带入关键节点校验；将需要新增数据的部分交给通用最小实验规则。

**失效边界：** 兴趣、叙述和调查并非无用，只是回答的问题不同。辅助服务本就是产品的一部分时，协助下完成可以是符合目标的证据；不能强行要求完全自助。人工试交付可以验证结果价值，但其人工成本和不可扩展部分仍要单独核算。

### 3. 分开验证产品成立所需的不同条件

**触发条件：** 团队试图用“技术跑通”“用户喜欢”“有人付费”中的一项，推出产品或新增功能整体已经成立。

根据当前目标选择会改变判断的条件，逐项查看现有证据；没有命中的条件不展开：

| 检查方向 | 要确认的条件 | 合适的证据方向 |
| --- | --- | --- |
| 结果价值 | 目标对象完成任务后得到所需结果，且相对原做法值得采用 | 实际任务结果、替代成本、采用与放弃原因 |
| 使用可行 | 在预定服务方式下，目标对象能理解并完成关键任务 | 与正式使用条件相近的任务观察、失败点和所需帮助 |
| 交付可行 | 提供方能在所需条件、规模和质量下交付 | 实测、运行记录、资源与依赖限制；演示之外的适用范围 |
| 经营或持续运行可行 | 收入、预算或其他支持能够覆盖必要投入，所需交易与规则条件成立 | 支持来源、履约和维护成本、决策与交易过程、适用授权和限制 |

一项证据可以支持多个条件，但应分别说明它实际证明了哪一部分。关键条件未验证时，整体结论保留条件或未知；不因另一个维度表现好而跳过它。

**回到主链的产物：** 将影响目标成立的缺口挂到对应问题节点，再连接候选机制和验证。检验顺序由该缺口对选择的影响、不确定性和验证成本决定；不另设固定打分、固定问题数量或固定实验时长。

**失效边界：** 公益、内部工具、研究或其他非直接售卖场景可以用任务收益、预算或资助判断，不强套付费与留存。收费产品也要区分使用者、付款者与决定者；已有商业主体规则负责这部分。只解释某项已知技术机制时，不额外执行需求发现。

## 不能直接假设

- 这些方法来自高星仓库，所以它们在本项目中已经得到验证。
- 产品问题必须先完整访谈一遍，或每项选择都要等用户确认。
- 提问次数越多，结论就越可靠。
- 用户提出某个功能，就已经证明该功能是解决问题的合适路径。
- 没人采取行动就没有需求；有人表示喜欢就有足够需求。
- 技术可行、使用可行、结果有价值与经营可行可以互相替代。
- 采用某个产品方法意味着可以自行联系用户、招募受试者、收费或上线实验。

## 证据与验证

优先使用与当前未知相匹配的材料：真实任务记录、访谈原始材料、带观察条件的试用、使用与交易数据、交付实测和适用约束。将原始观察与分析者解释分开，保留样本来源和未覆盖人群。

验证产物应说明下一项决策会怎样被证据改变，而不只增加访谈数量或指标清单。关键论点继续进入核心反向校验；需要新证据时，写出支持继续与提示调整的结果条件。不得把假想用户、模拟访谈或编造数据当作验证完成。

## 常见错误

- 把产品发现方法当作已经成立的商业结论。
- 换一个框架名称，重复已有的目标、问题、方案、替代路径与实验步骤。
- 把互相依赖的选择同时问出，再忽略先前回答对后续选项的影响。
- 将引导后的成功、补贴后的购买或单个积极反馈外推到正式运行。
- 为了显得果断，将未知改写成没有需求或已经验证。
- 将创业、订阅软件或面向消费者的指标强套到不同目标的产品。
