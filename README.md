# First Principles Analysis Skill

一套把模糊或复杂输入转化为清晰问题结构和连续因果分析，并进一步整理成有效信息密度高、局部理解负担可控成稿的 Skill。

当前能力分成五层：

```text
复杂输入的问题建模与场景化意图识别
+
目的型问题中的“最终目的—当前状态与问题—方案”结构
+
通用因果推理、关键节点校验与不同主体变量
+
带适用条件和失效边界的通用结论
+
形成语义锁定的分析定稿，并通过文章契约把它转换成问题明确、结构完整、视角稳定的交付形式
```

目标是先找对问题和推理方向，再让分析因果严密，同时让最终输出简洁、直白、直接。成文不以字数最短为目标，而是在保持事实、因果、条件和不确定性的前提下，降低读者获得正确理解所需的成本。

## 能处理什么

- 从长段输入中分离事实、用户观点、目标、限制、问题和交付要求；
- 识别一个核心问题及其支撑问题，或保留多个彼此独立的问题；
- 把问题结构补全成能够脱离原始对话运行的内部完整分析任务，并为成稿另行生成简短读者可见问题；
- 不依赖“是什么、为什么、怎么做”等问句形式，根据场景识别定义、解释、行动、判断和混合意图；
- 判断当前对象是否承载明确目的，并在适用时建立最终目的、当前状态、问题、方案和验证之间的关系；
- 定义、识别和分类；
- 解释技术、行为、组织或市场结果怎样形成、运行或被实现；
- 分析怎样达到一个目标；
- 比较方案和作出条件化判断；
- 混合的“为什么会这样 + 接下来怎么办”；
- 校验关键原因、必要条件、方案路径和小结论是否遗漏条件或替代路径；
- 把复杂分析整理成文章、报告、方案或直接回答；
- 控制段落碎片、微型例子、普通文字代码块和跨章节重复；
- 迭代 Skill、扩展主体指南、结论卡和回归案例。

## 核心变化

### 1. 复杂输入先建立问题结构

用户说得长，不代表问题多；用户只说一句，也可能包含多个不同目标。入口先把输入分成：

```text
事实与材料
+
用户观点和候选前提
+
目标、限制与评价标准
+
明确或隐含的问题
+
期望交付
```

再判断候选问题之间的关系：

```text
核心问题
→ 回答后最能改变当前理解、判断或行动

支撑问题
→ 回答核心问题所需的前提、证据或中间判断

独立问题
→ 有自己的对象、结果和交付，可以单独成立
```

有依赖的问题按真实顺序展开；独立问题不为了结构整齐被强行合并。同一核心问题也不因多个问句被拆成互相重复的并列回答。

### 2. 问句形式不直接决定意图

“是什么、为什么、怎么做”仍可作为底层推理方向，但疑问词只提供弱线索。入口同时检查：

- 对象或结果是否已经存在；
- 谁形成、运行、改变或选择结果；
- 用户是观察者、判断者、行动者，还是要求助手直接执行；
- 时间方向是解释过去和现在，还是从现在走向未来；
- 用户真正缺少的是边界、事实、原因、机制、路径、标准还是选择结果；
- 需要解释、判断、方案、步骤还是实际操作。

因此：

```text
“Agent 的工具调用是怎么做的？”
→ 通常是在理解已有对象的实现和运行机制

“我准备给自己的 Agent 加工具调用，应该怎么做？”
→ 是从当前状态达到尚未实现目标的行动问题

“Agent 的工具调用是怎么做的？我也要实现一个。”
→ 先解释已有机制，再设计用户的实现路径
```

当前明确目标优先于历史上下文。存在歧义时，只有不同理解会产生明显不同交付，才提出能够区分路线的最少澄清；否则先回答共享主线，或声明暂定范围后继续。

### 3. “是什么”不再一律改成“为什么”

纯定义和分类直接回答边界；当前事实直接确认；只有用户真正需要形成原因、运行过程或内部机制时，才转入解释路线。

### 4. 目的、现状、问题与方案成为一等推理结构

对用户目标、技术系统、产品、制度、工作流和完整方案，分析默认建立：

```text
最终目的与完成标准
→ 当前状态、已有能力与客观限制
→ 尚未成立的必要条件，也就是要解决的问题
→ 设计原则或改变方向
→ 具体方案、机制或行动路径
→ 验证、代价与适用边界
```

这条链明确了三个关系：

- 最终目的决定现状中的哪些差异构成问题；
- 当前状态提供事实，问题是目标与现状之间缺失的条件；
- 方案必须逐项处理已证明的问题，并接受结果验证。

最终目的的表达取决于问题方向。目标求解型写行动主体希望获得的外部结果；人为设计系统的原理还原可以先写对象最终形成的稳定角色或目标状态，例如“Agent 是以接口调用的大模型为基础的任务执行应用”。完成标准、运行要求和具体机制分别进入验证、问题和方案节点。无论哪一类，都不能把方案提前写入目的：例如“设计一个可中断渲染架构”已经预设解法，应先写主线程受限时需要成立的更新正确性和交互响应，再由现状推出可保存进度、可暂停和可调度等能力。

复杂系统允许递归：第一项方案改变系统状态后，新出现的副作用、成本和协作问题继续推出后续方案。这样，机制不会被一次平铺成模块清单。

### 5. 目的结构有明确适用边界

三个节点是稳定的语义关系，不是所有问题的固定模板。

默认使用：

- 主体准备达到目标；
- 设计、改造或优化系统；
- 解释人为设计物的逻辑需要；
- 有证据支持的有意识选择；
- 有明确评价标准的方案比较。

默认不强行使用：

- 纯定义和事实确认；
- 自然、生物和生态形成过程；
- 市场、行业、组织文化等无统一主体的群体结果；
- 愤怒、恐惧、冲动和习惯等自动或半自动反应；
- 没有历史材料支持的设计者真实动机。

不适用时，从“要解释的结果”开始，分析条件、触发、作用过程、维持因素和替代解释。这样既保留目的型问题的清晰结构，也避免目的论、拟人化和模板化。

### 6. 两条主要因果推理主线

解释已经存在的结果：

```text
结果
→ 长期条件
→ 直接触发
→ 中间作用过程
→ 维持和放大因素
→ 替代解释与证据
```

达成尚未实现的目标：

```text
目标和完成标准
→ 候选必要条件
→ 当前情况
→ 尚未成立的条件
→ 多条路径
→ 取舍、执行、验证和调整
```

人为设计系统会在解释链前加入外部任务和形成前已有能力，再由差距推出机制；判断、选择和混合问题会组合这些基础方向，但不会把过去形成原因和未来行动混成一条模糊链。

### 7. 关键节点进入因果链前先做反向校验

对直接支撑结论或行动选择的节点，先判断它声称的是必要条件、充分条件、促进条件、一种实现路径还是伴随关系，再检查：

```text
条件存在但结果没有出现
→ 是否遗漏共同条件、作用过程或抑制因素

条件不存在但结果仍然出现
→ 是否存在替代原因或替代路径

A 与 B 同时出现
→ 是否可能反向因果、共同原因或双向强化
```

严格命题与概率命题使用不同的反例标准。发现漏洞后必须补条件、增加替代路径、降低结论强度、缩小范围或删除节点，不能只附一句“存在例外”。目的结构中的最终目的、问题和方案同样要接受这项检查。

### 8. 主体指南按需加载

当前包含：

- 人的行为与情绪；
- 群体与组织；
- 技术系统与产品；
- 行业市场与资源流动；
- 商业与赚钱；
- 制度与政策；
- 自然与生物系统。

指南只提供优先检查方向，不强制填充所有变量。主体指南也帮助判断对象是否具有统一目的，防止把自然过程和群体涌现写成有意识设计。

### 9. 通用结论使用结论卡

当前包含：

- 利益关系链；
- 资源分配；
- 反馈延迟与周期；
- 人的行为与情绪；
- 信息、能力与时间差；
- 资金流向。

每条卡都包含成立条件、失效范围、证据和常见误用。结论卡产生的仍是候选节点，需要经过当前问题的事实筛选和关键节点校验。

### 10. 客观不等于替用户决定价值标准

Skill 不默认长期优于短期、稳定优于波动、持续优于一次性。方案比较使用用户明确选择的目标，同时说明法律、规则、安全、成本和后果。

### 11. 完整推演与最终成文分离

分析阶段先保证问题结构、目的结构适用性、事实、因果、关键节点强度、替代解释和证据边界完整。用户需要文章、报告或完整方案时，再执行成文转换：

```text
问题建模与场景路由
→ 判断目的结构是否适用
→ 完整推演与节点校验
→ 锁定问题结构、事实、因果、条件、结论强度和不确定性
→ 识别文章任务与读者
→ 提取最小完整因果主线
→ 按真实依赖生成段落骨架
→ 把抽象名词还原成主体、动作和状态变化
→ 先尝试不用例子，必要时加入一个整体例子
→ 控制代码块、列表、标题和重复
→ 去重、校准详细程度
→ 四层检查与推演回查
```

这避免六类退化：

- 严密地回答了错误的问题；
- 对所有对象强套最终目的和方案；
- 把研究记录和内部检查表当文章；
- 把多项机制压成抽象名词和属性清单；
- 为了简洁删断因果；
- 为了显得详细而大量换行、举例和重复。

### 12. 分析定稿与文章契约形成真正的阶段边界

用户需要文章、报告或完整方案时，Skill 不直接从原始对话生成正文。分析阶段先形成用于推理的内部完整分析任务和语义锁定的分析定稿；成文阶段再从核心问题生成简短读者可见问题，并明确文章类型、目标读者、读者任务、职责范围、必须覆盖项、范围外内容、详细程度和叙述视角。

默认成稿顺序是：

```text
标题
→ 要分析的问题
→ 适用时的最终目的
→ 当前状态与要解决的问题
→ 采用的方案
→ 验证、代价和边界
```

“要分析的问题”是从核心问题生成的读者可见表达，只说明文章回答什么；“最终目的”说明行动主体希望达到什么结果，或人为设计物最终形成什么稳定角色与目标状态。内部完整分析任务、必须覆盖项和证据边界仍保留在文章契约中。成文阶段只能选择、重排和表达已经成立的分析，不能改变核心未知、增加新结论或把“用户当前材料”等生成上下文写进正文。


### 13. 完整分析任务与读者可见问题分离

分析定稿中的完整任务负责锁定对象、范围、支撑问题和证据边界；文章开头的“要分析的问题”只负责让读者立即知道本文回答什么。成文阶段会从核心问题生成一到三个直接问题，并把必须覆盖的机制与资料边界分别保存在文章契约中，避免把全文答案目录写成长问句。

对人为设计系统的原理文章，最终目的还会区分对象稳定角色、运行结果和完成标准。正文先用一句话锁定对象最终形成什么，再由现状与问题逐步推出执行、反馈、安全、状态和验证等要求。

标题同样属于有效信息：父标题直接写明对象与主要关系，独立语义单元使用小标题，紧凑单段使用段首粗体，父章节不提前完整复述所有子章节。

### 14. 信息密度不等于句子和段落越碎越好

有效信息密度可以理解为：

```text
读者正确理解并能够使用的关键信息
÷
获得这些信息所需的理解成本
```

新的成文规则进一步明确：

- 段落由一个主要结论是否闭合决定，不能把“一句推进一个关系”执行成“一句话一个段落”；
- 多句话共同证明同一结论时，放在一个完整段落中；
- 默认先不用例子，先用准确、具体、直白的语言解释机制；
- 优先使用一个贯穿主链的整体例子，不为每个小论点分别创建微型例子；
- 代码块只承载代码、配置、精确数据、协议、复杂流程和可复制命令；普通句子和简单因果不放进代码块；
- 标题对应主要结构和机制，不为字段、小步骤和短结论单独建标题；
- 开头、正文、案例和总结不完整重复同一结论。

详细程度来自关键事实、因果、取舍和边界，不来自留白、列表和篇幅填充。

## 使用

将本仓库作为 Skill 安装后，用户可以直接提出问题，例如：

- Agent 到底是什么，为什么会形成现在这种结构？
- 请按最终目的、当前状态与问题、采用的方案解释 Fiber。
- 数据库索引是怎么做的？
- 我准备自己实现一个简化索引，应该怎么做？
- 为什么同事在我指出错误后生气？
- 为什么团队总在争核心项目？
- 猪肉价格为什么可能周期波动？
- 我怎样利用 AI 赚钱？
- 我应该留在当前公司还是接受新 Offer？
- 我得出“开车上班就不会迟到”，怎样检查这个小结论是否漏了条件？
- 我说了很多背景和多个问句，请先梳理核心问题、支撑问题和独立问题，再分析。
- 把以上分析写成一篇简洁、直白、因果完整的技术文章，控制换行和例子。

Skill 会先在内部整理输入、建立问题结构、判断目的结构是否适用、选择相关主体指南、校验关键节点，再按用户需要输出直接回答或成稿，不展示内部路由和检查脚手架。
